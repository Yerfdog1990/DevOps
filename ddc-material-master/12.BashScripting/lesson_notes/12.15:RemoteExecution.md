# Bash Scripting — Remote Execution

## Overview

Remote execution allows `scriptbox` to run commands on `web01`, `web02`, and `web03` without manually logging into each machine. Combined with SSH key-based authentication and passwordless `sudo`, this becomes the foundation for automated server management — the same approach used by tools like Ansible.

---

## The Setup — VMs and Network

### Vagrantfile

Four VMs are defined:

```ruby
Vagrant.configure("2") do |config|

  config.vm.define "scriptbox" do |scriptbox|
    scriptbox.vm.box = "eurolinux-vagrant/centos-stream-9"
    scriptbox.vm.network "private_network", ip: "192.168.10.12"
    scriptbox.vm.hostname = "scriptbox"
    scriptbox.vm.provider "virtualbox" do |vb|
      vb.memory = "1024"
    end
  end

  config.vm.define "web01" do |web01|
    web01.vm.box = "eurolinux-vagrant/centos-stream-9"
    web01.vm.network "private_network", ip: "192.168.10.13"
    web01.vm.hostname = "web01"
  end

  config.vm.define "web02" do |web02|
    web02.vm.box = "eurolinux-vagrant/centos-stream-9"
    web02.vm.network "private_network", ip: "192.168.10.14"
    web02.vm.hostname = "web02"
  end

  config.vm.define "web03" do |web03|
    web03.vm.box = "ubuntu/bionic64"
    web03.vm.network "private_network", ip: "192.168.10.15"
    web03.vm.hostname = "web03"
  end

end
```

| VM | OS | IP Address | Role |
|----|-----|------------|------|
| `scriptbox` | CentOS Stream 9 | `192.168.10.12` | Control node — runs scripts remotely |
| `web01` | CentOS Stream 9 | `192.168.10.13` | Target server |
| `web02` | CentOS Stream 9 | `192.168.10.14` | Target server |
| `web03` | Ubuntu Bionic 64 | `192.168.10.15` | Target server (Ubuntu) |

> `web03` is optional. If your machine does not have enough resources, it can be skipped. It is included to demonstrate cross-distribution scripting (CentOS vs Ubuntu).

## Step 1 — Set Hostnames on Each VM

Log into each VM and set its hostname so it shows correctly in the shell prompt:

```bash
# On each VM:
sudo vi /etc/hostname
# Type the VM name (web01, web02, web03) and save
```

The hostname makes it clear which machine you are connected to at any time.

## Step 2 — Add Hostname-to-IP Mappings on `scriptbox`

Edit `/etc/hosts` on `scriptbox` so it can resolve the web VM hostnames without needing DNS:

```bash
vi /etc/hosts
```

Add:

```
192.168.10.13   web01
192.168.10.14   web02
192.168.10.15   web03
```

## Step 3 — Create the `devops` User on Each Web VM

A dedicated `devops` user is created on each web server. This is the user `scriptbox` will use for remote execution — not `vagrant` or `root`.

### On CentOS VMs (web01 and web02)

Log in and create the user:

```bash
vagrant ssh web01
sudo -i
useradd devops
passwd devops
```

```text
[root@web01 ~]# useradd devops
[root@web01 ~]# passwd devops
Changing password for user devops.
New password:
BAD PASSWORD: The password is shorter than 8 characters
Retype new password:
passwd: all authentication tokens updated successfully.
```

> The "BAD PASSWORD" warning means the password does not meet quality requirements, but root can still set it. The account is created successfully.

Repeat on `web02`.

### On Ubuntu VM (web03)

Ubuntu uses `adduser` instead of `useradd` for interactive user creation:

```bash
vagrant ssh web03
sudo -i
adduser devops
```

`adduser` on Ubuntu is more interactive — it automatically creates the home directory, primary group, and prompts for a password in one command. `useradd` on Ubuntu works too but requires extra flags (`-m` for home directory, then a separate `passwd` call).

## Step 4 — Grant `devops` Passwordless `sudo` Access

The `devops` user needs to run system commands (like `systemctl`, `useradd`) with elevated privileges without being prompted for a password.

### CentOS VMs — Edit Sudoers with `visudo`

```bash
visudo
```

Add this line:

```
devops  ALL=(ALL)       NOPASSWD: ALL
```

**Always use `visudo`** — it validates the syntax before saving. A typo in `/etc/sudoers` can break `sudo` access entirely.

### Ubuntu VM — Same Process

```bash
visudo
```

Add:

```
devops  ALL=(ALL:ALL) NOPASSWD: ALL
```

Note: Ubuntu uses `(ALL:ALL)` (user:group) instead of `(ALL)`, but both formats work.

### Verify `sudo` Access

```bash
su - devops
sudo -l
# Should show: (ALL) NOPASSWD: ALL

sudo whoami
# Output: root (no password prompt)
```

## Step 5 — Enable Password Authentication on `web03` (Ubuntu)

Ubuntu's SSH defaults to **key-only login** — password authentication is disabled. When trying to SSH to `web03` from `scriptbox`, you get:

```
Permission denied (publickey)
```

To allow password login (needed to copy the SSH key in the next step):

```bash
vi /etc/ssh/sshd_config
```

Find and change:

```
PasswordAuthentication yes
```

Restart SSH:

```bash
systemctl restart ssh      # Ubuntu uses 'ssh', not 'sshd'
```

Now SSH password login works for `web03`.

## Step 6 — Set Up SSH Key-Based Authentication

Password-based login requires a password every time a command runs. For automation, **SSH key-based authentication** is used — no password needed for each connection.

### How SSH Keys Work

SSH key authentication uses a **matched key pair**:

| Key | Location | Behaviour |
|-----|----------|-----------|
| **Private key** (`id_rsa`) | Stays on `scriptbox` — never shared | Used to prove identity |
| **Public key** (`id_rsa.pub`) | Copied to each web server | Acts like a lock |

When you connect, `scriptbox` uses the private key to solve a cryptographic challenge from the server. The server verifies it with the public key. If they match, access is granted — **no password transmitted**.

Think of it as: **public key = padlock, private key = the key to open it**. You can give everyone a copy of the padlock, but only you have the key to open it.

### Generate the Key Pair on `scriptbox`

```bash
ssh-keygen
```

```text
Generating public/private rsa key pair.
Enter file in which to save the key (/root/.ssh/id_rsa):   ← press Enter
Enter passphrase (empty for no passphrase):                ← press Enter
Enter same passphrase again:                               ← press Enter
Your identification has been saved in /root/.ssh/id_rsa
Your public key has been saved in /root/.ssh/id_rsa.pub
The key fingerprint is:
SHA256:/nLdT2oQztdsQCRJIJPcfcwvm9tXgRzVQmb9JflpnI8 root@scriptbox
```

Two files are created:

```bash
ls ~/.ssh/
# id_rsa        ← private key (never share this)
# id_rsa.pub    ← public key (safe to distribute)
```

You can identify which is which by reading the content — private keys begin with `-----BEGIN OPENSSH PRIVATE KEY-----`, public keys are much shorter and begin with `ssh-rsa`.

### Copy the Public Key to Each Web Server

```bash
ssh-copy-id devops@web01
ssh-copy-id devops@web02
ssh-copy-id devops@web03
```

Each command:
1. Logs into the server (using the password — last time you need it)
2. Creates `/home/devops/.ssh/` if it doesn't exist
3. Appends the public key to `/home/devops/.ssh/authorized_keys`

```text
[root@scriptbox ~]# ssh-copy-id devops@web01
/bin/ssh-copy-id: INFO: 1 key(s) remain to be installed
devops@web01's password:
Number of key(s) added: 1
Now try logging into the machine, with: "ssh 'devops@web01'"

[root@scriptbox ~]# ssh-copy-id devops@web02
...
Number of key(s) added: 1

[root@scriptbox ~]# ssh-copy-id devops@web03
...
Number of key(s) added: 1
```

## Step 7 — Test Remote Execution

### Before Key Setup — Password Required Every Time

```bash
ssh devops@web01 uptime
# devops@web01's password: ← must type password
# 22:47:30 up 1:01, 0 users, load average: 0.00, 0.00, 0.00
```

### After Key Setup — No Password Needed

```bash
[root@scriptbox ~]# ssh devops@web01 uptime
22:59:12 up 1:12,  0 users,  load average: 0.00, 0.00, 0.00
```

No password prompt. The command ran on `web01` and the result appeared on `scriptbox`. You stayed on `scriptbox` the whole time.

This is **remote execution** — run a command on a remote machine from a local script without interactive login.

---

## How Remote Execution Works

```bash
ssh devops@web01 "command"
```

SSH connects to `web01` as `devops`, executes the command, returns the output, and returns you to your current shell. No need to log in, run the command, and log out manually.

```bash
# Run multiple commands:
ssh devops@web01 "hostname && uptime && df -h"

# Run privileged commands (NOPASSWD: ALL makes this work without a password):
ssh devops@web01 "sudo systemctl restart httpd"
```

## Running Remote Commands with a `for` Loop

Now that all three servers accept key-based login, you can use a `for` loop to run a command across all of them at once:

```bash
for host in web01 web02 web03
do
    ssh devops@$host hostname
done
```

Output:

```text
web01
web02
web03
```

Or run privileged commands on all servers:

```bash
for host in web01 web02 web03
do
    ssh devops@$host "sudo whoami"
done
```

Output:

```text
root
root
root
```

This is a simple form of the same approach that automation tools like **Ansible** use at scale.

## Summary of the Setup Process

```
1. Set hostnames on each web VM
2. Add hostname-to-IP entries in scriptbox's /etc/hosts
3. Create devops user on each web VM
4. Add devops to sudoers with NOPASSWD: ALL
5. Enable PasswordAuthentication on web03 (Ubuntu only)
6. Generate SSH key pair on scriptbox (ssh-keygen)
7. Copy public key to all web VMs (ssh-copy-id)
8. Test: ssh devops@web01 uptime (no password prompt)
```

---

## Why This Architecture Matters

| Before | After |
|--------|-------|
| Must log into each server, run commands, log out | Run commands on any server from `scriptbox` in one line |
| Password required every time | No password — SSH key handles authentication |
| Manual repetition for each server | `for` loop runs the same command across all servers |
| Not automatable (password prompts block scripts) | Fully automatable — scripts can run unattended |

This is the foundation for configuration management, deployment automation, and tools like Ansible — where one control node manages many servers using exactly this setup (SSH keys + passwordless sudo).
