# Monolithic vs Microservices Architecture

## Why This Matters for DevOps

Before diving into Docker and containers, it is important to understand *why* they exist. The shift from monolithic to microservices architecture is the primary driver behind containerisation — and as a DevOps engineer, you will be the one running, deploying, and maintaining these services. Understanding the architecture tells you what to expect operationally.

---

## Monolithic Architecture

### What Is It?

A **monolithic application** is one where all components of the application are built, deployed, and run as a **single, unified unit**. The entire application lives in one codebase and is packaged into one deployable artifact.

Think of the vProfile project: the entire application — user login, dashboard, posts, chat, notifications — is compiled into a single WAR file (`vprofile-v2.war`) and deployed to one Tomcat server. That is a monolith.

```
┌─────────────────────────────────────┐
│         vprofile-v2.war             │
│  ┌──────────┐  ┌─────────────────┐  │
│  │   UI     │  │  Business Logic │  │
│  ├──────────┤  ├─────────────────┤  │
│  │  Posts   │  │  Notifications  │  │
│  ├──────────┤  ├─────────────────┤  │
│  │   Chat   │  │  User Accounts  │  │
│  └──────────┘  └─────────────────┘  │
│            Single Database          │
└─────────────────────────────────────┘
          Deployed on one Tomcat
```

Everything must be written in the same language. Because vProfile started in Java, all sub-services must remain in Java. The architecture is like an elephant — it works, but it is difficult to move and slow to change.

### Key Characteristics

- **Single codebase** — all components developed and maintained together
- **Shared memory** — components communicate within the same process without network overhead
- **Centralised database** — one database handles all data storage
- **One deployment unit** — any change, no matter how small, requires redeploying the entire application
- **One language/stack** — all components must use the same technology

### Advantages

- Simple to develop, test, and deploy — everything is in one place
- Easier to debug — all components run in the same process
- Better performance for small applications — no inter-service network overhead
- Lower initial cost — less infrastructure needed
- Good for MVPs, small teams, and simple applications

### Disadvantages and Challenges

| Challenge | Impact |
|-----------|--------|
| **Long deployment cycles** | Every change — even a single line — requires repackaging and redeploying the entire application |
| **Risk of downtime** | Deployments often require taking the full application offline |
| **Limited scalability** | Scaling means duplicating the entire application stack, not just the component that needs more resources |
| **Tight coupling** | A bug in one component can bring down the entire application |
| **Technology lock-in** | Difficult to adopt new languages, frameworks, or libraries |
| **Growing complexity** | As the codebase grows, it becomes increasingly difficult to understand, maintain, and modify |

### Scaling a Monolith

Scaling strategies for monolithic applications include:

- **Vertical scaling** — add more CPU, RAM, or storage to the existing server
- **Load balancing** — run multiple instances of the whole application behind a load balancer
- **Caching** — reduce repeated database calls with in-memory caching (like Memcached in vProfile)
- **Database optimisation** — query tuning, indexing, database sharding

These strategies have limits — you can only scale the entire application, not individual parts of it.

## Microservices Architecture

### What Is It?

In a **microservices architecture**, an application is broken down into small, independent services — each one handling a single, specific business function. These services are deployed separately and communicate with each other over well-defined APIs.

Using the same vProfile example transformed into microservices:

```
┌──────────┐  ┌──────────┐  ┌──────────────┐  ┌──────────────┐
│    UI    │  │   Chat   │  │ Notification │  │    Posts     │
│  (Java)  │  │ (Node.js)│  │   (Python)   │  │    (Ruby)    │
└────┬─────┘  └────┬─────┘  └──────┬───────┘  └──────┬───────┘
     │             │               │                 │
     └─────────────┴───────────────┴─────────────────┘
                          │
                   ┌──────▼──────┐
                   │ API Gateway │
                   └─────────────┘
```

Each service:
- Has its own codebase
- Can be written in any language
- Has its own database
- Can be deployed independently
- Communicates via APIs

### Key Characteristics

- **Loosely coupled** — services are independent; a failure in one does not necessarily bring down others
- **Technology freedom** — each service can use the best language or framework for its job (Java, Python, Node.js, Ruby, Go)
- **Independent deployment** — update and redeploy one service without touching the others
- **Independent scaling** — scale only the service that needs more resources
- **API-based communication** — services talk to each other via HTTP REST APIs or message queues; the technology used internally is irrelevant

### The API Gateway

In a microservices system, external clients do not talk to individual services directly. Instead, all requests go through an **API Gateway** — a single entry point that:
- Routes requests to the correct microservice
- Handles authentication and authorisation
- Can perform load balancing and rate limiting
- Abstracts the internal service structure from the outside world

### Real-World Examples

| Company | How microservices are used |
|---------|--------------------------|
| **Amazon** | Separate services for product catalogue, cart, payment, order processing, notifications, recommendations, and logistics — each running independently |
| **Netflix** | Moved to microservices after facing major outages in 2007 — individual services for streaming, recommendations, user accounts, and billing |
| **Uber** | Switched from a monolith to microservices to handle global scale — separate services for rides, payments, driver matching, and notifications |

### Advantages

- **Independent development** — teams can work on different services simultaneously without blocking each other
- **Technology flexibility** — use the right tool for each job
- **Fault isolation** — one service failing does not bring down the entire system
- **Independent scaling** — scale only what needs scaling, reducing cost
- **Faster deployments** — deploy one small service rather than the entire application
- **Easier to understand** — each service is small and focused on one task

### Challenges

- **Operational complexity** — managing many services is harder than managing one
- **Network latency** — services communicate over the network; every inter-service call adds latency
- **Distributed data management** — maintaining data consistency across multiple databases is complex
- **Harder to debug** — a request may pass through multiple services; tracing failures is more difficult
- **More infrastructure needed** — each service needs its own deployment, monitoring, and logging setup

## The Isolation Problem — Why Containers Follow Microservices

Running a monolith is simple: one artifact, one server, one runtime.

Running microservices introduces an **isolation problem**:

- The UI service runs on Java/Tomcat
- The Chat service runs on Node.js
- The Notification service runs on Python
- The Posts service runs on Ruby

Each needs its own runtime environment, its own dependencies, its own configuration. If you run each on a dedicated VM:

```
Each service = one VM = one OS + runtime + dependencies + cost
```

With 10 microservices you have 10 VMs. With 50 microservices, 50 VMs. The infrastructure cost and management overhead escalates rapidly.

**The solution: containerisation.**

Each microservice is packaged into a **container** (using Docker) — a lightweight, isolated unit that includes the service and all its dependencies. Multiple containers run on the same host, sharing the OS kernel but remaining isolated from each other.

```
┌────────────────────────────────────────┐
│              Docker Host               │
│  ┌────────┐ ┌────────┐ ┌────────────┐  │
│  │  UI    │ │  Chat  │ │Notification│  │
│  │(Java)  │ │(Node)  │ │ (Python)   │  │
│  └────────┘ └────────┘ └────────────┘  │
│         Shared OS Kernel               │
└────────────────────────────────────────┘
```

This is why **microservices and containers are always mentioned together**. Microservices create the need for isolation; containers provide it efficiently and at low cost.

## Monolithic vs Microservices — Side by Side

| Aspect | Monolithic | Microservices |
|--------|-----------|---------------|
| Structure | Single unified application | Many small, independent services |
| Deployment | Entire app deployed as one unit | Each service deployed independently |
| Language | One language/stack for everything | Each service can use any language |
| Scaling | Scale the entire application | Scale individual services as needed |
| Database | Single shared database | Each service has its own database |
| Failure impact | One bug can crash the whole app | Failures are isolated to one service |
| Development speed | Simple initially; slows as app grows | More complex initially; scales better |
| Communication | In-process (fast) | Over the network via APIs (adds latency) |
| Debugging | Easier — everything in one place | Harder — traces span multiple services |
| Infrastructure cost | Lower — one server/deployment | Higher — many services need management |
| Best for | Small teams, MVPs, simple apps | Large teams, complex apps, high scale |

## Migrating from Monolithic to Microservices

This is a common real-world challenge. The recommended approach is gradual migration rather than a full rewrite:

1. **Evaluate** — identify the current monolith's components and which can be separated
2. **Decompose by business function** — each microservice should own one clear capability
3. **Strangler Fig Pattern** — gradually replace parts of the monolith with microservices while the old system remains running; over time the monolith "shrinks" until it can be retired
4. **Separate databases** — give each new microservice its own database schema to remove data coupling
5. **Define APIs** — establish clear API contracts for how services will communicate
6. **Set up CI/CD pipelines** — automate testing and deployment for each independent service
7. **Add observability** — centralised logging and monitoring become essential when you have many services

## DevOps Takeaway

| Architecture | What it means for DevOps |
|-------------|--------------------------|
| **Monolithic** | One artifact, one deployment, one server — simpler to operate |
| **Microservices** | Many artifacts, many deployments, many services — requires automation, containers, orchestration (Kubernetes), and strong CI/CD pipelines |

If you see **microservices** in a project, expect:
- **Docker** — for containerising each service
- **Kubernetes** — for orchestrating and scaling many containers
- **CI/CD pipelines** — for independently building and deploying each service
- **API Gateway** — for routing external traffic to the right service
- **Centralised logging and monitoring** — for visibility across many running services

All of these topics are covered later in the course.
