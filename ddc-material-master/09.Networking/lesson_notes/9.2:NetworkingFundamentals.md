## Overview

Networking commands are essential tools for diagnosing connectivity issues, scanning open ports, resolving DNS names, and tracing the path packets take across a network. This session uses five virtual machines defined in the Vagrantfile below to demonstrate these commands in a real environment:

| VM | Hostname | IP Address | OS | Service | Port | Memory |
|----|---------|-----------|-----|---------|------|--------|
| `web01` | web01 | `192.168.56.11` | Ubuntu Jammy 64 | Nginx (web server) | 80 | 800 MB |
| `app01` | app01 | `192.168.56.12` | CentOS Stream 9 | Tomcat (app server) | 8080 | 800 MB |
| `rmq01` | rmq01 | `192.168.56.13` | CentOS Stream 9 | RabbitMQ (message queue) | 5672 | 600 MB |
| `mc01` | mc01 | `192.168.56.14` | CentOS Stream 9 | Memcache (caching) | 11211 | 600 MB |
| `db01` | db01 | `192.168.56.15` | CentOS Stream 9 | MariaDB (database) | 3306 | 600 MB |

All VMs sit on the same private network (`192.168.56.0/24`) and can communicate with each other directly by IP or hostname (handled automatically by the `hostmanager` plugin).

**Line-by-line explanation:**

**Interface 1 — `lo` (Loopback)**

```
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 ...
    inet 127.0.0.1/8 scope host lo
       valid_lft forever preferred_lft forever
```

| Part | Meaning |
|------|---------|
| `lo` | Loopback interface — the machine talking to itself |
| `LOOPBACK,UP,LOWER_UP` | Interface is configured and active |
| `mtu 65536` | Maximum Transmission Unit — loopback allows very large packets |
| `inet 127.0.0.1/8` | The standard loopback IPv4 address (`/8` = subnet includes the whole 127.x.x.x range) |
| `valid_lft forever` | This address never expires |
| `inet6 ::1/128` | IPv6 loopback address (equivalent of 127.0.0.1) |

> The loopback interface is used when a process on the machine connects to itself — for example, a web app connecting to `localhost`.

---

**Interface 2 — `enp0s3` (NAT / Internet)**

```
2: enp0s3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
    link/ether 02:aa:f8:fc:c7:1b brd ff:ff:ff:ff:ff:ff
    inet 10.0.2.15/24 metric 100 brd 10.0.2.255 scope global dynamic enp0s3
       valid_lft 86278sec preferred_lft 86278sec
```

| Part | Meaning |
|------|---------|
| `enp0s3` | First physical network adapter (VirtualBox NAT adapter) |
| `BROADCAST,MULTICAST,UP,LOWER_UP` | Interface supports broadcast, is active, and has a physical link |
| `mtu 1500` | Standard Ethernet MTU — maximum packet size |
| `link/ether 02:aa:f8:fc:c7:1b` | MAC (hardware) address of this interface |
| `brd ff:ff:ff:ff:ff:ff` | Broadcast MAC address |
| `inet 10.0.2.15/24` | IPv4 address assigned by VirtualBox NAT (`/24` = 255.255.255.0 subnet) |
| `brd 10.0.2.255` | Broadcast address for this subnet |
| `scope global dynamic` | Publicly routable address, assigned dynamically (DHCP) |
| `metric 100` | Routing priority — lower metric = preferred route |
| `valid_lft 86278sec` | DHCP lease expires in ~24 hours (86278 ÷ 3600 ≈ 24h) |

> This is the interface VirtualBox uses to give the VM internet access by NATting through your host machine. The `10.0.2.x` range is VirtualBox's default NAT network.

---

**Interface 3 — `enp0s8` (Private Network)**

```
3: enp0s8: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
    link/ether 08:00:27:2e:c3:fa brd ff:ff:ff:ff:ff:ff
    inet 192.168.56.11/24 brd 192.168.56.255 scope global enp0s8
       valid_lft forever preferred_lft forever
```

| Part | Meaning |
|------|---------|
| `enp0s8` | Second network adapter (VirtualBox Host-Only adapter) |
| `link/ether 08:00:27:2e:c3:fa` | MAC address — `08:00:27` prefix identifies Oracle VirtualBox |
| `inet 192.168.56.11/24` | The **static IP** we set in the Vagrantfile for `web01` |
| `scope global` | Address is valid for communication beyond the local machine |
| `valid_lft forever` | Static address — no expiry (not DHCP) |
| `brd 192.168.56.255` | Broadcast address — packets sent here reach all VMs on the 56.x network |

> This is the interface that connects all five VMs together. `web01` uses this interface to communicate with `db01` (192.168.56.15), `app01` (192.168.56.12), etc.

**Key addresses summary:**

| Address | Interface | Purpose |
|---------|-----------|---------|
| `127.0.0.1` | `lo` | Loopback — machine talking to itself |
| `10.0.2.15` | `enp0s3` | NAT — internet access via VirtualBox |
| `192.168.56.11` | `enp0s8` | Private network — VM-to-VM communication |

If `ifconfig` is not available, use:
```bash
ip addr show
```

## 2. `ping` — Test Network Connectivity

**Purpose:** Send ICMP packets to a target IP address to check whether there is a network connection between two machines.

```bash
# Ping db01 by IP address
ping 192.168.56.15

# Ping app01 by IP address
ping 192.168.56.12

# Ping by hostname (works automatically via the hostmanager plugin)
ping db01
ping app01
```

**Example output:**
```
12 packets transmitted, 12 received, 0% packet loss
```

**Behaviour difference between OS:**

| OS | Behaviour |
|----|----------|
| Windows | Sends 4 packets and stops |
| Linux | Sends unlimited packets — press `Ctrl+C` to stop |

**What ping tells you:**
- ✅ Replies received → there is network connectivity
- ❌ No replies → the target is unreachable or blocking ICMP
- ⚠️ Packet loss → unstable connection between the two machines

### Resolving Hostnames with `/etc/hosts`

Because the Vagrantfile uses `config.hostmanager.enabled = true`, hostnames are automatically registered on every VM. You can also add entries manually:

```bash
# Edit the hosts file
sudo nano /etc/hosts

# Add entries for each VM
192.168.56.11   web01
192.168.56.12   app01
192.168.56.13   rmq01
192.168.56.14   mc01
192.168.56.15   db01
```

Now you can use hostnames directly:
```bash
ping db01      # Resolves to 192.168.56.15
ping app01     # Resolves to 192.168.56.12
```

## 3. `traceroute` / `tracert` — Trace the Network Path

**Purpose:** Show every hop (router) a packet passes through on its way to the destination, along with the latency at each hop.

> **Note:** `traceroute` is not installed by default on Ubuntu. Install it first:
> ```bash
> apt install traceroute
> ```

```bash
# Linux
traceroute www.google.com

# Windows (Command Prompt or PowerShell)
tracert www.google.com
```

**Real output — run from a Mac host machine (not inside the VM):**

```

10  142.251.204.204 (142.251.204.204)  8.888 ms  9.600 ms
    142.251.150.119 (142.251.150.119)  9.451 ms
```

**Line-by-line explanation:**

| Line | What it means |
|------|--------------|
| `Warning: www.google.com has multiple addresses` | Google uses many IPs for load balancing. `traceroute` picked one to trace |
| `64 hops max` | The maximum number of routers the probe will pass through before giving up |
| `40 byte packets` | The size of each probe packet sent |
| **Hop 1** `192.168.1.1` | Your **local home router** — the first device traffic exits through |
| **Hop 2** `100.85.0.1` | Your **ISP's first router** — traffic has left your home network |
| **Hop 3** `eth12.bpi.sila1-bcr02.myaisfibre.com` | A backbone router at your ISP (AIS Fibre). Two different paths (`.30` and `.46`) are shown because packets took slightly different routes |
| **Hop 4–5** `myaisfibre.com` routers | Further routing within the ISP's core network |
| **Hop 6** `* * *` | This router **did not respond** to the probe packets — it is configured to silently drop them (common on ISP routers). It does not mean the connection is broken |
| **Hop 7** `ais-idc.com` | Traffic entering an AIS data center / peering point |
| **Hops 8–9** `10.30.x.x` | Internal private addresses inside the ISP/data center network — not publicly routable |
| **Hop 10** `142.251.x.x` | **Google's network** — the packet has arrived. `142.251.150.119` is the final destination |

**Reading the three latency columns (e.g., `9.115 ms  2.405 ms  1.675 ms`):**

Each hop sends **three probe packets**. The three numbers are the round-trip time for each one in milliseconds.
- Consistent low values → healthy, low-latency hop
- One high value, two low → a spike, probably normal jitter
- All three consistently high → the bottleneck is at or before this hop

**What `* * *` means:**

The router at hop 6 did not send a reply. This is normal — many routers are configured to ignore diagnostic probe packets for security. It does not mean the path is broken, because subsequent hops responded successfully.

> **Why run from the host, not the VM?** Inside a VirtualBox VM, the NAT adapter hides the VM behind the host's network, so `traceroute` can only see as far as the VirtualBox gateway and no further. Run it from your Mac/Windows host to see the real path.

## 4. `netstat` — View Open Ports and Connections

**Purpose:** Display all open TCP ports on the current machine, along with the process using each port.

```bash
netstat -antp
```

| Flag | Meaning |
|------|---------|
| `-a` | Show all sockets (listening and established) |
| `-n` | Show numeric addresses (no DNS resolution) |
| `-t` | Show TCP connections only |
| `-p` | Show the process ID (PID) and process name |

**Real output from `web01`:**

```
root@web01:~# netstat -antp
Active Internet connections (servers and established)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name
tcp        0      0 0.0.0.0:22              0.0.0.0:*               LISTEN      799/sshd: /usr/sbin
tcp        0      0 127.0.0.53:53           0.0.0.0:*               LISTEN      583/systemd-resolve
tcp        0      0 10.0.2.15:22            10.0.2.2:50056          ESTABLISHED 2260/sshd: vagrant
tcp6       0      0 :::22                   :::*                    LISTEN      799/sshd: /usr/sbin
```

**Column-by-column explanation:**

| Column | Meaning |
|--------|---------|
| `Proto` | Protocol — `tcp` (IPv4) or `tcp6` (IPv6) |
| `Recv-Q` | Bytes received but not yet read by the application (0 = healthy) |
| `Send-Q` | Bytes sent but not yet acknowledged by the remote end (0 = healthy) |
| `Local Address` | The IP and port this machine is listening on or connected from |
| `Foreign Address` | The remote IP and port (0.0.0.0:* means any remote address) |
| `State` | `LISTEN` = waiting for connections; `ESTABLISHED` = active connection |
| `PID/Program name` | The process ID and name of the program holding this socket |

**Row-by-row explanation:**

| Row | Meaning |
|-----|---------|
| `0.0.0.0:22 LISTEN 799/sshd` | SSH is listening on **all interfaces** (any IP can connect on port 22) |
| `127.0.0.53:53 LISTEN 583/systemd-resolve` | The local DNS resolver is listening on loopback only — handles DNS queries from this machine |
| `10.0.2.15:22 → 10.0.2.2:50056 ESTABLISHED` | An **active SSH session** from `10.0.2.2` (your host machine via VirtualBox NAT) to this VM — this is your current terminal connection |
| `:::22 LISTEN 799/sshd` | SSH also listening on all **IPv6** interfaces |

> **Why is apache2 not shown?** Nginx is the web service for `web01` in this lab, and it has not been installed yet in this output — only SSH and the DNS resolver are running.

**Finding what port a specific process is using:**

```bash
# Search for apache2 process
ps -ef | grep apache2

# The grep itself appears as a result — that is normal
root  3949  2340  0 03:23 pts/1  00:00:00 grep --color=auto apache2
# This means apache2 is NOT running — only the grep command itself showed up
```

> When `grep` returns only its own process and not the actual service, the service is **not running** on this machine.

## 5. `ss` — Socket Statistics (Modern `netstat`)

**Purpose:** A faster, more detailed alternative to `netstat` for viewing open ports and active connections.

```bash
ss -tunlp
```

| Flag | Meaning |
|------|---------|
| `-t` | Show TCP sockets |
| `-u` | Show UDP sockets |
| `-n` | Numeric addresses (no DNS) |
| `-l` | Show only listening sockets |
| `-p` | Show process name and PID |

**Real output from `web01`:**

```
root@web01:~# ss -tunlp
Netid   State    Recv-Q  Send-Q  Local Address:Port    Peer Address:Port  Process
udp     UNCONN   0       0       127.0.0.53%lo:53           0.0.0.0:*     users:(("systemd-resolve",pid=583,fd=13))
udp     UNCONN   0       0       10.0.2.15%enp0s3:68        0.0.0.0:*     users:(("systemd-network",pid=1626,fd=18))
udp     UNCONN   0       0       [fe80::a00:27ff:fe2e:c3fa]%enp0s8:546    [::]:*     users:(("systemd-network",pid=1626,fd=23))
tcp     LISTEN   0       128     0.0.0.0:22                 0.0.0.0:*     users:(("sshd",pid=799,fd=3))
tcp     LISTEN   0       4096    127.0.0.53%lo:53           0.0.0.0:*     users:(("systemd-resolve",pid=583,fd=14))
tcp     LISTEN   0       128     [::]:22                    [::]:*        users:(("sshd",pid=799,fd=4))
```

**Row-by-row explanation:**

| Row | Meaning |
|-----|---------|
| `udp 127.0.0.53%lo:53` → `systemd-resolve` | UDP DNS listener on loopback — answers DNS queries from applications on this machine |
| `udp 10.0.2.15%enp0s3:68` → `systemd-network` | DHCP client on the NAT interface — listens for DHCP lease renewals from the VirtualBox NAT server |
| `udp [fe80::...]:546` → `systemd-network` | DHCPv6 client on the private network interface — IPv6 address configuration |
| `tcp 0.0.0.0:22 LISTEN` → `sshd pid=799` | SSH listening on all IPv4 interfaces. `Send-Q=128` is the connection backlog limit |
| `tcp 127.0.0.53%lo:53 LISTEN` → `systemd-resolve pid=583` | DNS resolver also listening on TCP (for large DNS responses that don't fit in UDP) |
| `tcp [::]:22 LISTEN` → `sshd pid=799` | SSH also listening on all IPv6 interfaces |

**Reading the `users:` field:**

```
users:(("sshd",pid=799,fd=3))
```

| Part | Meaning |
|------|---------|
| `"sshd"` | The process name holding this socket |
| `pid=799` | The process ID — use this with `ps -ef` or `kill` |
| `fd=3` | The file descriptor number within the process that owns this socket |

> `ss` is the recommended replacement for `netstat` on modern Linux systems. It reads directly from the kernel and is significantly faster on machines with many connections.

## 6. `nmap` — Network Port Scanner

**Purpose:** Scan open ports on a target machine. Primarily used to check whether a specific port is accessible from another machine.

```bash
# Install if not present
apt install nmap        # Ubuntu (web01)
dnf install nmap        # CentOS Stream 9 (db01, app01, mc01, rmq01)
```

**Real output — scanning localhost:**

```
root@web01:~# nmap localhost
Starting Nmap 7.80 ( https://nmap.org ) at 2026-06-01 03:28 UTC
Nmap scan report for localhost (127.0.0.1)
Host is up (0.0000040s latency).
Not shown: 999 closed ports
PORT   STATE SERVICE
22/tcp open  ssh
Nmap done: 1 IP address (1 host up) scanned in 0.11 seconds
```

| Part | Meaning |
|------|---------|
| `Nmap 7.80` | Version of nmap installed |
| `Host is up (0.0000040s latency)` | The machine responded — latency of 0.000004 seconds because it is scanning itself |
| `Not shown: 999 closed ports` | Nmap scanned 1000 common ports; 999 were closed and not shown to keep output clean |
| `22/tcp open ssh` | Port 22 is open and running SSH — the only service currently listening |
| `1 IP address (1 host up) scanned in 0.11 seconds` | Scan completed in 0.11 seconds |

---

**Real output — scanning `db01` from `web01`:**

```
root@web01:~# nmap 192.168.56.15
Starting Nmap 7.80 ( https://nmap.org ) at 2026-06-01 03:29 UTC
Nmap scan report for db01 (192.168.56.15)
Host is up (0.0029s latency).
Not shown: 998 filtered ports
PORT     STATE  SERVICE
22/tcp   open   ssh
9090/tcp closed zeus-admin
MAC Address: 08:00:27:87:C3:82 (Oracle VirtualBox virtual NIC)
Nmap done: 1 IP address (1 host up) scanned in 9.75 seconds
```

| Part | Meaning |
|------|---------|
| `Host is up (0.0029s latency)` | `db01` responded in 2.9ms — it is reachable on the private network |
| `Not shown: 998 filtered ports` | 998 ports did not respond — likely blocked by a firewall (CentOS Stream 9 enables `firewalld` by default) |
| `22/tcp open ssh` | SSH is open and accessible from `web01` |
| `9090/tcp closed zeus-admin` | Port 9090 actively refused the connection (not filtered, just not in use) |
| `MAC Address: 08:00:27:87:C3:82 (Oracle VirtualBox virtual NIC)` | The MAC address of `db01`'s network card — the `08:00:27` prefix confirms it is a VirtualBox VM |
| `scanned in 9.75 seconds` | Scanning a remote machine takes much longer than localhost because each filtered port must time out |

> **Filtered vs Closed:** `filtered` means a firewall is silently dropping probe packets. `closed` means the machine actively responded with a "connection refused" — the port is reachable but no service is listening on it.

```
;; WHEN: Mon Jun 01 03:31:20 UTC 2026
;; MSG SIZE  rcvd: 171
```

**Section-by-section explanation:**

**Header:**
```
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 29604
;; flags: qr rd ra; QUERY: 1, ANSWER: 8, AUTHORITY: 0, ADDITIONAL: 1
```

| Part | Meaning |
|------|---------|
| `status: NOERROR` | The DNS query succeeded — no errors |
| `flags: qr` | This is a **query response** (not a query) |
| `flags: rd` | **Recursion Desired** — the client asked the server to look up the full answer |
| `flags: ra` | **Recursion Available** — the server confirmed it supports recursive lookups |
| `ANSWER: 8` | The DNS server returned 8 IP addresses for this hostname |

**Question Section:**
```
;www.google.com.    IN    A
```
This shows what was asked: the **A record** (IPv4 address) for `www.google.com`.

**Answer Section:**
```
www.google.com.    263    IN    A    142.251.155.119
```

| Part | Meaning |
|------|---------|
| `www.google.com.` | The hostname that was resolved |
| `263` | **TTL (Time To Live)** in seconds — this answer can be cached for 263 seconds (~4 minutes) |
| `IN` | Internet class (standard) |
| `A` | Record type — IPv4 address |
| `142.251.155.119` | One of Google's IP addresses |

> Google returns **8 different IP addresses** for load balancing. Each request may be sent to a different server. This is called **round-robin DNS**.

**Footer:**
```
;; Query time: 16 msec
;; SERVER: 127.0.0.53#53(127.0.0.53) (UDP)
```

| Part | Meaning |
|------|---------|
| `Query time: 16 msec` | How long the DNS lookup took |
| `SERVER: 127.0.0.53#53` | The DNS server that answered — `127.0.0.53` is `systemd-resolved`, the local DNS cache running on `web01` itself. It forwarded the query to an upstream server |

## 8. `route` — View the Routing Table and Gateway

**Purpose:** Display the kernel routing table, including the default gateway used to reach external networks.

**Real output from `web01`:**

```
root@web01:~# route -n
Kernel IP routing table
Destination     Gateway         Genmask         Flags Metric Ref    Use Iface
0.0.0.0         10.0.2.2        0.0.0.0         UG    100    0        0 enp0s3
10.0.2.0        0.0.0.0         255.255.255.0   U     100    0        0 enp0s3
10.0.2.2        0.0.0.0         255.255.255.255 UH    100    0        0 enp0s3
192.168.1.1     10.0.2.2        255.255.255.255 UGH   100    0        0 enp0s3
192.168.56.0    0.0.0.0         255.255.255.0   U     0      0        0 enp0s8
```

**Column explanation:**

| Column | Meaning |
|--------|---------|
| `Destination` | The target network or host. `0.0.0.0` means "everything else" (default route) |
| `Gateway` | The next-hop router to send packets through. `0.0.0.0` means "send directly" (no gateway needed) |
| `Genmask` | The subnet mask. `0.0.0.0` = matches any address; `255.255.255.255` = exact host match |
| `Flags` | `U` = route is Up; `G` = uses a Gateway; `H` = this is a Host route (not a network) |
| `Metric` | Priority — lower metric is preferred when multiple routes match |
| `Iface` | Which network interface to send the packet out of |

**Row-by-row explanation:**

| Row | Meaning |
|-----|---------|
| `0.0.0.0 → 10.0.2.2 via enp0s3` | **Default route** — all traffic that does not match a more specific rule is sent to `10.0.2.2` (the VirtualBox NAT gateway), which forwards it to the internet |
| `10.0.2.0 → 0.0.0.0 via enp0s3` | Traffic for the `10.0.2.0/24` subnet is sent directly out of `enp0s3` — no gateway needed |
| `10.0.2.2 → 0.0.0.0 via enp0s3` | The gateway itself (`10.0.2.2`) is directly reachable on `enp0s3` |
| `192.168.1.1 → 10.0.2.2 via enp0s3` | Your host machine's home router (`192.168.1.1`) is reached via the NAT gateway |
| `192.168.56.0 → 0.0.0.0 via enp0s8` | Traffic for the private VM network (`192.168.56.0/24`) is sent directly out of `enp0s8` — `web01` can reach `db01`, `app01`, etc. without a gateway |

**With hostnames (non `-n`):**

```
root@web01:~# route
Kernel IP routing table
Destination     Gateway         Genmask         Flags Metric Ref    Use Iface
default         _gateway        0.0.0.0         UG    100    0        0 enp0s3
10.0.2.0        0.0.0.0         255.255.255.0   U     100    0        0 enp0s3
_gateway        0.0.0.0         255.255.255.255 UH    100    0        0 enp0s3
192.168.1.1     _gateway        255.255.255.255 UGH   100    0        0 enp0s3
192.168.56.0    0.0.0.0         255.255.255.0   U     0      0        0 enp0s8
```

Same table but `0.0.0.0` is shown as `default` and `10.0.2.2` is shown as `_gateway` (resolved from `/etc/hosts`). Use `-n` to always see numeric addresses.

## 9. `arp` — View the ARP Table

**Purpose:** Display the kernel's ARP (Address Resolution Protocol) table, which maps IP addresses to MAC addresses of machines on the local network.

**Real output from `web01`:**

```
root@web01:~# arp
Address                  HWtype  HWaddress           Flags Mask  Iface
db01                     ether   08:00:27:87:c3:82   C           enp0s8
app01                    ether   08:00:27:f4:81:3c   C           enp0s8
_gateway                 ether   52:54:00:12:35:00   C           enp0s3
```

**Column explanation:**

| Column | Meaning |
|--------|---------|
| `Address` | The IP address or hostname of the remote machine |
| `HWtype` | Hardware type — `ether` means Ethernet |
| `HWaddress` | The MAC (hardware) address of that machine's network card |
| `Flags` | `C` = Complete entry (confirmed, actively used). Other values: `M` = manually set, `P` = published |
| `Iface` | Which local interface was used to reach this machine |

**Row-by-row explanation:**

| Row | Meaning |
|-----|---------|
| `db01 → 08:00:27:87:c3:82` via `enp0s8` | `web01` has recently communicated with `db01` (192.168.56.15) on the private network. The `08:00:27` prefix confirms it is a VirtualBox VM. Matches the MAC seen earlier in the `nmap` scan |
| `app01 → 08:00:27:f4:81:3c` via `enp0s8` | Same for `app01` — also matches the MAC from the nmap scan output |
| `_gateway → 52:54:00:12:35:00` via `enp0s3` | The VirtualBox NAT gateway (`10.0.2.2`) — `52:54:00` is a QEMU/KVM virtual MAC prefix used by VirtualBox's NAT engine |

> **How ARP works:** When a machine wants to send a packet to an IP on the same network, it first broadcasts an ARP request asking "Who has IP x.x.x.x?". The owner replies with its MAC address. That mapping is then cached in the ARP table so future packets can be sent directly without broadcasting.

> **Only local network entries appear** — ARP only works within the same subnet. You will never see entries for machines on different networks (e.g., `www.google.com`) in the ARP table.

## 10. `mtr` — Live Traceroute with Packet Loss

**Purpose:** A dynamic, continuously updating combination of `ping` and `traceroute`. It shows every hop to the destination and highlights where packet loss is occurring in real time.

**Real output from `web01`:**

```
root@web01:~# mtr www.google.com
                                    My traceroute  [v0.95]
web01 (10.0.2.15) -> www.google.com (142.251.153.119)              2026-06-01T03:36:45+0000
Keys:  Help   Display mode   Restart statistics   Order of fields   quit
                                                     Packets               Pings
 Host                                              Loss%   Snt   Last   Avg  Best  Wrst StDev
 1. 142.251.153.119                                 0.0%    65   16.2  14.3   9.4  76.8   8.5
```

**Header explanation:**

| Part | Meaning |
|------|---------|
| `web01 (10.0.2.15)` | Source machine and IP -- the VM's NAT interface |
| `www.google.com (142.251.153.119)` | Destination -- one of Google's IPs |
| `2026-06-01T03:36:45+0000` | Timestamp when the trace started |

**Column explanation:**

| Column | Meaning |
|--------|---------|
| `Host` | The hostname or IP of each hop along the path |
| `Loss%` | Percentage of packets lost at this hop |
| `Snt` | Total packets sent so far (65 in this output) |
| `Last` | Latency of the most recent packet in milliseconds (16.2ms) |
| `Avg` | Average latency across all packets sent (14.3ms) |
| `Best` | Lowest latency recorded (9.4ms) |
| `Wrst` | Highest latency recorded (76.8ms -- one spike) |
| `StDev` | Standard deviation -- measures how consistent the latency is (8.5ms = slightly variable) |

**Why only 1 hop is shown:**

Inside a VirtualBox NAT VM, the NAT engine intercepts traffic and connects directly to the destination -- the intermediate routers are hidden behind the host machine's network. Run `mtr` from your host machine to see the full path.

**Reading loss and latency:**
- `Loss% = 0.0%` -- no packets are being dropped -- healthy connection
- `Last 16.2ms, Avg 14.3ms, Best 9.4ms, Wrst 76.8ms` -- mostly consistent with one spike, normal
- `StDev 8.5ms` -- moderate variation; under 20ms is generally acceptable for internet traffic

Press `q` to quit.

## 11. `telnet` — Test if a Specific Port is Open

**Purpose:** Attempt a TCP connection to a specific port on a target machine to verify the port is reachable.

**Real output — SSH port on `db01`:**

```
root@web01:~# telnet 192.168.56.15 22
Trying 192.168.56.15...
Connected to 192.168.56.15.
Escape character is '^]'.
SSH-2.0-OpenSSH_8.7
```

**Line-by-line explanation:**

| Line | Meaning |
|------|---------|
| `Trying 192.168.56.15...` | telnet is attempting a TCP connection to that IP |
| `Connected to 192.168.56.15.` | TCP connection established — port 22 is open and accepting connections |
| `Escape character is '^]'.` | Press `Ctrl + ]` to reach the telnet prompt, then type `quit` to exit |
| `SSH-2.0-OpenSSH_8.7` | The SSH service sent its **banner** — protocol version SSH-2.0, server software OpenSSH 8.7. Confirms the service is running correctly |

**Testing all lab services:**

```bash
# MariaDB on db01
telnet 192.168.56.15 3306

# Tomcat on app01
telnet 192.168.56.12 8080

# RabbitMQ on rmq01
telnet 192.168.56.13 5672

# Memcache on mc01
telnet 192.168.56.14 11211

# SSH on any VM
telnet 192.168.56.15 22
```

**Possible outcomes:**

| Output | Meaning |
|--------|---------|
| `Connected to ...` + service banner | Port is open and service is running |
| `Connection refused` | Port is closed or service not running — machine responded but rejected the connection |
| `No route to host` | Machine is unreachable or does not exist at that IP |
| `Connection timed out` | Firewall is silently dropping packets — machine is up but blocking this port |

Press `Ctrl + ]` then type `quit` to exit telnet.

> If `nmap` is unavailable, `telnet` is a quick lightweight alternative to check whether a specific port is open.

## Troubleshooting Workflow

```
Cannot connect to a service?
         │
         ▼
ping <target IP>
  e.g. ping 192.168.56.15   (db01)
  e.g. ping 192.168.56.12   (app01)
  ├── No reply → network connectivity problem → check route, firewall
  └── Reply received
         │
         ▼
nmap <target IP>  OR  telnet <target IP> <port>
  e.g. nmap db01
  e.g. telnet 192.168.56.15 3306
  ├── Port closed → service not running or firewall blocking
  └── Port open
         │
         ▼
netstat -antp  (run on the target machine)
  ├── Port not listed → service not started
  └── Port listed → check application logs
         │
         ▼
dig <hostname>  OR  ping <hostname>
  e.g. dig db01
  ├── No answer → DNS/hostmanager resolution broken → check /etc/hosts
  └── Resolves correctly → application-level issue
```
