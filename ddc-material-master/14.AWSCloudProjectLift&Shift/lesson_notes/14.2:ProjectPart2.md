## 1. The Problem — Why We Need Private DNS

The vprofile application (`app01`) needs to connect to backend services: MySQL, Memcache, RabbitMQ. The question is: **how does the application know where these backend services are?**

### The application.properties File

```properties
jdbc.url=jdbc:mysql://db01.vprofile.in:3306/accounts?...
memcached.active.host=mc01.vprofile.in
rabbitmq.address=rmq01.vprofile.in
```

> The application references backend services by **hostname** (`db01.vprofile.in`), not by IP address. But network connectivity actually happens via IP — so these names must **resolve** to IP addresses somehow.

### Why NOT Hardcode IP Addresses

```
❌ Bad practice: jdbc.url=jdbc:mysql://172.31.20.45:3306/accounts

Problem: If the db01 instance is deleted and recreated,
         it gets a NEW private IP.
         → You'd have to edit application.properties
         → Rebuild the application
         → Redeploy
         → Just because an IP changed!
```

> **Golden rule:** Configuration files should always reference services by **name**, never by IP. Let a DNS service handle the name-to-IP resolution.

### Why /etc/hosts Isn't the Right Answer in the Cloud

In the original local Vagrant setup, name resolution was handled via the `/etc/hosts` file on each machine. This technically *can* work in AWS too, but:

```
❌ Not scalable: every instance needs the file updated manually
❌ Not centralized: no single source of truth
❌ Not standard practice for cloud architecture
```

> The proper solution is a **private DNS service** — on AWS, that's **Amazon Route 53**.

---

## 2. What is Amazon Route 53?

> **Amazon Route 53** is a highly available and scalable cloud Domain Name System (DNS) web service — a reliable, cost-effective way to route end users to internet applications by translating names (like `www.example.com`) into IP addresses (like `192.0.2.1`).

- Fully compliant with **IPv6**
- Connects user requests to AWS infrastructure (EC2, ELB, S3) or even **infrastructure outside AWS**
- Supports **DNS health checks** to route traffic only to healthy endpoints

### Route 53 Products

| Product | Purpose |
|---|---|
| **Domain names** | Register a domain (e.g., example.com) |
| **Hosted zones** | Define how Route 53 responds to DNS queries for your domain |
| **Health checks** | Monitor endpoints; route only to healthy ones |
| **Traffic flow** | Visual tool for complex multi-endpoint routing policies |
| **Resolver** | Route DNS queries between VPCs and your network |

### Key Benefits

| Benefit | Description |
|---|---|
| **Highly available** | Built on AWS's distributed, reliable infrastructure |
| **AWS integration** | Maps domains to EC2, S3, CloudFront, ELB, and more |
| **Simple** | Sign up and start answering DNS queries within minutes |
| **Flexible routing** | Routes based on health, geographic location, latency, and more |

## 3. Public vs. Private Hosted Zones

| Type | Use Case |
|---|---|
| **Public Hosted Zone** | Resolves domain names for the public internet (e.g., your actual website domain) |
| **Private Hosted Zone** | Resolves names only **within your VPC** — internal service discovery |

> For this project, we only need **internal name resolution** between EC2 instances within the same VPC — so we use a **Private Hosted Zone**.

## 4. Creating a Private Hosted Zone — Step by Step

```
Route 53 → Hosted Zones → Create Hosted Zone

Domain name: vprofile.in
  (Use any domain name — but it MUST match what's referenced
   in application.properties)

Type: ✅ Private Hosted Zone (not Public)

Region: US East (N. Virginia) — match your EC2 instance region

VPC: Select your default VPC

→ Create Hosted Zone
```

> ⚠️ The domain name you choose here must exactly match the hostnames used in your application configuration (`db01.vprofile.in`, `mc01.vprofile.in`, `rmq01.vprofile.in`).

## 5. Creating DNS Records (A Records)

For each backend instance, create an **A record** mapping its hostname to its **private IP address**.

### A Record vs. CNAME Record

| Record Type | Maps | Example |
|---|---|---|
| **A Record** | Name → IP address | `db01.vprofile.in` → `172.31.20.45` |
| **CNAME Record** | Name → another name | `app.example.com` → `loadbalancer.elb.amazonaws.com` |

> For backend service discovery within a VPC, **A records** are used since we're mapping directly to private IPs.

### Step-by-Step — Creating Each Record

```
For each instance (db01, mc01, rmq01):

1. Go to EC2 → Instances → Select instance
2. Copy the PRIVATE IP address (NOT the public IP)
3. Go back to Route 53 → Hosted Zone → Create Record

Record name: db01   (just the subdomain part)
Record type: A
Value:       <private IP address>

→ Create Record
```

### Records Created for This Project

| Hostname | Resolves To | Used By |
|---|---|---|
| `db01.vprofile.in` | db01 private IP | MySQL connection in application.properties |
| `mc01.vprofile.in` | mc01 private IP | Memcache connection |
| `rmq01.vprofile.in` | rmq01 private IP | RabbitMQ connection |
| `app01.vprofile.in` | app01 private IP | Optional — not required since ALB connects to app01 directly |

> ⚠️ **Always double-check** you're using the **private IP**, not the public IP, when creating these records. Using a public IP would expose internal architecture details and likely fail anyway since these instances aren't meant for direct internet access.

## 7. Route 53 Routing Policies (Public Hosted Zones)

While this project uses a simple private zone with A records, Route 53 supports several **routing policies** for public-facing, production DNS — especially useful for multi-region architectures.

### Simple Routing
```
Default policy — single record, single resource
One name → One IP/endpoint
```

### Weighted Routing
```
Distribute traffic by percentage across multiple resources

Record Set 1: webserver-us-east (weight: 70)
Record Set 2: webserver-us-west (weight: 30)

→ ~70% of traffic goes to us-east, ~30% to us-west
→ Useful for A/B testing or gradual traffic shifting
```

### Latency-Based Routing
```
Routes users to the resource with the LOWEST LATENCY
(typically the nearest geographic region)

Record Set 1: webserver-us-east  (Region: us-east-1)
Record Set 2: webserver-eu-west  (Region: eu-west-1)

→ A user in Europe gets routed to eu-west-1
→ A user in the US gets routed to us-east-1
```

### Failover Routing
```
Acts like a region-based failover mechanism

Primary:   webserver-region-A   (active)
Secondary: webserver-region-B   (standby)

→ If primary fails health checks → traffic automatically
  routes to the secondary region
```

### Geolocation Routing
```
Routes based on the GEOGRAPHIC LOCATION of the user
(not necessarily the lowest latency — based on actual location rules)

Record Set 1: Users from North America → US server
Record Set 2: Users from Europe        → EU server

→ Useful for compliance (data residency laws) or
  localized content delivery
```

### Routing Policy Comparison

| Policy | Best For |
|---|---|
| **Simple** | Single endpoint, no special routing logic needed |
| **Weighted** | A/B testing, gradual rollout, percentage-based load distribution |
| **Latency-based** | Global apps — route users to fastest-responding region |
| **Failover** | Disaster recovery — automatic failover to standby region |
| **Geolocation** | Compliance or content localization based on user location |

## 8. Public Hosted Zone Setup (Reference)

For a production public-facing domain (not used in this lab, but the general pattern):

```
1. Buy a domain from a registrar (GoDaddy, etc.)
2. Route 53 → Create Hosted Zone (Public)
3. Route 53 auto-generates NS (Name Server) and SOA records
4. Copy the NS records → paste into your domain registrar's
   nameserver settings (e.g., GoDaddy DNS management)
5. Launch EC2 instances (possibly in multiple regions)
6. Create record sets in Route 53 pointing to those instances
   using your chosen routing policy
```

> **NS (Name Server) records** tell the internet "Route 53 is authoritative for this domain." **SOA (Start of Authority) records** contain administrative information about the zone.

## 10. Setting Up S3, IAM User, and IAM Role

### Step 1 — Create S3 Bucket

```
S3 → Create Bucket
Name: vprofile-las-artifacts-<unique-number>
  (bucket names must be globally unique)
→ Create Bucket
```

### Step 2 — Create IAM User with Access Keys (for local machine)

```
IAM → Users → Create User
Name: vprofile-S3-admin

Permissions: Attach policies directly
  → Search: S3
  → Select: AmazonS3FullAccess

→ Create User
```

### Generate Access Keys

```
IAM → Users → vprofile-S3-admin → Security Credentials
→ Create Access Key
→ Use case: Command Line Interface (CLI)
→ I understand the recommendation → Next
→ Create Access Key

→ Download CSV file immediately (cannot view secret key again later)
```

> ⚠️ **Critical security warning:** Never commit access keys to a public (or even private) source code repository. Bots constantly scan public repos for leaked AWS credentials — once found, attackers can spin up crypto-mining instances on your account or hold your account for ransom. If you ever expose keys accidentally, **immediately delete or disable them**.

### Step 3 — Create IAM Role (for the EC2 instance)

```
IAM → Roles → Create Role

Trusted entity: AWS Service
Use case:       EC2

Permissions: Search → Amazon S3 Full Access → Select

Role name: S3-admin

→ Create Role
```

### Step 4 — Attach the IAM Role to app01

```
EC2 → Instances → Select app01
→ Actions → Security → Modify IAM Role
→ Select: S3-admin
→ Update IAM Role
```

> **Why a role instead of access keys on the EC2 instance?** IAM roles are the secure, AWS-recommended way for an EC2 instance to access other AWS services — no embedded credentials, no risk of leaking access keys baked into an AMI or script. The instance can run `aws s3` commands using the role's permissions automatically.


### Step 3 — Download the Artifact from S3

```bash
aws s3 cp s3://vprofile-las-artifacts-<your-number>/vprofile-v2.war /tmp/
```

> This works without running `aws configure` on the instance — because the **IAM role** attached to app01 provides the necessary credentials automatically.

### Step 4 — Stop Tomcat and Remove the Default App

```bash
systemctl stop tomcat10
systemctl daemon-reload   # only needed if a unit file changed

# Locate Tomcat's webapps directory (Ubuntu path)
ls /var/lib/tomcat10/webapps
# → shows "ROOT" folder (the default Tomcat welcome page)

# Remove the default application
rm -rf /var/lib/tomcat10/webapps/ROOT
```

### Step 5 — Deploy the New Artifact

```bash
# Copy artifact into webapps, renamed to ROOT.war
cp /tmp/vprofile-v2.war /var/lib/tomcat10/webapps/ROOT.war
```

> Naming it `ROOT.war` makes Tomcat deploy it as the **root context** — so the app is accessible at `http://<host>/` instead of `http://<host>/vprofile-v2/`.

### Step 6 — Start Tomcat

```bash
systemctl start tomcat10

# Verify extraction (may take a minute)
ls /var/lib/tomcat10/webapps
# → ROOT.war and (after extraction) a ROOT/ folder should appear
```

> Tomcat automatically **extracts the .war file** into a folder when the service starts. If the `ROOT/` folder doesn't appear immediately, wait a moment and check again.

## 16. Common Issue — "User Not Found" After Login

```
Symptom: Login succeeds, but the app shows:
  "User Not Found — It seems we couldn't find your account."
```

**Likely causes:**
- The application connected successfully to Tomcat, but **failed to properly query the database** for the user record
- Possible reasons: the `db_backup.sql` data wasn't fully restored, the JDBC URL/hostname doesn't resolve correctly, or the database connection used the wrong schema/credentials

**Troubleshooting checklist:**
```
✅ Confirm db01.vprofile.in resolves to the correct private IP (ping test)
✅ Confirm MySQL on db01 has the "accounts" database with restored tables
✅ Confirm the JDBC URL in application.properties matches the actual Route 53 name
✅ Confirm security group allows port 3306 from the app security group
✅ Check Tomcat logs for connection errors: /var/log/tomcat10/catalina.out
```

| `aws_session_token` | Only needed for temporary security credentials |

```
1. Command line options       (e.g., --region flag)
```
