# AWS Lift and Shift Project — Part 1

---

## 1. Project Overview — What is "Lift and Shift"?

> **Lift and Shift** is a cloud migration strategy where you take an existing application — as-is — and move it from on-premises infrastructure to the cloud, with minimal re-architecting.

This project takes the **vprofile** multi-tier web application (previously set up locally using Vagrant) and migrates it to run in production on **AWS Cloud**.

### The On-Premises Problem

Running application services (databases, Tomcat, DNS, LAMP stack, etc.) in a physical data center requires:

| Resource Need | Description |
|---|---|
| **Virtualization team** | Manages the virtualization platform |
| **Data center operations team** | Handles physical infrastructure and operations |
| **Monitoring team** | 24/7 monitoring of services |
| **Sys admin team** | Day-to-day system administration |
| **Procurement cost** | Upfront capital expense to buy hardware |
| **Maintenance cost** | Ongoing hardware/software upkeep |
| **Manual processes** | Most tasks done by hand — slow and error-prone |
| **Scaling difficulty** | Scaling up/down regularly is complex and slow |

### The Cloud Computing Solution

| Benefit | Description |
|---|---|
| **Pay-as-you-go** | No upfront cost — consume infrastructure like electricity |
| **Elasticity** | Scale out or scale in on demand |
| **Cost control** | Pay only for what you use |
| **Simplified management** | AWS manages underlying infrastructure |
| **Automation** | Every step can be automated — Infrastructure as Code |

### Project Objectives

```
✅ Flexible infrastructure
✅ Pay-as-you-go model (no upfront cost)
✅ Modernize the application using AWS services
✅ Automation — Infrastructure as Code
```

## 2. AWS Services Used in This Project

| Service | Role |
|---|---|
| **EC2 Instances** | VMs for Tomcat, RabbitMQ, Memcache, and MySQL servers |
| **Elastic Load Balancer (ALB)** | Replaces Nginx — routes HTTPS traffic to Tomcat instances |
| **Auto Scaling Group** | Automatically scales Tomcat instances based on load |
| **S3** | Stores software artifacts (built application files) |
| **EFS** | Shared storage (where applicable) |
| **Route 53** | Private DNS service for backend service discovery |
| **IAM** | Access control and permissions |
| **ACM (AWS Certificate Manager)** | SSL/TLS certificate for HTTPS |
| **EBS** | Block storage backing the EC2 instances |

## 4. Architecture Design

```
                         Internet User
                              ↓
                    GoDaddy DNS (Domain)
                    points to ALB endpoint
                              ↓
            ┌───────────────────────────────────┐
            │  Application Load Balancer (ALB)  │
            │  Security Group: HTTPS only (443) │
            │  SSL Certificate: ACM             │
            └─────────────────┬─────────────────┘
                              ↓ Port 8080
            ┌────────────────────────────────────┐
            │     Tomcat Instances (App SG)      │
            │     Managed by Auto Scaling Group  │
            │     vprofile application deployed  │
            └─────────────────┬──────────────────┘
                              ↓ (via Route 53 Private DNS names)
            ┌─────────────────────────────────────┐
            │       Backend Security Group        │
            │  ┌─────────┐ ┌──────────┐ ┌───────┐ │
            │  │  MySQL  │ │ RabbitMQ │ │ Memc  │ │
            │  │  :3306  │ │  :5672   │ │:11211 │ │
            │  └─────────┘ └──────────┘ └───────┘ │
            └─────────────────────────────────────┘
```

### Key Architecture Points

- User accesses the app via a **domain name** (configured in GoDaddy DNS)
- DNS points to the **Application Load Balancer endpoint**
- ALB security group allows **only HTTPS traffic** (port 443) — certificate managed by **ACM**
- ALB routes requests to **Tomcat instances** on port 8080
- Tomcat instances are managed by an **Auto Scaling Group** — scales based on load
- Tomcat instances connect to backend services using **names resolved via Route 53 Private DNS** (not hardcoded IPs)
- Backend instances (MySQL, Memcache, RabbitMQ) sit in their own security group, isolated from the internet

## 5. Execution Flow — Project Roadmap

```
1. Log into AWS account
2. Create key pairs (for SSH access to instances)
3. Create security groups (load balancer, Tomcat, backend)
4. Launch instances with user data scripts (bash automation)
5. Update IP-to-name mapping in Route 53 (private DNS)
6. Build application from source code (on local machine)
7. Upload build artifact to S3 bucket
8. Download artifact from S3 to Tomcat EC2 instance
9. Set up Load Balancer with HTTPS
10. Map Load Balancer to GoDaddy DNS domain
11. Verify the entire setup
12. Build Auto Scaling Group for Tomcat instances
```

## 6. Security Groups — Three-Tier Design

This project uses **three separate security groups**, each scoped to the minimum access needed (least privilege principle).

### Finding Port Numbers from application.properties

Before creating security group rules, the required ports are found in the application source code:

```
src/main/resources/application.properties

db01:3306        → MySQL
Memcache: 11211  → Memcache
RabbitMQ: 5672   → RabbitMQ
```

### Security Group 1 — Load Balancer (vprofile-ELB-SG)

```
Name: vprofile-ELB-SG
Description: Security Group for the vprofile load balancer

Inbound Rules:
  HTTP  | TCP | 80  | 0.0.0.0/0 (any IPv4)
  HTTP  | TCP | 80  | ::/0      (any IPv6)
  HTTPS | TCP | 443 | 0.0.0.0/0 (any IPv4)
  HTTPS | TCP | 443 | ::/0      (any IPv6)

Outbound Rules: Default (do NOT modify — instance needs internet access)
```

> HTTP is allowed initially for testing; once HTTPS with the ACM certificate is configured, HTTP can be removed and only HTTPS retained.

### Security Group 2 — Application / Tomcat (vprofile-app-sg)

```
Name: vprofile-app-sg
Description: Security group for tomcat app server

Inbound Rules:
  Custom TCP | 8080 | Source: vprofile-ELB-SG (load balancer SG)
    Description: Allows traffic from vprofile load balancer
  SSH        | 22   | Source: My IP

Outbound Rules: Default (do NOT modify)
```

> ⚠️ If you're on a home/broadband connection, your public IP may change daily. If SSH stops working, edit the inbound rule and re-select "My IP" to refresh it.

### Security Group 3 — Backend Services (vprofile-backend-SG)

```
Name: vprofile-backend-SG
Description: Security group for mysql, memcache & rabbitmq, allowed from tomcat app server

Inbound Rules:
  MySQL (Custom TCP) | 3306  | Source: vprofile-app-sg
  Custom TCP         | 11211 | Source: vprofile-app-sg  (Memcache)
  Custom TCP         | 5672  | Source: vprofile-app-sg  (RabbitMQ)
  SSH                | 22    | Source: My IP

Outbound Rules: Default (do NOT modify)
```

### Critical Additional Rule — Self-Referencing Security Group

> **Why this is needed:** Services within the backend tier need to talk to each other (e.g., Memcache connecting to MySQL). Security groups are attached per-instance, not shared automatically — each instance only has the rules defined on its security group.

```
Edit vprofile-backend-SG → Add Inbound Rule:
  Type:   All traffic
  Source: vprofile-backend-SG (itself)

→ This allows ALL instances within the backend security group
  to communicate with each other on any port
```

> This rule is safe **as long as the instances themselves are not compromised** — since it only allows traffic between members of the same security group, not from the outside world.

### Security Group Summary Table

| Security Group | Inbound Allows | From |
|---|---|---|
| **vprofile-ELB-SG** | 80, 443 | Anywhere (0.0.0.0/0) |
| **vprofile-app-sg** | 8080 | vprofile-ELB-SG |
| **vprofile-app-sg** | 22 | My IP |
| **vprofile-backend-SG** | 3306, 11211, 5672 | vprofile-app-sg |
| **vprofile-backend-SG** | All traffic | vprofile-backend-SG (itself) |
| **vprofile-backend-SG** | 22 | My IP |

> ⚠️ A simpler (but less secure) alternative is to allow "all traffic from the app security group" instead of three individual port rules. This is easier to set up but violates least-privilege security practices — only open the exact ports needed.

## 9. Launching the Backend EC2 Instances

All four instances are launched the same general way — differing only in **name, security group, AMI, and user data script**.

### Common Launch Settings

| Setting | Value |
|---|---|
| AMI | Amazon Linux 2023 (Tomcat uses Ubuntu 24 — see below) |
| Instance type | t2.micro / t3.micro (free tier) |
| Key pair | vprofile-prod-key |
| Tags | Name + Project=vprofile (apply to instance AND volumes) |

> ⚠️ **Always tag your EBS volumes too** — not just instances. Untagged volumes are easy to forget and can pile up, wasting cost or risking accidental deletion of the wrong resource.

### Instance 1 — MySQL (vprofile-db01)

```
Name: vprofile-db01
Tags: Project=vprofile
AMI:  Amazon Linux 2023
Type: t2.micro
Key:  vprofile-prod-key
Security Group: vprofile-backend-SG
User Data: mysql.sh (paste full script, including the #!/bin/bash line)
```

> ⚠️ The **first line `#!/bin/bash` is required** — without it, the user data script will not execute. Another common cause of failure: accidentally modifying the security group's **outbound rules**, which blocks internet access needed to download packages.

### Instance 2 — Memcache (vprofile-mc01)

```
Name: vprofile-mc01
Security Group: vprofile-backend-SG
User Data: memcache.sh
```

### Instance 3 — RabbitMQ (vprofile-rmq01)

```
Name: vprofile-rmq01
Security Group: vprofile-backend-SG
User Data: rabbitmq.sh
```

### Instance 4 — Tomcat (vprofile-app01)

```
Name: vprofile-app01
AMI:  Ubuntu 24.04 LTS (HVM, SSD volume type) — NOT Amazon Linux
Security Group: vprofile-app-sg  ← different from the backend instances!
User Data: tomcat_ubuntu.sh
```

> **Why Ubuntu for Tomcat?** Ubuntu's repositories include Tomcat 10 directly (`apt install tomcat10`), making setup far simpler than CentOS/Amazon Linux, which requires manually downloading the Tomcat binary, creating a systemd service file, and configuring a Tomcat user. Ubuntu 24 specifically has Tomcat 10 in its repos; older Ubuntu versions only have Tomcat 9.

## 10. User Data Scripts — Analysis

### mysql.sh (Amazon Linux 2023)

```bash
#!/bin/bash
DATABASE_PASS='admin123'
sudo dnf update -y
sudo dnf install git zip unzip -y
sudo dnf install mariadb105-server -y
sudo systemctl start mariadb
sudo systemctl enable mariadb
cd /tmp/
git clone -b main https://github.com/hkhcoder/vprofile-project.git

# Equivalent of mysql_secure_installation, automated:
sudo mysqladmin -u root password "$DATABASE_PASS"
sudo mysql -u root -p"$DATABASE_PASS" -e "ALTER USER 'root'@'localhost' IDENTIFIED BY '$DATABASE_PASS'"
sudo mysql -u root -p"$DATABASE_PASS" -e "DELETE FROM mysql.user WHERE User='root' AND Host NOT IN ('localhost', '127.0.0.1', '::1')"
sudo mysql -u root -p"$DATABASE_PASS" -e "DELETE FROM mysql.user WHERE User=''"
sudo mysql -u root -p"$DATABASE_PASS" -e "DELETE FROM mysql.db WHERE Db='test' OR Db='test\_%'"
sudo mysql -u root -p"$DATABASE_PASS" -e "FLUSH PRIVILEGES"

# Create application database and user
sudo mysql -u root -p"$DATABASE_PASS" -e "create database accounts"
sudo mysql -u root -p"$DATABASE_PASS" -e "grant all privileges on accounts.* TO 'admin'@'localhost' identified by 'admin123'"
sudo mysql -u root -p"$DATABASE_PASS" -e "grant all privileges on accounts.* TO 'admin'@'%' identified by 'admin123'"

# Restore the schema/data dump
sudo mysql -u root -p"$DATABASE_PASS" accounts < /tmp/vprofile-project/src/main/resources/db_backup.sql
sudo mysql -u root -p"$DATABASE_PASS" -e "FLUSH PRIVILEGES"
```

| Step | Purpose |
|---|---|
| `dnf install mariadb105-server` | MariaDB package name on Amazon Linux 2023 |
| Manual SQL commands replacing `mysql_secure_installation` | Removes test users/DB, sets root password — fully automated, no interactive prompts |
| `grant ... TO 'admin'@'%'` | Allows the `admin` user to connect from **any host** — needed since Tomcat connects remotely |
| `db_backup.sql` | Restores the application's pre-built schema and seed data |

> Note: `'admin'@'%'` (any host) is broader than the local-only equivalent used in the Vagrant version (`'admin'@'app01'`) — reflects that the app server's IP isn't predictable in this AWS setup without DNS.

### memcache.sh (Amazon Linux 2023)

```bash
#!/bin/bash
sudo dnf install memcached -y
sudo systemctl start memcached
sudo systemctl enable memcached
sudo systemctl status memcached
sed -i 's/127.0.0.1/0.0.0.0/g' /etc/sysconfig/memcached
sudo systemctl restart memcached
sudo memcached -p 11211 -U 11111 -u memcached -d
```

| Step | Purpose |
|---|---|
| `sed -i 's/127.0.0.1/0.0.0.0/g'` | Changes Memcache from localhost-only to listening on **all interfaces** — required for Tomcat (a different instance) to connect |
| `memcached -p 11211 -U 11111 -u memcached -d` | Explicitly starts Memcache on TCP port 11211 and UDP port 11111, running as a daemon |

### rabbitmq.sh (Amazon Linux 2023)

```bash
#!/bin/bash
## Import signing keys
rpm --import 'https://github.com/rabbitmq/signing-keys/releases/download/3.0/rabbitmq-release-signing-key.asc'
rpm --import 'https://github.com/rabbitmq/signing-keys/releases/download/3.0/cloudsmith.rabbitmq-erlang.E495BB49CC4BBE5B.key'
rpm --import 'https://github.com/rabbitmq/signing-keys/releases/download/3.0/cloudsmith.rabbitmq-server.9F4587F226208342.key'

# Download repository definition file (hosted in the project's own GitHub repo)
curl -o /etc/yum.repos.d/rabbitmq.repo https://raw.githubusercontent.com/hkhcoder/vprofile-project/refs/heads/awsliftandshift/al2023rmq.repo

dnf update -y
dnf install socat logrotate -y
dnf install -y erlang rabbitmq-server

systemctl enable rabbitmq-server
systemctl start rabbitmq-server

sudo sh -c 'echo "[{rabbit, [{loopback_users, []}]}]." > /etc/rabbitmq/rabbitmq.config'
sudo rabbitmqctl add_user test test
sudo rabbitmqctl set_user_tags test administrator
rabbitmqctl set_permissions -p / test ".*" ".*" ".*"

sudo systemctl restart rabbitmq-server
```

| Step | Purpose |
|---|---|
| Three `rpm --import` commands | Trust the RabbitMQ and Erlang package signing keys |
| `curl -o /etc/yum.repos.d/rabbitmq.repo ...` | Downloads a pre-made repo definition file from the project's GitHub — simpler than embedding the repo config inline with `cat` heredocs in the script |
| `loopback_users: []` | Disables the default restriction that only allows the `guest` user to connect from localhost — necessary for remote app connections |
| `set_permissions -p / test ".*" ".*" ".*"` | Grants the `test` user full configure/write/read permissions on the default vhost `/` |

> **Why Amazon Linux 2023 needs a different script than CentOS:** Even though both are RPM-based, AL2023's repositories don't carry the same RabbitMQ packages as CentOS 7 did. The official RabbitMQ documentation provided the updated commands and signing key URLs used here.

### tomcat_ubuntu.sh (Ubuntu 24.04)

```bash
#!/bin/bash
sudo apt update
sudo apt upgrade -y
sudo apt install openjdk-17-jdk -y
sudo apt install tomcat10 tomcat10-admin tomcat10-docs tomcat10-common git -y
```

| Step | Purpose |
|---|---|
| `openjdk-17-jdk` | Java runtime required by Tomcat |
| `tomcat10` | Installs Tomcat 10 directly from Ubuntu's repository — no manual binary download needed |
| `tomcat10-admin`, `tomcat10-docs`, `tomcat10-common` | Supporting Tomcat packages (admin console, docs, shared libs) |

> Compare this to a CentOS-based manual Tomcat setup, which typically requires downloading the Tomcat tarball, extracting it, creating a dedicated `tomcat` user, and writing a custom `systemd` service file. Ubuntu's package availability eliminates all of that.

### nginx.sh (Reference — Original Local Setup, Not Used in AWS)

```bash
apt update
apt install nginx -y
cat <<EOT > vproapp
upstream vproapp {
 server app01:8080;
}
server {
  listen 80;
  location / {
    proxy_pass http://vproapp;
  }
}
EOT
mv vproapp /etc/nginx/sites-available/vproapp
```

## 12. Troubleshooting Philosophy for User-Data-Provisioned Instances

> Since everything is automated via user data scripts (no manual steps), troubleshooting a broken instance is rarely worth the time.

```
If a service isn't running after launch:
  1. Don't troubleshoot manually
  2. Simply DELETE the instance
  3. Launch a NEW instance
  4. Double-check:
     ✅ Correct security group selected
     ✅ Correct user data script pasted (including #!/bin/bash)
     ✅ Outbound security group rules NOT modified
     ✅ Correct AMI selected
  5. Re-verify the service after relaunch
```

> Common causes of failure: missing the shebang line, modified outbound rules blocking internet access (so packages can't download), wrong security group, or pasting the wrong script into the wrong instance.

## 13. Essential Linux Server Administration — tmux

> **tmux** (terminal multiplexer) keeps your terminal session alive on the **server** even if your local SSH connection drops.

### Why tmux Matters

```
Without tmux:
  SSH connection drops → running command (e.g., a long DB import) is KILLED

With tmux:
  SSH connection drops → command keeps running on the SERVER
  → reconnect SSH → reattach to tmux → exactly where you left off
```

### Installing and Using tmux

```bash
# Step 1: SSH into the instance
ssh -i vprofile-prod-key.pem ec2-user@<public-ip>

# Step 2: Install tmux (Amazon Linux 2023)
sudo dnf install tmux -y

# Step 3: Start a tmux session
tmux
# A status bar appears at the bottom — you're now inside tmux

# Step 4: Run your long-running command inside tmux
mariadb -u admin -p accounts
```

### If SSH Disconnects

```bash
# Reconnect via SSH
ssh -i vprofile-prod-key.pem ec2-user@<public-ip>

# Reattach to the existing tmux session
tmux attach
# → You're back exactly where you left off, even at the MariaDB prompt
```

### Useful tmux Commands

| Command | Action |
|---|---|
| `tmux` | Start a new session |
| `tmux ls` | List all active sessions |
| `tmux attach` | Reattach to the most recent session |
| `Ctrl+b` then `d` | Detach from tmux (session keeps running) |

### Typical Workflow

```bash
ssh -i key.pem ec2-user@server
tmux
mariadb -u admin -p accounts
# ... even if SSH breaks here, the mariadb session keeps running on the server
```

> tmux is considered **essential for server administration** — especially for long-running database imports, deployments, or any task you can't afford to lose if your connection drops.

## 14. Essential Linux Command — sudo -i

### What It Does

```
sudo   → run a command with elevated (root) privileges
-i     → start a login shell AS the target user (root by default)

sudo -i  ≈  su -
```

### Before and After

```bash
# Before
[ec2-user@ip-172-31-18-139 ~]$

sudo -i

# After
[root@ip-172-31-18-139 ~]#
```

**What changes:**
- Username switches from `ec2-user` to `root`
- Prompt symbol changes from `$` to `#`
- Home directory becomes `/root`
- Root's environment variables and startup files load

### sudo -i vs. a Single sudo Command

```bash
# Single command — only THIS command runs as root
sudo dnf install tmux -y
# → returns to ec2-user prompt immediately after

# sudo -i — STAYS as root for multiple commands
sudo -i
dnf install tmux -y
systemctl status mariadb
cat /etc/shadow
exit   # ← returns to ec2-user
```

### sudo -i vs. sudo su

| Command | What It Does |
|---|---|
| `sudo -i` | Asks sudo to start a clean root login shell directly |
| `sudo su` | Uses sudo to run `su`, which then switches to root — may preserve some original user environment variables depending on system config |
| `sudo su -` | The trailing `-` makes `su` create a proper login shell — approximately equivalent to `sudo -i` |

> **Recommended modern practice:** Use `sudo -i` on Amazon Linux, Ubuntu, Rocky Linux, and RHEL. It's simpler, doesn't depend on `su`, and clearly expresses intent: "give me a root login shell."

### Exiting Root

```bash
exit
# or Ctrl+D

[root@ip-172-31-18-139 ~]# exit
logout
[ec2-user@ip-172-31-18-139 ~]$
```

### When to Use sudo -i

```
✅ Use sudo -i when doing multiple admin tasks in a row:
   sudo -i
   dnf update
   systemctl restart mariadb
   journalctl -u mariadb

✅ Use a single "sudo <command>" for one-off tasks:
   sudo dnf install tmux -y
```
