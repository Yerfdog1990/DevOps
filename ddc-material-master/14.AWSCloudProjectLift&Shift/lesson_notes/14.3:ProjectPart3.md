## 2. AWS Certificate Manager (ACM)

> **AWS Certificate Manager (ACM)** provisions, manages, deploys, and renews SSL/TLS certificates for use with AWS services — at no extra charge for public certificates used with integrated services like ALB and CloudFront.

### Why You Need a Certificate

- Without a certificate, users access your app over **HTTP (unencrypted)**
- With a certificate, users connect over **HTTPS (encrypted)**
- Browsers show a padlock icon for HTTPS connections — users see "Connection is secure"
- ACM automates certificate renewal so you never worry about expiry

### ACM Certificate Types

| Type | Description | Cost |
|---|---|---|
| **Public certificate** | Issued by Amazon, trusted by all browsers — for public-facing websites | Free |
| **Private certificate** | For internal resources (servers, IoT devices, microservices) | Monthly fee via Private CA |
| **Imported certificate** | Bring your own certificate from another CA | Free to store |

### How ACM Works

```
Step 1: Request a certificate for your domain (e.g., *.yerfdog.xyz)
Step 2: Validate domain ownership
         → DNS validation (recommended): add a CNAME record to your DNS
         → Email validation: click link sent to domain registrant email
Step 3: Certificate issued by Amazon ✅
Step 4: Attach to your ALB/CloudFront — AWS deploys and manages it
Step 5: Auto-renewal handled by AWS — no manual intervention
```

### Public Key vs. Private Key — What's Safe to Share

When a visitor connects to your HTTPS website, their browser sees the **public certificate**. This is intentional and not a security risk.

| Item | Public or Private? | Safe to Share? |
|---|---|---|
| **Certificate** (CN, issuer, expiry, serial number) | Public | ✅ Yes — shown to every visitor |
| **Public key** (inside the certificate) | Public | ✅ Yes — required for encryption |
| **SHA-256 fingerprints** | Public | ✅ Yes — used to verify certificate identity |
| **Private key** (`privkey.pem`, `server.key`) | Private | ❌ Never — exposes your identity |

### Certificate Hierarchy Explained

```
Amazon Root CA 1  (built into all browsers/OSes — trusted by design)
     ↓
Amazon RSA 2048 M01  (intermediate CA — issued by root CA)
     ↓
*.yerfdog.xyz  (your wildcard certificate — covers all subdomains)
```

When a browser visits `https://vprofileapp.yerfdog.xyz`:
1. Server sends the certificate chain
2. Browser verifies chain back to the trusted root CA
3. Browser uses the **public key** to establish encrypted session
4. User sees the padlock 🔒

### Wildcard Certificate

A certificate for `*.yerfdog.xyz` covers:
- `yerfdog.xyz`
- `www.yerfdog.xyz`
- `vprofileapp.yerfdog.xyz`
- `app.yerfdog.xyz`
- Any other subdomain of `yerfdog.xyz`

### ACM with AWS ALB — Security Model

```
User's browser ←→ ALB (holds the certificate + private key)
                        ↓
                  App Servers (Tomcat)
                  (private key never leaves AWS)
```

> When using ACM with ALB: **AWS holds and protects the private key** — you cannot download it. This is why ACM is considered secure. Browsers only ever receive the public certificate. The critical thing to never expose is files like `privkey.pem`, `server.key`, or `-----BEGIN PRIVATE KEY-----` blocks.

### Requesting an ACM Public Certificate

```
ACM → Request a certificate → Request a public certificate

Domain names:
  *.yerfdog.xyz  (wildcard — covers all subdomains)
  yerfdog.xyz    (apex domain — optional but good practice)

Validation method:
  ✅ DNS validation (recommended)
  → AWS provides a CNAME record to add to your DNS (GoDaddy/Route 53)
  → Once the CNAME is added, certificate issues automatically

→ Request
```

## 3. Creating the Target Group

Before creating the load balancer, create the target group that the ALB will route traffic to.

```
EC2 → Load Balancing → Target Groups → Create Target Group

Target type: Instances

Settings:
  Target group name: vprofile-las-tg
  Protocol:          HTTP
  Port:              8080  ← IMPORTANT: Tomcat runs on 8080, not 80

VPC: Default VPC
```

### Health Check Configuration

```
Health check protocol: HTTP
Health check path:     /login  (or / — any valid page)

Advanced health check settings:
  Port:              Override → 8080  ← must match Tomcat's port
  Healthy threshold:   2
  Unhealthy threshold: 2
  Timeout:            5
  Interval:           30
  Success codes:      200
```

> ⚠️ **Two places to set port 8080:** Once in the target group's main protocol/port setting, and once in the health check override. If either is left at 80, the health check will fail — instances will show as unhealthy even though Tomcat is running.

### Register the Target Instance

```
→ Click Next
→ Find and select: vprofile-app01

Make sure port shows 8080:
  Instance: vprofile-app01 | Port: 8080

→ Click "Include as pending below"
→ Verify app01 appears at port 8080 in the review section

→ Create Target Group
```

```

```

### Basic Configuration


### Network Mapping

```

Availability Zones: Select ALL available zones
  us-east-1a | subnet-0bc54d69845c02122
  us-east-1b | subnet-0d6c685cbce271805
  us-east-1c | subnet-02c885186c8ae7601
  us-east-1d | subnet-0c2965165a0dc8917
  us-east-1e | subnet-0a6ab64ce55a14c35
  us-east-1f | subnet-0bf079dbdcedd1e19
```

> Selecting all AZs ensures the load balancer can route to instances in any zone and remains available even if one AZ has issues.

### Security Groups

```
Remove: default security group
Add:    vprofile-ELB-SG  (allows HTTP:80 and HTTPS:443 from anywhere)
```

### Listeners and Routing

```
Listener 1: HTTP:80  → Forward to vprofile-las-tg
Listener 2: HTTPS:443 → Forward to vprofile-las-tg
```

**For the HTTPS:443 listener, configure the certificate:**

```
Default SSL/TLS server certificate:
  Source:      From ACM
  Certificate: *.yerfdog.xyz  (your ACM certificate)

Security policy: ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09 (Recommended)
```

> If you don't have a domain and ACM certificate, you can skip the HTTPS listener and only use HTTP:80. You'll still be able to test the application — just without encryption.

## 9. Auto Scaling Group for Tomcat

With the load balancer verified and working, the final step is to place the Tomcat instance into an **Auto Scaling Group** — so the application automatically handles load changes and self-heals from instance failures.

### Step 1 — Create an AMI from app01

Before creating an Auto Scaling Group, you need an AMI (Amazon Machine Image) that captures app01's current state — with Tomcat, the WAR deployed, and all configurations in place.

```
EC2 → Instances → Select vprofile-app01
→ Actions → Image and Templates → Create Image

Image name:        vprofile-app01-AMI
Description:       App01 with vprofile WAR deployed
Reboot instance:   ✅ Enabled (ensures filesystem consistency)

→ Create Image → Wait for status: available ✅
```

### Step 2 — Create a Launch Template

```
EC2 → Launch Templates → Create Launch Template

Name:           vprofile-app-lt
AMI:            vprofile-app01-AMI (the one you just created)
Instance type:  t2.micro
Key pair:       vprofile-prod-key
Security group: vprofile-app-sg

→ Create Launch Template
```

### Step 3 — Create Auto Scaling Group

```
EC2 → Auto Scaling Groups → Create Auto Scaling Group

Name:            vprofile-app-ASG
Launch template: vprofile-app-lt

Step 2 — Network:
  VPC: Default VPC
  AZs: Select all available zones

Step 3 — Load Balancing:
  ✅ Attach to an existing load balancer
  → Choose from existing load balancer target groups
  → Select: vprofile-las-tg

Health checks:
  ✅ EC2 health checks (always on)
  ✅ ELB health checks (recommended — detects if Tomcat crashes)

Step 4 — Group Size and Scaling:
  Desired capacity: 1
  Min:              1
  Max:              4

  Scaling policy:
    ✅ Target tracking scaling
    Metric: Average CPU Utilization
    Target: 50%

Step 6 — Tags:
  Name: vprofile-app  ← Auto-applied to instances launched by ASG

→ Create Auto Scaling Group
```

> Once the ASG is created, it immediately launches one instance from the AMI. The original `app01` can now be **terminated** — the ASG's instance takes over and is managed automatically.

### Step 4 — Terminate the Original app01

```
EC2 → Instances → Select vprofile-app01 (original, manually created)
→ Instance State → Terminate

The ASG's instance replaces it and serves traffic through the ALB target group.
```

> ⚠️ **You cannot directly terminate an ASG-managed instance to "delete" it** — if you terminate an ASG instance, the ASG immediately launches a replacement to maintain desired capacity. To remove instances, you must reduce the desired/min capacity to 0, or delete the ASG itself.

## 10. Session Stickiness

If you configure the ASG with multiple instances and users experience login issues (like the login page refreshing without logging in), **enable stickiness** on the target group.

```
Target Groups → vprofile-las-tg → Attributes → Edit

Stickiness:
  ✅ Enable load balancer generated cookie stickiness
  Duration: 1 day (or as needed)

→ Save Changes
```

**Why stickiness matters for this app:**

```
Without stickiness:
  Request 1 → Instance A (user logs in, session stored on A)
  Request 2 → Instance B (no session → login fails!)

With stickiness:
  All requests from the same user → always routed to Instance A
  → Session is preserved ✅
```

> Stickiness is only needed if the application stores session data **locally on the instance** (stateful). For truly stateless applications (sessions stored in a shared DB or Redis), stickiness is not needed.

## 12. Project Cleanup (Complete)

Clean up in this specific order to avoid orphan resources and extra charges:

### Step 1 — Delete Auto Scaling Group

```
EC2 → Auto Scaling Groups → Select vprofile-app-ASG
→ Delete → Confirm

This automatically terminates all ASG-managed instances.
(Do NOT manually terminate the ASG instances first — the ASG will recreate them)
```

### Step 2 — Terminate Remaining EC2 Instances

```
EC2 → Instances → Remove the filter for "running" instances
→ Select all remaining instances:
    vprofile-db01
    vprofile-mc01
    vprofile-rmq01
→ Instance State → Terminate → Confirm
```

### Step 3 — Delete Load Balancer

```
EC2 → Load Balancers → Select vprofile-ALB
→ Actions → Delete Load Balancer → Confirm
```

### Step 4 — Delete Target Group (Optional)

```
EC2 → Target Groups → Select vprofile-las-tg
→ Actions → Delete → Confirm
(No charges for target groups, but delete for clean environment)
```

### Step 5 — Check and Delete EBS Volumes

```
EC2 → Elastic Block Store → Volumes
→ After instances are terminated, any volumes in "Available" state
  are detached and costing money
→ Select → Actions → Delete Volume
```

### Step 6 — Clean Up Route 53

```
Route 53 → Hosted Zones → vprofile.in
→ Select ALL custom records (db01, mc01, rmq01, app01)
  ⚠️ Do NOT delete the NS and SOA records (required to delete the zone)
→ Delete Records → Confirm

Then delete the hosted zone itself:
Route 53 → Hosted Zones → Select vprofile.in → Delete Hosted Zone
```

### Step 7 — Deregister AMI and Delete Snapshots

```
EC2 → Images → AMIs → (filter: Owned by me)
→ Select vprofile-app01-AMI
→ Actions → Deregister AMI → Deregister

Then:
EC2 → Elastic Block Store → Snapshots
→ Select the snapshot associated with the AMI
→ Actions → Delete Snapshot → Delete
```

> **Why this order?** You must deregister the AMI before you can delete the snapshot — the snapshot cannot be deleted while the AMI references it.

### Step 8 — Delete S3 Bucket

```
S3 → Select vprofile-las-artifacts bucket
→ Empty (type "permanently delete" → Empty)
  (Bucket still exists but is now empty)
→ Delete Bucket (type the bucket name → Delete)
```

### Step 9 — Clean Up Security Groups and Key Pairs (Optional)

```
EC2 → Security Groups → Delete:
  vprofile-ELB-SG
  vprofile-app-sg
  vprofile-backend-SG

EC2 → Key Pairs → Delete:
  vprofile-prod-key

IAM → Users → vprofile-S3-admin → Delete
IAM → Roles → S3-Admin → Delete
```

### Step 10 — Final Verification

```
EC2 Dashboard → Refresh

Verify:
  ✅ 0 Running instances
  ✅ 0 Load balancers
  ✅ 0 Volumes
  ✅ 0 Snapshots
  ✅ 0 Elastic IPs
  ✅ 0 Auto Scaling Groups
  ✅ S3 bucket deleted
  ✅ Route 53 hosted zone deleted
```

### Cleanup Order Summary

```
1. Delete Auto Scaling Group          (terminates ASG instances)
2. Terminate remaining EC2 instances  (db01, mc01, rmq01)
3. Delete Load Balancer
4. Delete Target Group (optional)
5. Delete unused EBS Volumes
6. Remove Route 53 records → Delete Hosted Zone
7. Deregister AMI → Delete Snapshot
8. Empty S3 Bucket → Delete Bucket
9. Delete Security Groups, Key Pairs, IAM User, IAM Role (optional)
10. Verify EC2 Dashboard is clean
```
