# Git Tags & Semantic Versioning

## 1. What is a Git Tag?

A **Git tag** is a named pointer to a specific commit — like placing a sticky note on a commit saying "this is important." Unlike branches, tags don't move as new commits are added. They stay anchored to the exact commit they were created on.

Tags are most commonly used to:
- Mark **release versions** (v1.0.0, v2.3.1)
- Mark **milestones** or stable checkpoints
- Trigger **CI/CD pipelines** (e.g. build a Docker image when a new tag is pushed)
- Enable **rollbacks** to a specific known-good version

---

## 2. Semantic Versioning — The Standard Format

Almost every modern software product uses **semantic versioning**. Look at any app:

| Software | Version |
|---|---|
| Brave Browser | `1.71.114` |
| Git | `3.7.6` |
| VS Code | `1.91.1` |

All follow the same format: **`MAJOR.MINOR.PATCH`**

### What Each Number Means

```
v  2  .  1  .  6
   ^     ^     ^
   │     │     └── PATCH — Bug fix or small improvement
   │     └──────── MINOR — New feature added (backward compatible)
   └────────────── MAJOR — Breaking change (backward incompatible)
```

| Version Part | When to Increment | Example |
|---|---|---|
| **PATCH** | Bug fix, small improvement | `v1.0.0` → `v1.0.1` |
| **MINOR** | New feature, backward compatible | `v1.0.1` → `v1.1.0` |
| **MAJOR** | Breaking change, not backward compatible | `v1.1.0` → `v2.0.0` |

**Example:** A project upgrades from JDK 11 to JDK 17, breaking compatibility with JDK 11 — that's a MAJOR version bump.

### Common Version Labels

| Tag | Meaning |
|---|---|
| `v1.0.0-alpha` | Internal testing |
| `v1.0.0-beta` | Public beta / testing release |
| `v1.0.0` | Final production release |

## 3. Two Types of Git Tags

### Lightweight Tag
A simple pointer to a commit. No extra metadata — just a name attached to a commit hash. Used for local references and quick debugging.

```bash
git tag v1.0.0               # Tag current commit
git tag v1.0.0 abc1234       # Tag a specific commit
```

### Annotated Tag (Recommended for Releases)
Stored as a full Git object. Includes:
- Tagger's name and email
- Date and time
- Tag message

Annotated tags are the standard for official releases and CI/CD integration.

```bash
git tag -a v1.0.0 -m "Initial release"
git tag -a v1.0.0 abc1234 -m "Tagging older commit"
```

| Feature | Lightweight | Annotated |
|---|---|---|
| Stores metadata | ❌ No | ✅ Yes (author, date, message) |
| Stored as Git object | ❌ No | ✅ Yes |
| Best for | Quick local references | Official releases, CI/CD |
| Command | `git tag <name>` | `git tag -a <name> -m "msg"` |

## 4. Creating Tags

### Tag the Current Commit (HEAD)
```bash
git tag v1.0.0                          # Lightweight
git tag -a v1.0.0 -m "Release v1.0.0"  # Annotated
```

### Tag a Specific Older Commit
First find the commit hash:
```bash
git log --oneline
# abc1234 Fix login bug
# def5678 Add payment feature
# 7g8h9i0 Initial commit
```

Then tag it:
```bash
git tag -a v1.0.0 abc1234 -m "Tagging v1.0.0 release"
```

### Real-World Example — Tagging a Bug Fix
```bash
git log --oneline
# Last tag was v3.5.2

git tag -a v3.5.3 -m "Bug fix: corrected JDK version reference"
```

PATCH version incremented from `3.5.2` → `3.5.3` because it's a bug fix.

## 5. Viewing Tags

### List All Tags
```bash
git tag
# v1.0.0
# v2.0.0
# v3.5.2
# v3.5.3
```

### Filter Tags by Pattern
```bash
git tag -l 'v1.*'        # Show only tags starting with v1.
```

### View Details of a Specific Tag
```bash
git show v2.0.0
# Shows: tag name, tagger, date, message, and the commit diff
# Press q to quit
```

## 6. Pushing Tags to Remote (GitHub)

Tags are **not automatically pushed** when you run `git push`. You must push them explicitly.

### Push a Single Tag
```bash
git push origin v3.5.3
```

### Push All Tags at Once
```bash
git push --tags
```

### Push Commits AND Tags Together
```bash
git push --follow-tags        # Push commits + all annotated tags reachable from branch
```

> In VS Code: Command Palette (`Ctrl+Shift+P`) → search **Git Push** → select **Push and Follow Tags**

After pushing, tags appear in your GitHub repository under the **Tags** tab.

---

## 7. Viewing Tags on GitHub

1. Go to your repository on GitHub
2. Click **Tags** (next to branches dropdown)
3. See all tags with their commit messages and dates

### Marking a Tag as a Release on GitHub

1. Go to **Releases** in your repository
2. Click **Create a new release**
3. Choose your **branch** from the dropdown
4. Select an existing **tag** from the dropdown
5. Give it a **title** (e.g. "UI Bug Fix - v3.5.3")
6. Add a description of what changed
7. Click **Publish release**

Releases make your tags more visible and allow users to download source code snapshots.

## 8. Checking Out a Tag

You can view your repository at the exact state of any tag:

```bash
git checkout v1.0.0
```

This puts you in **detached HEAD state** — you're not on any branch, just viewing a historical snapshot.

```
HEAD detached at v1.0.0
```

You can look around, run code, inspect files — but any commits you make here won't belong to a branch.

### Exit Detached HEAD State
```bash
git switch main              # Return to main branch
```

### Create a Branch from a Tag (to make changes)
```bash
git checkout -b hotfix-v1.0.0 v1.0.0
# Now you're on branch hotfix-v1.0.0 starting from tag v1.0.0
```

---

## 9. Deleting Tags

### Delete a Local Tag
```bash
git tag -d v1.0.0
```

### Delete a Remote Tag
```bash
git push origin --delete v1.0.0
```

### Force-Update a Tag (Move it to a Different Commit)
```bash
git tag -f -a v1.0.0 abc1234 -m "Corrected tag"
git push origin -f v1.0.0     # Force-push to update remote
```

> ⚠️ Force-pushing tags rewrites remote history. Only do this on personal branches or after coordinating with your team.

## 10. Troubleshooting Tags

### Detached HEAD State After `git checkout <tag>`
```bash
git checkout v1.0.0
# Now in detached HEAD

# Fix: create a branch from here
git checkout -b hotfix-v1.0.0
# Now you're safely on a branch
```

### Tag Conflict — Local and Remote Have Different Commits for Same Tag
```bash
# Option 1: Delete and recreate
git tag -d v1.0.0
git push origin --delete v1.0.0
git tag -a v1.0.0 -m "Corrected tag"
git push origin v1.0.0

# Option 2: Force-push (use only if you're confident)
git push origin -f v1.0.0
```

## 11. Semantic Versioning in Practice

### Typical Release Workflow
```bash
# Developer makes a commit
git add .
git commit -m "Fix navbar rendering bug"

# Tag the commit with semantic version
git tag -a v3.5.3 -m "Patch: fix navbar rendering bug"

# Push both commit and tag
git push origin main
git push origin v3.5.3
# OR:
git push --follow-tags
```

### Incrementing Version Numbers

```
Current: v3.5.2

Bug fix only:         v3.5.3   (PATCH: 2 → 3)
New feature added:    v3.6.0   (MINOR: 5 → 6, reset PATCH to 0)
Breaking change:      v4.0.0   (MAJOR: 3 → 4, reset MINOR and PATCH to 0)
```

**Rule:** When you increment MAJOR, reset MINOR and PATCH to 0. When you increment MINOR, reset PATCH to 0.

## 12. Git Tags in CI/CD Pipelines

Tags are commonly used to **trigger automated builds and deployments**:

- Push a tag → Jenkins/GitHub Actions detects the new tag → builds the application → deploys it
- Docker images are often tagged with the Git tag: `myapp:v3.5.3`
- Makes every deployed version fully traceable back to a specific commit

```yaml
# Example: GitHub Actions trigger on tag push
on:
  push:
    tags:
      - 'v*'         # Trigger when any tag starting with v is pushed
```

This is why tagging in the right semantic version format matters — CI/CD pipelines read these tags to determine what and how to deploy.

## 13. Best Practices

| Practice | Why |
|---|---|
| Always prefix with `v` | Convention: `v1.0.0` not `1.0.0` |
| Use annotated tags for releases | Stores metadata, integrates better with tools |
| Follow MAJOR.MINOR.PATCH strictly | Communicates scope of change clearly |
| Don't tag every commit | Only tag meaningful milestones or releases |
| Push tags explicitly | They don't push automatically with `git push` |
| Use release labels for pre-releases | `v1.0.0-alpha`, `v1.0.0-beta` for clarity |
| Document your tag in the message | Makes release history readable |

| `git push origin --delete v1.0.0` | Delete a remote tag |
| `git tag -f -a v1.0.0 -m "msg"` | Force-update a tag to current commit |

---

## 15. Key Takeaways

- A Git tag is a **permanent, named pointer** to a specific commit — it doesn't move as new commits are added.
- **Semantic versioning** format is `MAJOR.MINOR.PATCH` — patch = bug fix, minor = new feature, major = breaking change.
- When incrementing MAJOR, reset MINOR and PATCH to 0. When incrementing MINOR, reset PATCH to 0.
- Use **annotated tags** (`-a`) for releases — they store metadata and work better with CI/CD tools.
- Tags are **not pushed automatically** — you must explicitly `git push origin <tag>` or `git push --tags`.
- `git checkout <tag>` puts you in **detached HEAD state** — view-only. Create a branch (`-b`) to make changes.
- Tags are commonly used to **trigger CI/CD pipelines** — a new version tag tells the pipeline to build and deploy.
- Only tag **meaningful milestones** — tagging every commit defeats the purpose and clutters the repository.
- Always prefix tags with `v` (e.g. `v1.0.0`) — it's the universal convention and expected by most tools.
- Tags make deployments **fully traceable** — every version in production can be mapped back to an exact commit.
