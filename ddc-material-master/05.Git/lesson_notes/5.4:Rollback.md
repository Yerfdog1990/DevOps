# Git Rollback

## 1. Why Rollback?

In real-world development, things break. You make changes to a file, something stops working, and you need to undo those changes. Git gives you multiple ways to roll back — each suited to a different stage of the workflow.

The key is knowing **how far along** your change is:

```
Stage 1: Changes made, not yet staged
Stage 2: Changes staged (git add), not yet committed
Stage 3: Changes committed (git commit)
```

Each stage has its own rollback method.

---

## 2. Checking What Changed — `git diff`

Before rolling back, always check what actually changed using `git diff`.

### Before Staging
```bash
git diff
```
Shows the difference between your **working directory** and the **last commit**. Lines added show with `+`, lines removed with `-`.

### After Staging (git add)
```bash
git diff --cached
```
Shows the difference between the **staging area** and the **last commit**. Plain `git diff` shows nothing once files are staged — you need `--cached` to see staged changes.

### Between Two Commits
```bash
git log --oneline                       # Get commit IDs
git diff abc1234..def5678               # Compare two commits
```

> Always use `git diff` before rolling back — it confirms exactly what you're undoing and prevents surprises.

---

## 3. The Three Rollback Levels

```
Working Directory  →  Staging Area  →  Local Repository
  (git add .)          (git commit)
       ↑                    ↑                  ↑
  git checkout          git restore        git revert
  <filename>            --staged           OR
                        <filename>         git reset --hard
                                           <commit-id>
```

---

## 4. Level 1 — Rollback Before Staging

**Situation:** You edited a file but haven't run `git add` yet.

```bash
git checkout <filename>
```

**Example:**
```bash
vim jupiter1.rb          # Make some changes
git status               # Shows: modified: jupiter1.rb
git diff                 # Shows exactly what changed

git checkout jupiter1.rb # Rollback — file restored to last commit
git status               # Clean — nothing to commit
```

> This **immediately discards** your unsaved changes. There is no undo for this — the changes are gone.

---

## 5. Level 2 — Rollback After Staging (`git add`)

**Situation:** You've already run `git add` (file is in the staging area) but haven't committed yet.

```bash
git restore --staged <filename>
```

**Example:**
```bash
vim jupiter1.rb          # Make changes
git add jupiter1.rb      # Stage the file

git diff                 # Nothing — it's already staged
git diff --cached        # Shows staged changes

git restore --staged jupiter1.rb   # Unstage the file
git status               # Shows: modified (back to unstaged)
git diff                 # Can see changes again
```

After `git restore --staged`, the file goes back to **Level 1** — changes still exist in your working directory but are no longer staged. You can then either keep editing or use `git checkout <filename>` to discard completely.

---

## 6. Level 3 — Rollback After Committing

Once you've committed, you have two options depending on whether you want to **keep the history** of the mistake or **erase it**.

---

### Option A — `git revert` (Soft Rollback — keeps history)

`git revert` creates a **new commit** that undoes the changes of a previous commit. The original commit stays in the history — nothing is erased.

```bash
git log --oneline
# a1b2c3d Add content to jupiter1.rb   ← you want to undo this
# e4f5g6h Previous clean commit

git revert HEAD              # Revert the most recent commit
# OR
git revert a1b2c3d           # Revert a specific commit by ID
```

Git opens vim for a revert commit message — save and quit (`:wq`) to accept the default.

After reverting:
```bash
git log --oneline
# f7g8h9i Revert "Add content to jupiter1.rb"   ← new revert commit
# a1b2c3d Add content to jupiter1.rb             ← original still in history
# e4f5g6h Previous clean commit
```

The file content is back to how it was before `a1b2c3d`, but **both commits remain in the log**.

**When to use `git revert`:**
- When the commit has already been **pushed to a shared remote** — rewriting shared history causes problems for teammates
- When you want to **preserve the audit trail** of what happened

---

### Option B — `git reset --hard` (Hard Rollback — erases history)

`git reset --hard` moves the branch pointer back to a specific commit and **permanently removes** all commits after that point, along with their data.

```bash
git log --oneline
# a1b2c3d Add content to jupiter1.rb   ← and everything after this is gone
# e4f5g6h Previous clean commit         ← go back to here

git reset --hard e4f5g6h     # Reset to this commit, erase everything after
```

After resetting:
```bash
git log --oneline
# e4f5g6h Previous clean commit         ← only this remains
```

The commits after `e4f5g6h` are **permanently gone** — no history, no way to recover them.

**When to use `git reset --hard`:**
- When the commit has **NOT been pushed** to a shared remote yet
- When you want a completely clean slate with no trace of the mistake
- Fixing an accidental commit on the wrong branch (before pushing)

> ⚠️ **Warning:** `git reset --hard` is irreversible. Always double-check the commit ID before running it. Never use it on commits that have already been pushed to a shared repository — it will cause conflicts for your teammates.

---

## 7. All Reset Modes — `git reset` Explained

`git reset` has three modes depending on what you want to happen to the changes after the commit is removed.

### Mode Comparison

| Mode | Removes Commit | Staging Area | Working Files |
|---|---|---|---|
| `--soft` | ✅ Yes | Changes stay staged | Files unchanged |
| `--mixed` (default) | ✅ Yes | Changes unstaged | Files unchanged |
| `--hard` | ✅ Yes | Cleared | Files deleted ⚠️ |

---

### `git reset --soft HEAD~1` — Undo commit, keep changes staged

The commit is removed but all its changes remain **staged and ready to recommit**. Nothing in your files changes.

```bash
# History before:
# A --- B --- C   ← C is the latest commit

git reset --soft HEAD~1

# History after:
# A --- B
# Changes from C are still staged (git add was not undone)
```

**Use case:** You committed with the wrong message and want to recommit with a better one:
```bash
git reset --soft HEAD~1
git commit -m "Correct commit message"
```

---

### `git reset --mixed HEAD~1` — Undo commit, unstage changes (default)

The commit is removed and changes are **unstaged**, but still exist in your files. This is the default mode if you just run `git reset HEAD~1`.

```bash
git reset --mixed HEAD~1
# OR simply:
git reset HEAD~1

# Changes from the commit are now:
# - NOT committed
# - NOT staged
# - Still present in your files
```

**Use case:** You want to undo the commit and re-examine what you staged before recommitting.

---

### `git reset --hard HEAD~1` — Undo commit and delete changes

The commit is removed and all its changes are **permanently deleted** from files too.

```bash
git reset --hard HEAD~1

# Changes from the commit are:
# - NOT committed
# - NOT staged
# - GONE from files ⚠️
```

---

### Undoing Multiple Commits with `git reset`

```bash
git reset --hard HEAD~3
```

Removes the last 3 commits entirely.

```
Before: A --- B --- C --- D --- E
After:  A --- B
```

Commits C, D, and E are permanently erased.

---

## 8. Viewing an Old Commit — `git checkout` and `git switch --detach`

Sometimes you don't want to undo anything — you just want to **look at** what the project looked like at an older point in time.

### Classic Method
```bash
git log --oneline                   # Find the commit hash
git checkout a1b2c3d                # Go to that commit
```

### Modern Method (Preferred)
```bash
git switch --detach a1b2c3d         # Same result, cleaner syntax
```

Both put you in **detached HEAD state** — you're viewing a historical snapshot. You can inspect files, run code, look around. You are not on any branch.

```bash
# To return to your branch:
git switch main
```

> Detached HEAD is read-only exploration — no changes you make here will affect any branch unless you explicitly create a new one.

---

## 9. Rolling Back After Push — `git push --force` ⚠️

If you've already pushed to a remote and need to revert using `git reset`, you must force-push to overwrite the remote history:

```bash
git reset --hard HEAD~1
git push --force
```

> ⚠️ **Dangerous.** `git push --force` rewrites the remote history. Anyone else working on that branch will have their local history broken. Only use this on **personal or private branches** — never on shared branches like `main`.

**The safe alternative after pushing is always:**
```bash
git revert <commit-hash>    # Safe — creates a new commit, no history rewriting
git push origin main
```

---

## 10. Comparison — All Reset Modes vs Revert

| Command | Removes Commit | Files Changed | History Rewritten | Safe After Push |
|---|---|---|---|---|
| `git restore <file>` | Not committed yet | ✅ Restored | ❌ N/A | ✅ Yes |
| `git restore --staged <file>` | Not committed yet | ❌ Kept | ❌ N/A | ✅ Yes |
| `git reset --soft HEAD~1` | ✅ Yes | ❌ Kept | ✅ Yes (local) | ❌ No |
| `git reset --mixed HEAD~1` | ✅ Yes | ❌ Kept (unstaged) | ✅ Yes (local) | ❌ No |
| `git reset --hard HEAD~1` | ✅ Yes | ⚠️ Deleted | ✅ Yes (local) | ❌ No |
| `git revert <hash>` | ❌ Adds new commit | ❌ Undone via new commit | ❌ No | ✅ Yes |

---

## 11. Comparison — `git revert` vs `git reset --hard`

| Feature | `git revert` | `git reset --hard` |
|---|---|---|
| Removes commit from history | ❌ No — adds a new revert commit | ✅ Yes — erases commits |
| Safe for shared/pushed code | ✅ Yes | ❌ No — never on pushed commits |
| Preserves audit trail | ✅ Yes | ❌ No |
| Can recover after running | ✅ Yes (revert is just a commit) | ❌ No (data is gone) |
| Best for | Shared repos, production code | Local mistakes before pushing |

---

## 12. `HEAD` — What it Means

`HEAD` is a pointer that always points to the **current commit** — the latest commit on your current branch.

```bash
git revert HEAD          # Revert the most recent commit
git reset --hard HEAD~1  # Go back one commit from the current position
git reset --hard HEAD~2  # Go back two commits
```

| Expression | Meaning |
|---|---|
| `HEAD` | The current (most recent) commit |
| `HEAD~1` | One commit before current |
| `HEAD~2` | Two commits before current |

## 13. Full Rollback Decision Flow

```
You made a change...
        │
        ▼
 Have you run git add?
   NO ──► git restore <file>              (discard working dir changes)
          OR git checkout <file>          (older alternative)
        │
       YES (staged)
        │
        ▼
 Have you run git commit?
   NO ──► git restore --staged <file>    (unstage, keep changes)
        │
       YES (committed)
        │
        ├── Just want to look at old commit? ──► git switch --detach <hash>
        │
        ├── Undo commit, keep changes staged? ──► git reset --soft HEAD~1
        │
        ├── Undo commit, unstage changes? ──► git reset --mixed HEAD~1
        │
        ├── Has it been pushed to remote?
        │     NO ──► git reset --hard HEAD~1    (erase commits locally)
        │    YES ──► git revert <hash>          (safe — new commit, no rewrite)
        │
        └── Multiple commits to remove?
              git reset --hard HEAD~3           (remove last 3, before push only)
```

## 14. Quick Reference Summary

| Command | When to Use | What it Does |
|---|---|---|
| `git diff` | Before staging | Show unstaged changes |
| `git diff --cached` | After staging | Show staged changes vs last commit |
| `git diff <id1>..<id2>` | Anytime | Compare two commits |
| `git restore <file>` | Before staging | Discard working directory changes |
| `git restore .` | Before staging | Discard ALL unstaged changes |
| `git checkout <file>` | Before staging | Same as restore (classic) |
| `git restore --staged <file>` | After staging | Unstage a file, keep changes |
| `git reset --soft HEAD~1` | After commit, before push | Undo commit, keep staged |
| `git reset --mixed HEAD~1` | After commit, before push | Undo commit, unstage changes |
| `git reset --hard HEAD~1` | After commit, before push | Undo commit, delete changes ⚠️ |
| `git reset --hard HEAD~3` | Before push | Remove last 3 commits entirely ⚠️ |
| `git revert HEAD` | After committing or pushing | New commit that undoes last commit |
| `git revert <hash>` | After committing or pushing | New commit that undoes specific commit |
| `git checkout <hash>` | Anytime | View old commit (read-only, classic) |
| `git switch --detach <hash>` | Anytime | View old commit (read-only, modern) |
| `git push --force` | After reset on remote ⚠️ | Force overwrite remote (dangerous) |
| `git log --oneline` | Anytime | Find commit IDs |

---

## 15. Key Takeaways

- Git rollback is **stage-dependent** — the method you use depends on how far the change has progressed.
- Always run **`git diff`** before rolling back — confirm what you're undoing before you do it.
- `git restore <file>` — instant rollback for unstaged changes. Irreversible, no recovery.
- `git restore --staged <file>` — moves a staged file back to "modified but unstaged". Changes are not lost.
- **`git reset --soft`** undoes the commit but leaves changes staged — ideal for fixing a commit message.
- **`git reset --mixed`** (the default) undoes the commit and unstages changes — files are untouched.
- **`git reset --hard`** is the most aggressive — commit gone, files gone. Only use **before pushing**.
- **`git revert`** is always the safe choice after pushing — it creates a new undoing commit without rewriting history.
- `git push --force` rewrites remote history — only ever use on personal branches, never on shared `main`.
- `git switch --detach <hash>` lets you safely explore an old commit without affecting any branch.
- `HEAD` is your current position. `HEAD~1` = one step back, `HEAD~3` = three steps back.
- When in doubt: **`git revert` is always safe. `git reset --hard` is always final.**
