# Git Versioning

## 1. The Git Versioning Workflow Overview

Git versioning involves three key areas:

```
Working Directory  →  Staging Area  →  Local Repository  →  Remote Repository
  (make changes)      (git add)         (git commit)          (git push)
```

And in reverse — pulling others' changes:
```
Remote Repository  →  Local Repository
    (git pull)
```

---

## 2. Initial Git Setup — Global Config

Before you can commit anything, Git needs to know **who you are**. This is recorded with every commit so the team can see who made each change.

```bash
git config --global user.email "your@email.com"
git config --global user.name "Your Name"
```

| Option | Meaning |
|---|---|
| `--global` | Applies to all repositories on your machine |
| `--local` | Applies only to the current repository |

> Use the same email address as your GitHub account — this links your local commits to your GitHub profile correctly.

You only need to do this **once per machine**. After that, every commit you make includes your name and email automatically.

---

## 3. Creating a Local Git Repository

### Step 1 — Create a directory and navigate into it
```bash
mkdir titanwork
cd titanwork
```

### Step 2 — Initialize Git
```bash
git init
```

This creates a hidden `.git` directory inside your folder:
```bash
ls -a
# .  ..  .git
```

The `.git` directory is the engine of Git — it stores all versions, history, branches, and configuration for this repository. **Never delete or modify it manually.**

After `git init`, your terminal prompt changes to show the current branch name (e.g. `(master)` or `(main)`).

---

## 4. Adding Files to the Repository

Git does **not** track empty directories — it only tracks files. Create some files or directories with files:

```bash
mkdir nebula jupiter pluto
touch jupiter/jupiter.py nebula/nebula.py
touch saturn1.py saturn2.py
```

---

## 5. Checking Repository Status — `git status`

```bash
git status
```

Output before staging:
```
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        jupiter/
        nebula/
        saturn1.py
```

**Untracked** means Git sees the files but is not recording changes to them yet.

---

## 6. Staging Files — `git add`

Staging means telling Git: *"Include these changes in the next commit."*

```bash
git add .                   # Stage everything in the current directory
git add saturn1.py          # Stage a specific file
git add jupiter/            # Stage a specific directory
```

Check status again after staging:
```bash
git status
# Changes to be committed:
#   new file: jupiter/jupiter.py
#   new file: saturn1.py
```

Files now show as **"Changes to be committed"** — they are in the **staging area**.

> The staging area (also called the **index**) is a holding zone between your working directory and the local repository. It lets you choose exactly which changes go into the next commit.

---

## 7. Committing — `git commit`

A commit saves a permanent snapshot of everything in the staging area into your **local repository**.

```bash
git commit -m "New files added"
```

Output:
```
13 files changed, 0 insertions(+), 0 deletions(-)
```

After committing:
```bash
git status
# nothing to commit, working tree is clean
```

### Commit Message Best Practices

Every commit requires a message. Good messages explain **what changed and why**:

```bash
git commit -m "Add Saturn moon names"
git commit -m "Updated Saturn moon list — removed duplicates"
git commit -m "Fix login bug in auth module"
```

> A clear commit history is invaluable when tracing bugs or understanding what changed and when.

## 8. Connecting to a Remote Repository (GitHub)

A **remote repository** is the shared, cloud-hosted version of your repo (on GitHub, Bitbucket, etc.).

### Creating a Repository on GitHub

1. Go to **github.com** and log in
2. Click **New Repository**
3. Give it the **same name** as your local directory (e.g. `titanwork`)
4. Choose **Public** (anyone can see) or **Private** (authentication required)
5. Click **Create Repository** — leave README unchecked for now

GitHub shows you the HTTPS and SSH URLs of the new (empty) repo.

### Linking Local Repo to Remote

Copy the HTTPS URL from GitHub and run:

```bash
git remote add origin https://github.com/username/titanwork.git
```

This adds an entry inside `.git/config` pointing to the remote:
```bash
cat .git/config
# [remote "origin"]
#     url = https://github.com/username/titanwork.git
```

Rename your branch to `main` (modern standard):
```bash
git branch -m main
```

### Pushing Local Repo to Remote — First Time

```bash
git push -u origin main
```

| Part | Meaning |
|---|---|
| `push` | Send commits to the remote |
| `-u` | Set `origin main` as the default upstream (only needed once) |
| `origin` | The name of the remote (GitHub repo) |
| `main` | The branch to push |

Git will prompt for authentication (browser popup or username/password). Once authenticated, credentials are saved — no need to enter them again.

After pushing, refresh GitHub — you'll see all your files, directories, and commit messages, including who made them and when.

## 9. Making and Tracking Changes

### Edit a file
```bash
vim saturn1.py
# Add: "Saturn has many moons: Mimas, Dione, Rhea, Hyperion, Phoebe..."
# Save and quit :wq
```

### Check what changed
```bash
git status
# modified: saturn1.py
```

### Stage, commit, push
```bash
git add .
git commit -m "Add Saturn moon names"
git push origin main
```

### View the change on GitHub
Click the commit message on GitHub — lines **added** show in green with `+`, lines **removed** show in red with `-`.

---

## 10. Viewing Commit History — `git log`

### Full log
```bash
git log
```

Shows for each commit:
- Full commit ID (hash)
- Author name and email
- Date and time
- Commit message

### Compact one-line log
```bash
git log --oneline
# a1b2c3d Add Saturn moon names
# e4f5g6h Updated Saturn moon list
# 7i8j9k0 New files added
```

### Inspect a specific commit
```bash
git show a1b2c3d              # Show exactly what changed in this commit
```

Output shows lines **added** (`+`) and lines **removed** (`-`) — same as GitHub's diff view.

---

## 11. Pulling Changes — `git pull`

When someone else pushes changes to the remote repository, pull those changes to your local copy:

```bash
git pull
```

**Practical scenario:**
- A teammate edits `saturn10.py` directly on GitHub and commits
- You run `git pull` locally to receive their change
- `git log` now shows their commit with their name and timestamp

```bash
git pull
git log --oneline
# b2c3d4e Update saturn10.py      ← teammate's commit, now in your local repo
# a1b2c3d Add Saturn moon names   ← your previous commit
```

## 12. Two Ways to Start Working with a Remote Repo

| Approach | When to use | Commands |
|---|---|---|
| **Local → Remote** | You created the repo locally first | `git init` → `git remote add origin <url>` → `git push -u origin main` |
| **Remote → Local** | Repo already exists on GitHub | `git clone <url>` |

### Cloning an existing repository
```bash
git clone https://github.com/username/titanwork.git
cd titanwork
```

`git clone` downloads the **complete repository** — all files, all branches, all history — in one command.

## 13. Full Local-to-Remote Workflow

```bash
# ── One-time setup ──────────────────────────────────────────────
git config --global user.name "Your Name"
git config --global user.email "your@email.com"

# ── Create local repo ───────────────────────────────────────────
mkdir titanwork && cd titanwork
git init

# ── Add files and commit locally ────────────────────────────────
touch saturn1.py
git add .
git commit -m "Initial commit"

# ── Connect to GitHub remote ────────────────────────────────────
git remote add origin https://github.com/username/titanwork.git
git branch -m main
git push -u origin main

# ── Day-to-day cycle ────────────────────────────────────────────
vim saturn1.py              # Make changes
git status                  # Check what changed
git add .                   # Stage changes
git commit -m "Update"      # Commit locally
git push origin main        # Push to remote

# ── Get others' changes ─────────────────────────────────────────
git pull                    # Pull from remote
git log --oneline           # Review history
git show <commit-id>        # See what a specific commit changed
```

## 14. Quick Reference Summary

| Command | What it does |
|---|---|
| `git config --global user.name "Name"` | Set global username |
| `git config --global user.email "email"` | Set global email |
| `git init` | Initialize a new local repository |
| `git status` | Show working tree and staging area status |
| `git add .` | Stage all changed files |
| `git add <file>` | Stage a specific file |
| `git commit -m "message"` | Commit staged changes to local repo |
| `git remote add origin <url>` | Link local repo to a remote |
| `git branch -m main` | Rename branch to main |
| `git push -u origin main` | Push and set upstream (first time only) |
| `git push origin main` | Push commits to remote |
| `git pull` | Fetch and merge latest changes from remote |
| `git clone <url>` | Clone a complete remote repo locally |
| `git log` | View full commit history |
| `git log --oneline` | View compact commit history |
| `git show <commit-id>` | Show what a specific commit changed |

---

## 15. Key Takeaways

- Before your first commit, always set `git config --global user.name` and `user.email` — every commit is permanently tagged with this info.
- `git init` creates the `.git` folder — this hidden directory IS the Git database. Never delete it.
- Git tracks **files only** — empty directories are ignored entirely.
- The core local cycle is: **`git add` → `git commit`**. The push cycle adds: **`git push`**.
- `git status` is your most-used command — run it constantly to understand the state of your repo.
- The **staging area** (index) is a deliberate step between editing and committing — it lets you craft focused, clean commits.
- Every commit needs a meaningful message — it becomes your permanent audit trail.
- `git log --oneline` gives a compact history; `git show <id>` reveals exactly what changed in any commit.
- `git pull` syncs others' remote changes to your local machine — run it before starting work each day in a team environment.
- Public repos clone without authentication; private repos require credentials (browser login or SSH key).
