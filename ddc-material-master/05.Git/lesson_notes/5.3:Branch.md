# Git Branches

## 1. What is a Branch?

A **branch** is an independent line of development — an isolated copy of the codebase where you can make changes without affecting the stable `main` code.

### Why Branches Exist

In team environments, multiple developers work on different features simultaneously. Branches keep each person's work isolated until it's ready to be merged back.

- Keep **stable, working code** in `main`
- Create a **new branch** for each feature, sprint, or bug fix
- Make changes freely in that branch
- **Merge** back into `main` when the work is done and tested

## 2. Branch Naming Conventions

### Feature / Component-Based (Most Common in Companies)
```
feature/auth-service
feature/payment-api
feature/modelmapper-config
feature/JIRA-102-auth-service        ← with ticket number
```

### Task / Bug Fix Branches
```
task/add-login-api
bugfix/fix-auth-error
hotfix/payment-timeout
```

### Git Flow Style (Used in Many Professional Teams)
```
main                    ← production-ready, always stable
develop                 ← integration branch
feature/login-page      ← individual feature work
release/v1.2.0          ← preparing a release
hotfix/security-patch   ← urgent production fix
```

### Learning / Daily Progress Style
```
day-1-linux
day-2-git
day-3-shell-scripting
```

### Best Practices for Naming

| Rule | Good | Bad |
|---|---|---|
| Use lowercase | `feature/login-api` | `Feature/LoginAPI` |
| Use hyphens not spaces | `feature/user-profile` | `feature/user profile` |
| Be descriptive | `feature/jwt-authentication` | `stuff`, `test1`, `changes` |

## 3. Full Branch Workflow — with Diagram

### Visual Flow

```
main    ──●────────────────────────────────────────●──► push origin main
           \                                      /
            ● create feature branch              ● merge feature into main
             \                                  /
feature/X     ●──●──● (make changes, commit)──●
                                               ▲
                                          git push origin feature/X
```

### Step-by-Step Commands

```bash
# Step 1 — Start on main, pull latest
git switch main
git pull origin main

# Step 2 — Create and switch to a new feature branch
git switch -c feature/modelmapper-config
# -c means: create AND switch in one command

# Step 3 — Make your changes
# (edit files, create classes, etc.)

# Step 4 — Stage and commit
git add .
git commit -m "Add ModelMapper configuration"

# Step 5 — Push the feature branch to remote
git push -u origin feature/modelmapper-config
# -u sets upstream tracking (only needed first time per branch)

# Step 6 — Switch back to main
git switch main

# Step 7 — Pull latest main (good practice before merging)
git pull origin main

# Step 8 — Merge the feature branch into main
git merge feature/modelmapper-config
# Git may open vim for a merge commit message — :wq to accept

# Step 9 — Push updated main to remote
git push origin main
```

## 4. Creating and Listing Branches

```bash
git branch -c sprint1           # Create a branch from current branch
git switch -c feature/login     # Create AND switch in one step (preferred)
git branch -a                   # List all branches (local + remote)
git branch                      # List local branches only (* = current branch)
```

---

## 5. Switching Between Branches

```bash
git switch main                     # Switch to main (modern — preferred)
git switch feature/modelmapper-config  # Switch to a feature branch
git checkout sprint1                # Classic alternative (still works)
```

> Always check which branch you're on before committing or pushing:
> ```bash
> git branch        # The * shows your current branch
> ```

## 6. Git-Aware File Operations in Branches

When making changes inside a branch, use Git-aware versions of file commands:

```bash
# Removing files
git rm saturn6.py           # Removes from disk AND from Git's index
# NOT: rm saturn6.py        ← leaves Git confused

# Renaming / moving files
git mv saturn1.py saturn11.py    # Renames and updates Git's index
# NOT: mv saturn1.py saturn11.py ← Git sees it as delete + new file
```

## 7. `.gitignore` — Ignoring Files in Branches

Some files should never be committed (logs, temp files, credentials). Create a `.gitignore` in each branch that needs it:

```bash
vim .gitignore
```

```
*.log           # Ignore all log files
*.tmp           # Ignore temp files
debug.log       # Ignore a specific file
node_modules/   # Ignore an entire directory
```

Commit `.gitignore` to the branch:
```bash
git add .gitignore
git commit -m "Add gitignore"
```

## 8. Pushing All Branches at Once

```bash
git push --all origin           # Push every local branch to the remote
```

## 9. ⚠️ Fixing a Commit Made on the Wrong Branch

This is one of the most common Git mistakes. You committed on `main` but the changes should have gone into `feature/entities`.

### Situation

```
main          -> accidentally has commit abc1234
feature/entities -> is missing that commit (should have it)
```

### The Fix — `git cherry-pick`

`git cherry-pick` copies a specific commit from one branch and applies it to another, without affecting the original branch.

#### Step 1 — Find the commit hash on the wrong branch

Switch to `main` (where the accidental commit is) and get the hash:

```bash
git switch main
git log --oneline
# abc1234 feat(entity): add entities and entity relation diagram   ← this is the one
# def5678 previous commit
```

Copy the commit hash: `abc1234`

#### Step 2 — Switch to the correct branch

```bash
git switch feature/entities
```

#### Step 3 — Cherry-pick the commit onto the correct branch

```bash
git cherry-pick abc1234
```

Now `feature/entities` contains the commit. Verify:

```bash
git log --oneline
# abc1234 feat(entity): add entities and entity relation diagram  ← now here ✓
```

#### Step 4 — Push the correct branch to remote

```bash
git push origin feature/entities
```

#### Step 5 — Switch back to main and remove the accidental commit

```bash
git switch main
git reset --hard HEAD~1
```

| Command | What it does |
|---|---|
| `git reset` | Only unstages files — does NOT remove commits |
| `git reset --hard HEAD~1` | Removes the last commit AND resets files to previous state |

`HEAD~1` means "go back one commit from the current HEAD."

#### Step 6 — Pull latest main (sync with remote)

```bash
git pull origin main
# Usually: Already up to date.
```

#### Step 7 — Merge the correct branch into main

```bash
git merge feature/entities
```

#### Step 8 — Push updated main to remote

```bash
git push origin main
```

### Full Fix Flow — Visual

```
BEFORE (wrong state):
main          ──●──abc1234 (accidental)
feature/entities ──● (missing the commit)

STEP 1: git log on main → get hash abc1234
STEP 2: git switch feature/entities
STEP 3: git cherry-pick abc1234
feature/entities ──●──abc1234 ✓

STEP 4: git push origin feature/entities
STEP 5: git switch main → git reset --hard HEAD~1
main          ──● (accidental commit removed) ✓

STEP 6: git pull origin main
STEP 7: git merge feature/entities
STEP 8: git push origin main
main          ──●──abc1234 ✓ (now merged correctly)
```

## 10. Common Mistake — Pushing to the Wrong Remote Branch

```bash
# You are on main but accidentally run:
git push origin feature/entities
# Git pushes MAIN's content to origin/feature/entities — wrong!
```

**Always confirm your current branch before pushing:**

```bash
git branch          # * shows current branch
# * main            ← you are on main! Switch first.
git switch feature/entities
git push origin feature/entities    # Now correct
```

---

## 11. Optional Cleanup — Deleting a Branch After Merge

Once a feature branch is fully merged and no longer needed:

```bash
git branch -d feature/entities          # Delete local branch
git push origin --delete feature/entities  # Delete remote branch
```

## 12. Quick Reference Summary

| Command | What it does |
|---|---|
| `git branch -c <name>` | Create a new branch |
| `git switch -c <name>` | Create AND switch to a new branch |
| `git switch <branch>` | Switch to an existing branch |
| `git branch -a` | List all branches (local + remote) |
| `git branch` | List local branches (`*` = current) |
| `git push origin <branch>` | Push a specific branch to remote |
| `git push --all origin` | Push all branches to remote |
| `git merge <branch>` | Merge named branch into current branch |
| `git log --oneline` | View compact commit history |
| `git cherry-pick <hash>` | Copy a specific commit to current branch |
| `git reset --hard HEAD~1` | Remove the last commit (irreversible locally) |
| `git pull origin main` | Pull latest changes from remote main |
| `git branch -d <name>` | Delete a local branch (after merge) |
| `git push origin --delete <name>` | Delete a remote branch |

---

## 13. Key Takeaways

- **Always start from `main`** and pull before creating a new branch — this ensures your branch is based on the latest stable code.
- Use **`git switch -c feature/name`** to create and switch in one command — the modern, clean way.
- **Always check your current branch** (`git branch`) before committing or pushing — most wrong-branch mistakes happen because of this.
- `git cherry-pick <hash>` is the clean way to move a commit from the wrong branch to the right one.
- `git reset --hard HEAD~1` removes the last commit locally — use this to clean up the branch the commit was accidentally made on.
- After cherry-picking: **push the correct branch → remove from wrong branch → pull main → merge → push main** — this is the complete recovery workflow.
- `git push origin feature/X` pushes your **current local branch** to `origin/feature/X` — the two are separate. Git does not automatically switch branches when pushing.
- Use descriptive branch names: `feature/modelmapper-config` is far better than `stuff` or `test1`.
- Delete branches after merging — it keeps the repository clean and avoids confusion.
- The merge commit message in vim: just `:wq` to accept the default — no need to change it.
