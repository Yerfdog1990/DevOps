# Re-Architecting With AWS Cloud — Part 1

---

## 1. Project Overview — What is Re-Architecture (Refactoring)?

> **Re-architecture** (also called **refactoring**) is a cloud migration strategy where you don't just move services to the cloud (lift and shift) — you **replace them with managed cloud services** (PaaS/SaaS) that AWS operates for you.

### Previous Strategy vs. This Strategy

| Aspect | Lift and Shift (Previous) | Re-Architecture (This Project) |
|---|---|---|
| **EC2 instances** | Manual — you manage OS, software, patching | Beanstalk manages EC2 automatically |
| **Database** | MariaDB on EC2 (you manage it) | **Amazon RDS** (AWS manages it) |
| **Cache** | Memcache on EC2 (you manage it) | **Amazon ElastiCache** (AWS manages it) |
| **Message queue** | RabbitMQ on EC2 (you manage it) | **Amazon MQ** (AWS manages it) |
| **App deployment** | Manual — SSH, copy WAR, restart Tomcat | **Elastic Beanstalk** — deploy with one click |
| **Load Balancer** | Manual ALB setup | **Built into Beanstalk** |
| **Auto Scaling** | Manual ASG setup | **Built into Beanstalk** |
| **CDN** | None | **Amazon CloudFront** |
| **Operational overhead** | High — many servers to manage | Low — cloud manages most things |

### Why Re-Architecture?

| Benefit | Description |
|---|---|
| **Boost agility** | Add features faster with less infrastructure management |
| **Improve business continuity** | Managed services have built-in HA and backups |
| **Effective scaling** | Cloud services scale automatically |
| **Better performance** | Optimized managed services vs. self-managed software |
| **Lower operational overhead** | Small teams can manage large workloads |
| **Infrastructure as Code** | Everything configurable programmatically |
| **Pay as you go** | No upfront capital expense |

```

     ↓

  └── Amazon MQ (RabbitMQ 3.13)       → message queue service

  └── Amazon S3 bucket (deploy with one click to Beanstalk)
```

## 5. Backend Security Group

> All three backend services (RDS, ElastiCache, Amazon MQ) are placed in **one shared security group**. This allows them to communicate with each other (internal traffic) and to be accessed from the Beanstalk application instances.

### Step 1 — Create Empty Security Group First

```
EC2 → Security Groups → Create Security Group

Name:        vprofile-rearch-backend-SG
Description: Security group for RDS, ElastiCache, Amazon MQ (re-architecture project)

Inbound Rules:  (leave empty for now)
Outbound Rules: Default (do NOT modify)

→ Create Security Group
```

> The reason to create it empty first: you need the security group's own **ID** to add the self-referencing rule. You can't reference a security group that hasn't been created yet.

### Step 2 — Add Self-Referencing Rule (After Creation)

```
Security Groups → Select vprofile-rearch-backend-SG → Edit Inbound Rules

Add Rule:
  Type:   All traffic
  Source: vprofile-rearch-backend-SG  (its own security group ID)
  Description: Allow all traffic within backend SG

→ Save Rules
```

> **Why this rule is needed:** All backend services (RDS, ElastiCache, MQ) are in this security group. They need to communicate with each other (e.g., application makes calls that chain through services). This rule allows any service within the backend SG to talk to any other service within it on any port.

### Step 3 — Add Beanstalk Rule (Added LATER)

After Elastic Beanstalk is created, it generates its own security group for the EC2 instances. At that point, add another inbound rule:

```
Edit Inbound Rules → Add Rule:
  Type:   All traffic
  Source: [Beanstalk App Instance Security Group ID]
  Description: Allow traffic from Beanstalk app instances

→ Save Rules
```

## 7. Creating Amazon RDS (MySQL)

### Prerequisites — Parameter Group

```
RDS → Parameter Groups → Create Parameter Group

Name:        vprofile-rds-rearch-paragrp
Description: vprofile-rds-rearch-paragrp
Engine:      MySQL Community
Family:      mysql8.4  ← must match the DB version you'll create
Type:        DB parameter group  ← NOT cluster parameter group

→ Create
```

> Parameter groups control hundreds of MySQL configuration options. The default group works for most cases. Create your own group so you can later modify specific MySQL settings (buffer size, max connections, etc.) without touching the default. Tested and confirmed working with vprofile on MySQL 8.4.

### Prerequisites — Subnet Group

```

Description: vprofile-rds-rearch-subgrp
VPC:         Default VPC

Availability Zones: Select all zones

→ Create
```

> **Note:** If you get an error that a particular zone or subnet is unavailable, remove it from the selection and try again.

## 8. Creating Amazon ElastiCache (Memcached)

### What is ElastiCache?

> **Amazon ElastiCache** is a fully managed, in-memory caching service compatible with Valkey, Memcached, and Redis OSS. It delivers sub-millisecond response times by storing frequently accessed data in memory, reducing load on the database.

| Capability | Description |
|---|---|
| **Fully managed** | AWS handles patching, monitoring, failure recovery, backups |
| **Extreme performance** | Sub-millisecond response times, optimized node placements |
| **Scalable** | Scale in/out/up/down to meet demand |
| **Compatible** | Valkey, Memcached, Redis OSS |

**Use cases:** DB query caching, session storage, real-time analytics, ML feature stores, ad targeting.

**Pricing:** Valkey is 20% cheaper than Redis on node-based clusters; 33% cheaper on Serverless. Billed per node-hour or by data stored/requests (Serverless).

```
ElastiCache → Parameter Groups → Create Parameter Group

Name:        vprofile-rearch-cache-paragrp
Description: vprofile-rearch-cache-paragrp
Family:      memcached1.6  ← must match the engine version

→ Create
```

## 9. Creating Amazon MQ (RabbitMQ)

### What is Amazon MQ?

> **Amazon MQ** is a fully managed message broker service for **Apache ActiveMQ** and **RabbitMQ**. It makes it easy to migrate messaging applications to the cloud without rewriting code — it's compatible with standard AMQP protocols.

| Benefit | Description |
|---|---|
| **Accelerate migration** | Standard APIs and protocols — no code rewrite needed |
| **Offload operations** | AWS manages administration, maintenance, and HA provisioning |
| **Reduce cost** | Pay only for broker usage and storage |

> **Amazon MQ vs. Amazon SQS/SNS:** MQ is for migrating existing message brokers (RabbitMQ/ActiveMQ). SQS/SNS are AWS-native services designed from the ground up for the cloud. MQ is the right choice here because we want to keep RabbitMQ compatibility with the vprofile application.

### Create the RabbitMQ Broker

```
Amazon MQ → Create brokers → Get started

Step 1 — Select broker engine:
  ✅ RabbitMQ
  Broker engine version: 3.13
    ← IMPORTANT: Do NOT select 4.2 or later
    ← 3.13 is more stable, mature, and tested with vprofile
  → Next

Step 2 — Select deployment mode:
  ✅ Single-instance broker
    ← for learning/dev; use Cluster for production
  → Next

Step 3 — Configure settings:
  Broker name: vprofile-rearch-rabbitmq

  Broker instance type:
    mq.m7g.medium (1 CPU, ~4 GB RAM)
    ← Minimum available for MQ — no t3.micro option for Amazon MQ

  RabbitMQ access:
    Username: rabbit (or any username you choose)
    Password: BlueBunny980  ← Must be 12+ characters, with uppercase, numbers
    ← SAVE THIS PASSWORD — you'll need it for application.properties

  Additional settings → Engine version: 3.13

  Monitoring: CloudWatch Logs → ✅ Enable (for production use cases — helps with troubleshooting)

Step 4 — Network settings:
  Access type: ✅ Private access
    ← app connects to MQ internally within AWS VPC — no public access needed

  VPC: Default VPC
  Subnet: Default subnet

  Security group: Remove default → Select vprofile-rearch-backend-SG

  Data encryption: AWS owned CMK (no option to disable — this is fine)
    ← vprofile's awsrefactor branch is configured to use encrypted traffic for MQ

  Tags: Name = vprofile-rearch-rabbitmq

→ Next → Review → Create broker
```

> ⚠️ **Broker creation takes 5-10 minutes.** The endpoint appears once the broker status is "Running".

## 10. application.properties — awsrefactor Branch

The `awsrefactor` branch of the vprofile application uses different configuration values than the lift-and-shift branch. Key differences:

```properties
#JDBC Configuration for Database Connection
jdbc.driverClassName=com.mysql.cj.jdbc.Driver
jdbc.url=jdbc:mysql://<RDS-ENDPOINT>:3306/accounts?useUnicode=true&characterEncoding=UTF-8&zeroDateTimeBehavior=convertToNull
jdbc.username=admin
jdbc.password=<RDS-AUTO-GENERATED-PASSWORD>

#Memcached Configuration
memcached.active.host=<ELASTICACHE-ENDPOINT>
memcached.active.port=11211

#RabbitMQ Configuration
rabbitmq.address=<AMAZONMQ-ENDPOINT>   ← just the hostname, no amqps://
rabbitmq.port=5671                      ← 5671 for TLS (awsrefactor branch)
rabbitmq.username=rabbit
rabbitmq.password=<YOUR-MQ-PASSWORD>
```

> These values will be filled in after all backend services are created and running. The **endpoints** are available in each service's console page once status is "Available" or "Running".
