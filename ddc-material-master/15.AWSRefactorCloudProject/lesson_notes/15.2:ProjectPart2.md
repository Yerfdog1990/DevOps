## 1. Initialize the RDS Database

The RDS MySQL instance is running but empty — it needs the vprofile application schema loaded into the `accounts` database. Since RDS is private (no public internet access), we must do this from an EC2 instance inside the same VPC.

### Step 1 — Launch a Temporary MySQL Client EC2 Instance

```
EC2 → Launch Instance

Name:           mysql-client  (temporary — will be deleted after DB init)
AMI:            Ubuntu Server 24.04 LTS
Type:           t2.micro
Key pair:       vprofile-rearch-key (or create a new one)
Security group: Create new → vpro-mysql-client-sg
  → Rule: SSH | Port 22 | Source: My IP

→ Launch Instance
```

### Step 2 — Allow MySQL Client to Access RDS

The temporary EC2 instance needs to reach the RDS instance on port 3306. The RDS is in the **backend security group** — add a rule there.

```
Get the security group ID of your mysql-client EC2 instance (vpro-mysql-client-sg)

EC2 → Security Groups → vprofile-rearch-backend-SG → Edit Inbound Rules

Add Rule:
  Type:   MySQL/Aurora (or Custom TCP)
  Port:   3306
  Source: [vpro-mysql-client-sg security group ID]
  Description: Allow MySQL access from DB init client

→ Save Rules
```

### Step 3 — SSH and Install MySQL Client

```bash
ssh -i vprofile-rearch-key.pem ubuntu@<mysql-client-public-ip>

sudo -i  # Become root

apt update && apt install mysql-client git -y
```

## 2. What is AWS Elastic Beanstalk?

> **AWS Elastic Beanstalk (EBS)** is a fully managed service for deploying and scaling web applications. You upload your code — Beanstalk automatically handles capacity provisioning, load balancing, auto scaling, and health monitoring.

### What Beanstalk Replaces from Lift and Shift

| Previous (Manual) | Beanstalk (Automated) |
|---|---|
| EC2 instance (manual setup) | EC2 auto-created and managed |
| Tomcat installation script | Platform selected (Tomcat) |
| Security group creation | Auto-created by Beanstalk |
| Target group + health check | Built-in, configurable |
| Application Load Balancer | Auto-created and managed |
| Auto Scaling Group | Built-in, configurable |
| AMI creation | Handled by Beanstalk |
| S3 bucket for artifacts | Built-in per environment |
| CloudWatch monitoring | Auto-integrated |
| Deployment pipeline | Upload and deploy (one button) |

**Supported platforms:** Go, Java (Tomcat), .NET, Node.js, PHP, Python, Ruby, Docker

**Cost:** No additional charge for Beanstalk itself — you pay only for the EC2 instances, ALB, EBS volumes, and other resources it creates.

### Capacity (Auto Scaling)

```
Environment type: ✅ Load balanced  (NOT single instance)

Min instances: 2  ← minimum for load balancer to function
Max instances: 4

Instance type: t3.micro  ← free tier eligible
  (Default may be t2.small which isn't free — change to t3.micro)

Fleet composition: On-Demand instances

Scaling trigger: NetworkOut  ← most relevant for web applications
  (Traffic going out = users being served; scales with actual user load)
  
  Alternative: CPUUtilization (also commonly used)
  NetworkOut is preferred for web apps because it reflects actual serving activity
```

> **Why NetworkOut over CPU?** For web applications, network output directly correlates with serving user requests. When traffic increases, so does NetworkOut — making it an excellent signal to scale out. CPU is less direct since some requests may be lightweight but numerous.

### Load Balancer Configuration

```
Load balancer type: Application Load Balancer (ALB)
  (NLB is high-performance but expensive; ALB is ideal for HTTP/HTTPS)

Visibility: Public (internet-facing)

Listeners:
  HTTP:80 → Default process (port 80)
  (HTTPS:443 added later via Configuration after creation)

Process settings → Edit → Sessions:
  ✅ Enable stickiness  ← CRITICAL for vprofile
  Duration: 86400 seconds (1 day) or any value

  Reason: vprofile stores sessions on individual instances.
  Without stickiness, load balancer may route return requests to a different
  instance where the user's session doesn't exist → forced re-login.
```

### Health Check (Very Important)

The vprofile application returns the login page at `/login`, not the root path `/`. Beanstalk's default health check to `/` returns a redirect, which may not be considered healthy.

```
Process settings → Edit → Health check path: /login
HTTP code: 200-499
```

> This is set during creation or can be updated after. The health check must reach a URL the application actually responds to with HTTP 200.

### Monitoring

```

  (Collects 40+ metrics; required for proper rolling deployment behavior
   — checks instance health between batch deployments)

Monitoring interval: 5 minutes (free tier; 1 minute costs extra)

Email notifications: your-email@example.com
  (Receive alerts when environment health changes or deployments fail)
```

### Deployment Policy

```
Deployment policy: Rolling
Batch size: 50%  ← with 2 instances, deploys one at a time

Explanation:
  50% of 2 instances = 1 instance updated at a time
  This means one instance serves users while the other gets updated
  When batch 1 is healthy → moves to batch 2

```

  ← EXPECTED! One instance pulled from LB, getting updated
11:11:09 INFO Environment health: Degraded → Info

### Rolling Deployment — What's Happening

```
With Rolling (50%), 2 instances:

Round 1:
  Instance A → pulled from LB → updated → health checked → re-added to LB
  (During this time, Instance B handles ALL traffic)

Round 2:
  Instance B → pulled from LB → updated → health checked → re-added to LB
  (During this time, Instance A handles ALL traffic)

Result: Zero downtime, but brief capacity reduction
```

## 9. Elastic Beanstalk Deployment Policies

Understanding deployment options is important for DevOps roles and interviews:

### All at Once
```
Fastest, cheapest, but causes DOWNTIME.
All instances updated simultaneously.
Best for: dev environments, when downtime is acceptable.
Worst for: production traffic.
```

### Rolling
```
No additional cost. Brief capacity reduction during update.
Instances updated in batches (percentage or fixed number).
Best for: production when some capacity reduction is acceptable.
Example: 10-20% batch size for 10 instances = 1-2 at a time.
```

### Rolling with Additional Batch
```
No capacity reduction. Slightly more expensive (temporary extra instances).
Launches new batch BEFORE taking old instances out of service.
Best for: when you need full capacity at ALL times during deployment.
Example: 10 instances + 2 new = 12 instances temporarily → update 2 → remove 2 old.
```

### Immutable
```
Safest, most expensive. Zero downtime, easy rollback.
Creates entirely NEW set of instances with new code.
When healthy → shifts traffic → terminates old instances.
Best for: critical production, high-risk deployments.
```

### Traffic Splitting (Canary Testing)
```
Most advanced. Gradually shifts traffic to new version.
Launches new instances → sends X% of traffic there → validates → shifts rest.
If unhealthy → shifts traffic BACK to old instances immediately.
Best for: validating new versions with real traffic before full rollout.
Common interview topic: "What is canary testing?"
```

### Comparison Table

| Policy | Downtime? | Cost | Capacity During Update | Safe Rollback? |
|---|---|---|---|---|
| All at once | ✅ Yes | Cheapest | 0% during update | No |
| Rolling | ❌ No | Same | Reduced | No |
| Rolling + batch | ❌ No | Higher | Full (100%) | No |
| Immutable | ❌ No | Highest | Full + extra | ✅ Yes |
| Traffic splitting | ❌ No | High | Full | ✅ Yes (instant) |

### As Configuration Code (.ebextensions)

```yaml
# Rolling deployment — 25% at a time
option_settings:
  aws:elasticbeanstalk:command:
    DeploymentPolicy: Rolling
    BatchSizeType: Percentage
    BatchSize: 25

# Immutable with health check override
option_settings:
  aws:elasticbeanstalk:command:
    DeploymentPolicy: Immutable
    HealthCheckSuccessThreshold: Warning
    IgnoreHealthCheck: true
    Timeout: "900"

# Traffic splitting — 15% canary, 10-minute evaluation
option_settings:
  aws:elasticbeanstalk:command:
    DeploymentPolicy: TrafficSplitting
  aws:elasticbeanstalk:trafficsplitting:
    NewVersionPercent: "15"
    EvaluationTime: "10"
```

## 13. Common Issues and Troubleshooting

### "Environment health: Degraded during deployment"

```
This is NORMAL and EXPECTED during Rolling deployments.
Wait for the deployment to complete — health returns to "Ok" automatically.
See Section 8 for the full event timeline example.
```

### Application loads but login fails

```
Cause: Wrong DB credentials or endpoint in application.properties

Check:
  1. Was the WAR rebuilt AFTER updating application.properties?
  2. Is the RDS endpoint correct in the JDBC URL?
  3. Is the password the auto-generated one saved at RDS creation?
  4. Was the db_backup.sql schema loaded into the 'accounts' database?
  
Fix: Update application.properties → mvn install → Upload and deploy again
```

### Target instances show unhealthy in load balancer

```
Cause: Health check path misconfigured OR app not started yet

Check:
  1. Health check path should be /login (not /)
  2. Stickiness should be enabled
  3. App may still be starting — wait 2-3 minutes

Fix: Configuration → Instance traffic → Process → Edit → Health check path: /login
```

### "Beanstalk must use launch templates" error

```
Cause: Root volume type left as "Container default" instead of GP3

Fix: When creating environment, change root volume type to GP3 (SSD)
This forces Beanstalk to use modern launch templates instead of deprecated launch configurations.
```
