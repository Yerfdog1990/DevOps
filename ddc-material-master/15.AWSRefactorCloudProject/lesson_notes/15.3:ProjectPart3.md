## 1. Why CloudFront? The Global Latency Problem

Our vprofile application is hosted in **North Virginia (us-east-1)**. This means:

```
User in North America  → 50ms latency    ✅ Fast
User in Europe         → 150-200ms       ⚠️ Slower
User in Asia           → 300ms+          ❌ Slow
User in Australia      → 350ms+          ❌ Very slow
```

> **Do we create separate servers in every region?** No — that would be expensive, complex to manage, and require data synchronization. The solution is a **Content Delivery Network (CDN)**.

### How CloudFront Solves This

```
Without CloudFront:
  User in Australia
       ↓ ~350ms each request
  Load Balancer (N. Virginia)
       ↓
  Tomcat EC2 Instance

With CloudFront:
  User in Australia
       ↓ ~20ms (nearby edge location)
  CloudFront Edge Location (Sydney)
       ↓ Only on FIRST request (cache miss)
  Load Balancer (N. Virginia)
       ↓
  Tomcat EC2 Instance

  Second request:
  User in Australia → CloudFront Sydney (cached) → ~20ms ✅
```

**The edge location caches content.** Once the first user from a region requests the page, the content is stored at the nearest edge location. All subsequent users from that region get the cached version — much faster, without hitting the origin server.

## 2. What is Amazon CloudFront?

> **Amazon CloudFront** is a Content Delivery Network (CDN) web service that distributes content globally with low latency and high transfer speeds. It caches copies of your content at **edge locations** worldwide and delivers them from the location closest to each user.

### Key Terms

| Term | Definition |
|---|---|
| **Origin** | The source of your actual content — can be S3, EC2, ELB, or any web server (even non-AWS) |
| **Edge Location** | A smaller data center globally deployed specifically for content caching and delivery |
| **Distribution** | A CloudFront configuration — defines which origin to use, caching rules, security policies |
| **TTL (Time to Live)** | How long content stays cached at edge locations (default: 1 day) |
| **Regional Edge Cache** | Intermediate caches between edge locations and origin servers — larger, cache for longer |
| **CDN** | Content Delivery Network — a global system of distributed servers that deliver content based on geographic location |

### AWS Global Scale

| Infrastructure | Count |
|---|---|
| Regions | 30+ |
| Availability Zones | 100+ |
| CloudFront Edge Locations | 600+ |

> CloudFront has **far more locations** than AWS regions — specifically optimized for content delivery, not for running services.

### CloudFront Benefits

| Benefit | Description |
|---|---|
| **Low latency** | Content delivered from edge location closest to user |
| **High performance** | Persistent connections to origin; TCP optimization |
| **Cost efficient** | No minimum commitment; data transfer from AWS origins to CloudFront is free |
| **Secure** | HTTPS, WAF integration, DDoS protection |
| **Global reach** | 600+ edge locations — works for any user on earth |
| **No origin lock-in** | Works with S3, EC2, ELB, or any custom non-AWS origin |
| **Bi-directional** | Edge locations support both downloads (read) AND uploads (write via S3 Transfer Acceleration) |

### TTL and Cache Invalidation

- Default TTL = **1 day** — objects are deleted from edge cache after 24 hours
- Objects are then re-fetched from origin on next request
- **Manual invalidation** is possible — remove objects before TTL expires
- ⚠️ Manual invalidation is **not free** — there's a per-invalidation charge
- Use case: deploy a new version of your app → old version still cached at edges → manually invalidate to force immediate update

### CloudFront vs. S3

| Feature | Amazon S3 | Amazon CloudFront |
|---|---|---|
| Primary purpose | Object storage | Content distribution |
| Best for | Durable, accessible storage | Fast global delivery of frequently accessed content |
| Geographic redundancy | Multi-AZ within a region | Global edge network |

## 5. Creating the CloudFront Distribution

### Step 1 — Remove Old GoDaddy CNAME (Optional — Can Update Later)

```
GoDaddy → Domain → Manage DNS
→ Find the CNAME record pointing to Beanstalk ALB
→ Delete Record
```

> You can wait and update it later after creating the CloudFront distribution.

### Step 2 — Create the CloudFront Distribution

```
AWS Console → CloudFront → Create a CloudFront distribution
```

#### Plan Selection

```
Select: Free ($0/month) — for learning
  → 1M requests / 100 GB per month
  → DDoS protection, WAF, CDN, TLS certificate included
```

#### Basic Configuration

```
Distribution name: VProfileCloudFront
Description:       VProfileCloudFront (or something descriptive)
Distribution type: Single website or app
```

#### Domain Setup (Step 2 of Wizard)

```
You can add your custom domain now or skip and do it later:
  Domain: vprorearch.yerfdog.xyz  (your subdomain.yourdomain.com)

  Skip for now if preferred → "Skip domain setup"
  (We'll add the domain via "Add domain" after creation)
```

#### Origin Configuration (Step 3 — Specify Origin)

```
Origin type: Elastic Load Balancing

Origin:
  → Browse Load Balancer
  → Select region: us-east-1
  → Select your Beanstalk ALB:
    awseb--AWSEB-IbFHz2Mnl4ks-934071651.us-east-1.elb.amazonaws.com
  → ELB type: Application Load Balancer

Origin path: (leave blank)
  ← Only needed if serving from a subdirectory like /login or /app

Origin access: Customize Origin settings (for ELB origins — not S3 OAC)

Grant CloudFront access to origin: No (ELB is publicly accessible)
Enable Origin Shield: No (adds extra caching layer — optional, adds cost)

Connection attempts: 3
Connection timeout: 10 seconds
```

#### Cache Settings

```
Viewer protocol policy: HTTP and HTTPS
  (or "Redirect HTTP to HTTPS" for security-only — recommended in production)

Allowed HTTP methods: GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE
  ← Keep all methods — the app needs POST for login/form submissions

Cache policy: UseOriginCacheControlHeaders
  ← Uses the cache headers from your application
```

#### Security (Step 4 — Enable Security)

```
Security protections: Enabled (WAF)
Use monitor mode: No

AWS WAF:
  → For a public website, WAF is recommended
  → It blocks common attacks: SQL injection, XSS, DDoS
  → Not free, but for production it's essential
  → For learning/this project: can skip WAF to avoid cost
```

> **About WAF:** This is **application-level** security (Layer 7), unlike security groups which are **network-level** (Layer 4). WAF understands HTTP — it can block requests based on content, headers, geographic location, IP reputation, and bot signatures. Different from and complementary to security groups.

## 8. Validating CloudFront is Working

### Check Via Browser Developer Tools

```
1. Open a different browser OR use Incognito/Private mode
   (ensures no cached responses from previous direct-ALB access)

2. Press F12 → Network tab (or Console tab)

3. Navigate to: https://vprorearch.yerfdog.xyz

4. Click on the main GET request for the page

5. Click Headers tab → scroll down → look for "via" header

Expected value:
  via: 1.1 d1234abcd.cloudfront.net (CloudFront)
```

**What the headers tell you:**
- `via: ...cloudfront.net` → Request was routed through CloudFront ✅
- CloudFront received the request, forwarded to ALB on cache miss, cached the response
- Next user in the same region gets the cached version directly from the edge location

## 9. How Traffic Flows With CloudFront

```
First user (cache miss):
  User → DNS resolves to CloudFront → Edge location (no cache)
       → CloudFront fetches from ALB → Tomcat → Response
       → CloudFront caches response at edge location
       → Response delivered to user

Second user in same region:
  User → DNS resolves to CloudFront → Edge location (cache HIT)
       → Response served immediately from cache ✅
       → ALB and Tomcat not involved
```

> You won't "feel" the difference as the developer because you're likely in the same region as the origin (N. Virginia). The performance improvement is most dramatic for users geographically far from your origin.

## 10. CloudFront with S3 as Origin (Alternative Setup)

When the origin is S3 (e.g., for static websites), the setup differs slightly:

```
S3 bucket (Block all public access ON)
     ↑
CloudFront Distribution
  → Origin access: OAC (Origin Access Control) — recommended
  → Create new OAC → keep default settings → Create
  → AWS generates a bucket policy to copy

S3 bucket → Permissions → Bucket Policy → Paste generated policy
  (allows CloudFront IAM role to GetObject from bucket)
```

> For S3 origins: **Block Public Access can remain ON** — CloudFront uses the OAC (a special IAM identity) to access the bucket privately. Users can't access S3 directly; they must go through CloudFront.

For ELB/EC2 origins: OAC is not used (these are publicly accessible services).

## 11. Project Cleanup

Clean up in this specific order — some services depend on others:

### Step 1 — Disable CloudFront Distribution

```
CloudFront → Select your distribution
→ Disable  (⚠️ Cannot delete while enabled — must disable first)
→ Wait for status to change from "Deploying" to "Disabled"
  (takes 5-10 minutes)
```

### Step 2 — Delete RDS

```
RDS → Databases → Select vprofile-rds-rearch
→ Actions → Delete

Options:
  ☐ Create final snapshot (uncheck — no data to preserve)
  ☐ Retain automated backups (uncheck)
  ✅ I acknowledge that upon instance deletion, automated backups...

Type: "delete me"
→ Delete

(Takes several minutes)
```

### Step 3 — Delete ElastiCache

```
ElastiCache → Memcached caches → Select vprofile-rearch-cache
→ Actions → Delete
→ Type the cluster name → Delete
```

### Step 4 — Delete Amazon MQ Broker

```
Amazon MQ → Brokers → Select vprofile-rearch-rabbitmq
→ Actions → Delete
→ Type the broker name → Delete
```

### Step 5 — Prepare Backend Security Group for Beanstalk Deletion

> Before deleting Beanstalk, you must remove the inbound rule that references the Beanstalk security group from the backend security group. Otherwise the rule creates a dependency that blocks Beanstalk's full cleanup.

```
EC2 → Security Groups → vprofile-rearch-backend-SG
→ Edit Inbound Rules
→ Find and Remove: the rule that says "All traffic from Beanstalk instance SG"
→ Save Rules
```

### Step 6 — Terminate Elastic Beanstalk Environment

```
Elastic Beanstalk → Environments → Select your environment
→ Actions → Terminate Environment
→ Type the environment name → Terminate

(Takes several minutes — terminates EC2 instances, ALB, ASG, S3 bucket, CloudWatch alarms)
```

### Step 7 — Delete CloudFront Distribution (After Disabled)

```
CloudFront → Select distribution (must show "Disabled")
→ Refresh until "Deploying" disappears
→ Delete → Confirm
```

### Step 8 — Remove GoDaddy DNS Record

```
GoDaddy → Domain → Manage DNS
→ Find the CNAME record pointing to CloudFront
→ Delete Record
```

### Step 9 — Delete Backend Security Group

```
EC2 → Security Groups → Select vprofile-rearch-backend-SG
→ Actions → Delete Security Group → Confirm
```

### Step 10 — Verify Complete Cleanup

```
EC2 Dashboard → Refresh:
  ✅ 0 Running instances
  ✅ 0 Load balancers
  ✅ 0 Volumes

ElastiCache → 0 Clusters
RDS → 0 Databases
Amazon MQ → 0 Brokers
CloudFront → 0 Distributions
Beanstalk → 0 Environments
```

### Cleanup Order Summary

```
1. Disable CloudFront (must disable before delete)
2. Delete RDS
3. Delete ElastiCache
4. Delete Amazon MQ
5. Edit backend-SG: remove Beanstalk rule
6. Terminate Beanstalk environment
7. Delete CloudFront (after it's fully disabled)
8. Delete GoDaddy DNS record
9. Delete backend security group
10. Verify EC2 Dashboard is clean
```

## 12. Complete Project Architecture Recap

```
Re-Architecture — Full Stack (vprofile on AWS PaaS/SaaS)

Internet Users
     ↓
Amazon Route 53 (DNS)
     ↓
Amazon CloudFront (CDN — 600+ global edge locations)
  → Caches static content at edge locations near users
  → On cache miss: forwards to ALB
     ↓
Application Load Balancer (inside Elastic Beanstalk)
  → HTTPS:443 with ACM certificate
  → Stickiness enabled
     ↓
EC2 Instances (Auto Scaling Group — managed by Beanstalk)
  → t3.micro, Min 2, Max 4
  → Tomcat 10 / Corretto 21 / Amazon Linux 2023
  → Rolling deployment (50% batch)
  → Enhanced health monitoring
  → vprofile WAR artifact from S3 bucket

CloudWatch Alarms
  → Monitor ASG via NetworkOut metric
  → Scale out/in automatically

S3 Bucket
  → Stores WAR artifacts for deployment

Backend Services (vprofile-rearch-backend-SG):
  ├── Amazon RDS (MySQL 8.4)      → replaces MySQL on EC2
  │     Port 3306
  │     accounts database
  ├── Amazon ElastiCache          → replaces Memcache on EC2
  │     Memcached 1.6, port 11211
  │     No TLS (disabled)
  └── Amazon MQ (RabbitMQ 3.13)  → replaces RabbitMQ on EC2
        Port 5671 (AMQPS/TLS)
        SSL enabled, TLSv1.2
```
