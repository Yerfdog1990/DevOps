# Code Build & Deploy 

## Overview

With the Tomcat service running, the next step is to build the vProfile application from source and deploy it onto Tomcat. This is a three-stage process:

1. **Set up Maven** — the build tool that compiles the Java source code into a deployable package
2. **Clone and configure the source code** — pull the project from GitHub and verify backend connection settings
3. **Build and deploy** — compile the artifact and replace Tomcat's default application with it

> This is still performed on `app01`. Make sure you are logged in and are the root user before proceeding.

---

## Stage 1: Maven Setup

### Why Maven?

The vProfile source code is written in Java. Tomcat cannot run raw Java source files — it needs a compiled, packaged archive called a **WAR file** (Web Application Archive). Maven is the build tool that handles this compilation and packaging process.

Maven is not installed via `dnf` here. Like Tomcat, the binary is downloaded directly.

---

### 1. Navigate to /tmp and Download Maven

```bash
cd /tmp/
wget https://archive.apache.org/dist/maven/maven-3/3.9.9/binaries/apache-maven-3.9.9-bin.zip
```

> **If this download fails or times out**, the Apache archive servers may be unreachable from your VM. This is a known intermittent issue. See the alternative download method below before continuing.

---

#### Troubleshooting: Apache Download Fails

**Symptom:** The `wget` command times out, or `curl` downloads only a few bytes (e.g. 9 bytes) and `unzip` then fails with:

```
End-of-central-directory signature not found. Either this file is not a zipfile...
```

This means the download returned an error page rather than the actual ZIP. The Apache mirror is unreachable from your VM.

**Fix: Download from Maven Central instead**

First, remove any corrupted partial download:

```bash
rm -f apache-maven-3.9.9-bin.zip
```

Then download from Maven Central, which hosts the identical file and is typically more reliably reachable:

```bash
wget -4 https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.9/apache-maven-3.9.9-bin.zip
```

A successful download looks like:

```
Length: 9202456 (8.8M) [application/zip]
Saving to: 'apache-maven-3.9.9-bin.zip'
apache-maven-3.9.9-bin.zip  100% [=====>]  8.78M  54.1MB/s  in 0.2s
saved [9202456/9202456]
```

> The `-4` flag forces IPv4, which helps if your VM has IPv6 connectivity issues. The file is identical to the Apache-hosted version — same Maven 3.9.9, same ZIP archive, same installation layout.

Once downloaded, continue with the steps below and verify Maven works after installation:

```bash
/usr/local/maven3.9/bin/mvn -version
```

Expected output:

```
Apache Maven 3.9.9
Maven home: /usr/local/maven3.9
Java version: ...
```

---

### 2. Extract the Archive

```bash
unzip apache-maven-3.9.9-bin.zip
```

You should now have a folder called `apache-maven-3.9.9` in `/tmp/`.

---

### 3. Copy Maven to a Permanent Location

```bash
cp -r apache-maven-3.9.9 /usr/local/maven3.9
```

This places Maven at `/usr/local/maven3.9`. The Maven binary will later be called using its full path: `/usr/local/maven3.9/bin/mvn`.

---

### 4. Set the Maven Memory Option

The VM has limited memory. Without this setting, Maven may fail with an out-of-memory error. Set an environment variable to tell Maven it can use up to 512 MB:

```bash
export MAVEN_OPTS="-Xmx512m"
```

> **What this does:** `-Xmx512m` sets the maximum Java heap size to 512 MB. The VM may not physically have this much free, but this tells the JVM it is allowed to use up to that amount if needed. This prevents Maven from refusing to start due to its own conservative memory defaults.

## Stage 2: Clone and Configure the Source Code

### 5. Clone the Repository

Clone the vProfile project source code from GitHub, using the `local` branch:

```bash
git clone -b local https://github.com/hkhcoder/vprofile-project.git
```

> The `local` branch contains configuration intended for this local VM-based setup. Other branches (e.g. `main`) are used for cloud or container deployments.

---

### 6. Navigate Into the Project Directory

```bash
cd vprofile-project
```

> All remaining commands in this section must be run from inside this directory.

---

### 7. Review `application.properties`

This is the most critical configuration file in the project. It tells the vProfile application how to connect to every backend service in the stack:

```bash
vim src/main/resources/application.properties
```

The file contains entries like the following:

```properties
# JDBC Configuration for Database Connection
jdbc.driverClassName=com.mysql.cj.jdbc.Driver
jdbc.url=jdbc:mysql://db01:3306/accounts?useUnicode=true&characterEncoding=UTF-8&zeroDateTimeBehavior=convertToNull
jdbc.username=admin
jdbc.password=admin123

# Memcached Configuration — Active and Standby Host
# For Active Host
memcached.active.host=mc01
memcached.active.port=11211

# RabbitMQ
rabbitmq.address=rmq01
rabbitmq.port=5672
rabbitmq.username=test
rabbitmq.password=test
```

**JDBC URL parameters explained:**

| Parameter | Purpose |
|-----------|---------|
| `useUnicode=true` | Enables Unicode character support for the connection |
| `characterEncoding=UTF-8` | Sets character encoding to UTF-8, ensuring special characters are handled correctly |
| `zeroDateTimeBehavior=convertToNull` | Converts MySQL's zero date values (`0000-00-00`) to `null` instead of throwing an exception — important for MySQL/Java compatibility |

Note that Memcached supports an **active/standby** configuration. In this project only the active host (`mc01`) is configured; a standby host entry also exists in the file for high-availability setups.

**How hostname resolution works:** The hostnames `db01`, `mc01`, and `rmq01` are resolved to IP addresses using the `/etc/hosts` entries configured during VM setup. This is why verifying `/etc/hosts` was an early step on every VM.

**Important:** This file is **baked into the WAR artifact at build time**. If any backend credentials differ from what is in this file, the application will fail to connect. If you used different usernames, passwords, or database names during setup, update them here before building.

For this project with the default setup, **no changes are needed**. The values already match what was configured on each backend VM.

> Remember this file path — `src/main/resources/application.properties` — as it will be updated in later parts of the course for AWS, Docker, and Kubernetes deployments.

## Stage 3: Build and Deploy

### 8. Build the Source Code with Maven

From inside the `vprofile-project` directory, run:

```bash
/usr/local/maven3.9/bin/mvn install
```

**What this does:**

- Maven reads the project's `pom.xml` file to understand dependencies and build configuration
- Downloads any required libraries
- Compiles all Java source files
- Packages everything (including `application.properties`) into a single WAR file

This step takes several minutes. When complete, a new `target/` directory will appear.

Verify the artifact was created:

```bash
ls target/
```

You should see `vprofile-v2.war`. This is the deployable Java web application archive.

---

### 9. Stop Tomcat

Stop the Tomcat service before making changes to the webapps directory:

```bash
systemctl stop tomcat
```

---

### 10. Remove the Default Tomcat Application

Tomcat ships with a default `ROOT` application. Remove it so the vProfile app can take its place as the default:

```bash
rm -rf /usr/local/tomcat/webapps/ROOT*
```

> Naming the artifact `ROOT.war` makes it the **default application**, meaning it is served at the root URL (e.g. `http://app01:8080/`) rather than a sub-path.

---

### 11. Deploy the Artifact

Copy the built WAR file into Tomcat's `webapps` directory as `ROOT.war`:

```bash
cp target/vprofile-v2.war /usr/local/tomcat/webapps/ROOT.war
```

When Tomcat starts, it will automatically detect and extract `ROOT.war` into a `ROOT/` folder.

---

### 12. Start Tomcat

```bash
systemctl start tomcat
```

---

### 13. Fix Ownership

After Tomcat extracts the WAR, the resulting files may be owned by root. Reset ownership of the entire webapps directory to the `tomcat` user:

```bash
chown tomcat.tomcat /usr/local/tomcat/webapps -R
```

---

### 14. Restart Tomcat and Verify

```bash
systemctl restart tomcat
systemctl status tomcat
```

The output should show `active (running)`. Press `q` to exit.

Verify the deployment by checking that the `ROOT` folder now exists:

```bash
ls /usr/local/tomcat/webapps/
```

You should see both `ROOT.war` and a `ROOT/` directory (the extracted application).

## Key Concepts

| Concept | Explanation |
|---------|-------------|
| **Maven** | A Java build tool that compiles source code and packages it into a deployable artifact |
| **WAR file** | Web Application Archive — the Java equivalent of a zip file, containing a compiled web app |
| **`mvn install`** | Maven command that compiles, tests, and packages the project into a WAR file in `target/` |
| **`ROOT.war`** | Naming the artifact `ROOT.war` makes it Tomcat's default application, served at the root URL |
| **`application.properties`** | Config file baked into the artifact at build time — contains all backend connection details |
| **`MAVEN_OPTS`** | Environment variable used to pass JVM flags to Maven, such as memory limits |
