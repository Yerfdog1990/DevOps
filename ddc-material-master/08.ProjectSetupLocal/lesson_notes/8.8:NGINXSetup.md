# Nginx Setup 

## Overview

Nginx is the final service in the vProfile stack. It runs on `web01` and acts as a **reverse proxy**, sitting in front of the Tomcat application server. When a user accesses the application in a browser, the request hits Nginx on port 80 (standard HTTP), and Nginx forwards it to Tomcat on `app01:8080`. From the user's perspective, they only ever interact with Nginx — the Tomcat server is not directly exposed.

```
User (browser) → Nginx :80 (web01) → Tomcat :8080 (app01)
```

> Nginx runs on **Ubuntu**, not Rocky Linux. This means package management uses `apt` instead of `dnf`/`yum`, and the command behaviour is slightly different.

---

## A Note on `apt update` vs `apt upgrade`

Unlike on Rocky Linux where `dnf update` both checks for and applies updates in one step, Ubuntu separates this into two commands:

| Command | What it does |
|---------|-------------|
| `apt update` | Refreshes the package index — checks what updates are available. Makes **no changes** to installed software. |
| `apt upgrade` | Downloads and applies the available updates found by `apt update`. |

Both should be run in sequence before installing any software.

## Setup Steps

### 1. Log Into the Nginx VM

```bash
vagrant ssh web01
```

Then switch to the root user:

```bash
sudo -i
```

---

### 2. Verify `/etc/hosts` Entries

```bash
cat /etc/hosts
```

Ensure `app01` is present with its correct IP address. Nginx will use the hostname `app01` in the proxy configuration to forward traffic — if this entry is missing, the proxy will fail to connect.

---

### 3. Update the OS

Run both commands in sequence:

```bash
apt update
apt upgrade
```

> During the upgrade you may be prompted with interactive screens. Press `Space` to acknowledge, and use `Tab` to navigate to OK and press `Space` to confirm.

You can also chain them to run automatically without prompts:

```bash
apt update && apt upgrade -y
```

---

### 4. Install Nginx

```bash
apt install nginx -y
```

After installation, verify the directory structure Nginx uses for site configuration:

```bash
ls /etc/nginx/
```

You will see two relevant directories:

| Directory | Purpose |
|-----------|---------|
| `sites-available/` | Where you **define** site configuration files |
| `sites-enabled/` | Where you **activate** sites by placing links to files in `sites-available/` |

This two-directory pattern keeps inactive configurations saved without loading them into Nginx.

---

### 5. Create the Nginx Configuration File

Create a new site configuration file:

```bash
vi /etc/nginx/sites-available/vproapp
```

Enter insert mode (`i`) and paste the following content exactly:

```nginx
upstream vproapp {
    server app01:8080;
}

server {
    listen 80;
    location / {
        proxy_pass http://vproapp;
    }
}
```

Save and exit: press `Esc`, then type `:wq` and press `Enter`.

**How this configuration works:**

The file has two blocks:

**`upstream vproapp`** — defines a named backend group called `vproapp`. It contains one server: `app01:8080`. In a load-balanced setup (covered in the AWS section of the course), multiple servers can be listed here and Nginx will distribute traffic between them.

**`server`** — defines how Nginx handles incoming requests:

- `listen 80` — Nginx listens for HTTP traffic on port 80
- `location /` — matches all requests to the root path and beyond
- `proxy_pass http://vproapp` — forwards matched requests to the `vproapp` upstream group, which resolves to `app01:8080`

So the complete request flow is: browser hits `web01:80` → Nginx receives it → forwards to `app01:8080` → Tomcat handles it and returns the response.

---

### 6. Remove the Default Nginx Site

Nginx ships with a default site enabled in `sites-enabled`. Remove it so it does not conflict with the vproapp configuration:

```bash
rm -rf /etc/nginx/sites-enabled/default
```

---

### 7. Enable the vproapp Site

Create a symbolic link from `sites-available/vproapp` into `sites-enabled/`. This is how Nginx activates a site:

```bash
ln -s /etc/nginx/sites-available/vproapp /etc/nginx/sites-enabled/vproapp
```

> Nginx reads everything in `sites-enabled/` when it starts. The symbolic link means the actual file stays in `sites-available/` while `sites-enabled/` just points to it. To disable a site, you delete the link — the original file remains untouched.

---

### 8. Restart Nginx

```bash
systemctl restart nginx
```

If the restart succeeds silently, the configuration is valid and Nginx is running. If it fails, check the status for errors:

```bash
systemctl status nginx
```

> The most common cause of a failed restart is a copy-paste error in the configuration file. If you see an error, open the file again (`vi /etc/nginx/sites-available/vproapp`), compare it carefully against the content in Step 5, fix any issues, and retry.

## Key Concepts

| Concept | Explanation |
|---------|-------------|
| **Reverse proxy** | A server that receives client requests and forwards them to a backend server on the client's behalf |
| **Upstream block** | Nginx's way of defining a named group of backend servers; enables load balancing when multiple servers are listed |
| **`proxy_pass`** | Nginx directive that forwards the request to the specified upstream |
| **`sites-available`** | Holds all defined site configs — active or not |
| **`sites-enabled`** | Holds symbolic links to active configs; only these are loaded by Nginx |
| **Symbolic link (`ln -s`)** | A pointer to another file; used here to activate a site without duplicating its config file |

| Port | Protocol | Service | Purpose |
|------|----------|---------|---------|
| 80 | TCP | Nginx | Receives incoming HTTP requests from users |
| 8080 | TCP | Tomcat | Receives forwarded requests from Nginx |

## Post-Setup Verification Checks

Run these three checks to confirm Nginx is fully operational end-to-end before testing in the browser.

### 1. Confirm Nginx Is Listening on Port 80

```bash
ss -tulpn | grep nginx
```

Expected output:

```
LISTEN  0  511  0.0.0.0:80  0.0.0.0:*  users:(("nginx",...))
```

This confirms Nginx is bound to port 80 and accepting connections on all interfaces.

---

### 2. Confirm `web01` Can Resolve `app01`

The Nginx proxy config uses the hostname `app01` — if `web01` cannot resolve it, the proxy will fail. Verify with either:

```bash
ping app01
```

or:

```bash
getent hosts app01
```

Expected output:

```
192.168.56.12   app01
```

If this fails, check `/etc/hosts` on `web01` and add the missing entry.

---

### 3. Test the Reverse Proxy from Inside `web01`

```bash
curl localhost
```

**Possible outcomes:**

| Result | Meaning |
|--------|---------|
| Application HTML returned | Nginx is working and successfully reaching Tomcat on `app01` ✅ |
| `502 Bad Gateway` | Nginx is working but cannot reach `app01:8080` — check that Tomcat is running on `app01` |
| Connection refused | Nginx itself is not listening — re-check the restart and status steps |

If you get a `502 Bad Gateway`, the issue is not Nginx — it means Nginx is correctly forwarding requests but Tomcat on `app01` is not ready or not reachable. Verify Tomcat status on `app01`:

```bash
vagrant ssh app01
sudo -i
systemctl status tomcat
```

### Complete Traffic Flow

Once all checks pass, the full end-to-end request path is confirmed:

```
Browser → web01:80 → Nginx → app01:8080 → Tomcat → vProfile Application
                                                   ↕           ↕           ↕
                                                 db01        mc01        rmq01
```

The stack is fully set up and ready for browser validation.
