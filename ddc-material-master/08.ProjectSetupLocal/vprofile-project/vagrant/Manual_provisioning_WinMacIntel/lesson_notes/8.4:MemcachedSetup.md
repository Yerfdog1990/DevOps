# Memcached Setup 
## Overview

Memcached is an in-memory caching layer used in the vProfile stack to cache database query results. It runs on its own VM (`mc01`) and is accessed remotely by the Tomcat application server. The key configuration task is ensuring Memcached listens on all network interfaces (not just localhost) so that remote services can connect to it.

---

## Why Remote Listening Matters

By default, most services — including Memcached — are configured to listen **only on the local loopback address** (`127.0.0.1`) for security reasons. This means they reject any incoming connection from another machine.

In a multi-VM stack like vProfile, Tomcat runs on a separate server and needs to reach Memcached over the network. If Memcached is still bound to `127.0.0.1`, Tomcat will fail to connect even if:

- The Memcached service is running
- The network between VMs is functional
- Firewall rules are correct

The fix is to change the bind address to `0.0.0.0`, which means **listen on all IPv4 interfaces**.

> **Debugging tip:** If a service can't connect to a remote service despite everything appearing fine, always check whether the remote service is configured to accept connections from non-local IPs.

## Setup Steps

### 1. Log Into the Memcached VM

```bash
vagrant ssh mc01
```

Then switch to the root user:

```bash
sudo -i
```

---

### 2. Verify `/etc/hosts` Entries

Ensure all VMs in the stack are resolvable by hostname. Check the hosts file:

```bash
cat /etc/hosts
```

If any entries are missing, add them manually with the correct IP addresses and hostnames for each VM in the stack.

---

### 3. Update the OS

Apply the latest patches before installing any software:

```bash
yum update -y
```

> This step is optional for lab/project environments but is good practice. It can be skipped without affecting the project setup.

---

### 4. Install Memcached

First install the EPEL repository (required to get the Memcached package), then install Memcached itself:

```bash
sudo dnf install epel-release -y
sudo dnf install memcached -y
```

---

### 5. Start and Enable the Memcached Service

Start the service immediately and enable it to start automatically on boot:

```bash
sudo systemctl start memcached
sudo systemctl enable memcached
```

Verify the service is running:

```bash
sudo systemctl status memcached
```

---

### 6. Configure Memcached to Accept Remote Connections

By default, Memcached binds to `127.0.0.1` (localhost only). Use `sed` to replace this with `0.0.0.0` in the configuration file:

```bash
sed -i 's/127.0.0.1/0.0.0.0/g' /etc/sysconfig/memcached
```

**What this does:**
- Opens `/etc/sysconfig/memcached`
- Finds the line: `OPTIONS="-l 127.0.0.1"`
- Replaces it with: `OPTIONS="-l 0.0.0.0"`

`0.0.0.0` tells Memcached to listen on **all available IPv4 interfaces**, allowing remote machines (like the Tomcat server) to connect.

You can verify the change by viewing the file:

```bash
cat /etc/sysconfig/memcached
```

---

### 7. Restart Memcached

After any configuration change, the service must be restarted for the new settings to take effect:

```bash
sudo systemctl restart memcached
```

> **Rule of thumb:** Whenever you edit a service's configuration file, always restart that service.

---

### 8. Configure the Firewall

Open the required ports so that other VMs can reach Memcached:

```bash
# Allow TCP port 11211 (standard Memcached port)
firewall-cmd --add-port=11211/tcp
firewall-cmd --runtime-to-permanent

# Allow UDP port 11111
firewall-cmd --add-port=11111/udp
firewall-cmd --runtime-to-permanent
```

---

### 9. Start Memcached as a Daemon

Run Memcached explicitly with the configured ports, binding it to the `memcached` user and starting it in the background as a daemon:

```bash
sudo memcached -p 11211 -U 11111 -u memcached -d
```

**Flag breakdown:**

| Flag | Meaning |
|------|---------|
| `-p 11211` | Listen on TCP port 11211 |
| `-U 11111` | Listen on UDP port 11111 |
| `-u memcached` | Run as the `memcached` system user |
| `-d` | Run as a background daemon |

## Troubleshooting: SELinux Blocking Firewall Commands

On Rocky Linux systems with SELinux in **Enforcing** mode, you may encounter a permission denial when running `firewall-cmd --runtime-to-permanent`. This is commonly caused by an incorrect SELinux security context on files inside `/etc/sysconfig/network-scripts/`.

---

### Understanding the Root Cause

SELinux uses **security context labels** to decide which processes can access which files. Each file has a label like:

```
user:role:type:level
```

The `type` field is the most important for access control. Network configuration files should carry the type `net_conf_t`. If a file was created or copied in a way that gave it the wrong type — such as `user_tmp_t` (meant for temporary user files) — then `firewalld` cannot access or modify it, and the command fails.

**Example of wrong label:**
```
unconfined_u:object_r:user_tmp_t:s0
```

**Correct label:**
```
unconfined_u:object_r:net_conf_t:s0
```

---

### Fix: Restore Correct SELinux Contexts

Run `restorecon` to reset all files in the network-scripts directory back to their correct SELinux labels:

```bash
restorecon -Rv /etc/sysconfig/network-scripts/
```

You should see output similar to:

```
Relabeled /etc/sysconfig/network-scripts/ifcfg-eth1
  from unconfined_u:object_r:user_tmp_t:s0
  to   unconfined_u:object_r:net_conf_t:s0
```

Then retry the firewall command:

```bash
firewall-cmd --runtime-to-permanent
```

It should now return `success`.

---

### If It Still Fails: Isolate SELinux as the Cause

Temporarily set SELinux to permissive mode (it logs violations but does not block them):

```bash
setenforce 0
```

Retry:

```bash
firewall-cmd --runtime-to-permanent
```

If it succeeds now, SELinux was definitely the cause. Re-enable enforcing mode immediately after:

```bash
setenforce 1
```

> **Note:** `setenforce 0` is only for diagnosing the issue. Do not leave SELinux in permissive mode in production environments.

---

### Recommended Alternative: Use `--permanent` Flag Instead

Rather than adding a runtime rule and then converting it with `--runtime-to-permanent`, the cleaner and more standard approach on Rocky Linux is to write the permanent rule directly:

```bash
firewall-cmd --permanent --add-port=11211/tcp
firewall-cmd --reload
```

Then verify the port is open:

```bash
firewall-cmd --list-ports
```

Expected output:

```
11211/tcp
```

This approach avoids the SELinux issue with `--runtime-to-permanent` entirely and is the recommended administrative method.

## Verifying a Successful Setup

Once the firewall is configured and Memcached is running, verify everything with the following checks.

### 1. Check the Memcached Service

```bash
systemctl status memcached
```

The service should show as `active (running)`.

### 2. Verify the Firewall Port

```bash
firewall-cmd --list-ports
```

Expected output:

```
11211/tcp
```

### 3. Verify Memcached Is Listening

```bash
ss -tulpn | grep 11211
```

Expected output:

```
tcp  LISTEN  0  1024  0.0.0.0:11211  0.0.0.0:*  users:(("memcached",pid=XXXXX,fd=26))
```

This confirms:

- Memcached started successfully
- It is listening on port `11211`
- It is accepting connections on **all network interfaces** (`0.0.0.0`), including `127.0.0.1`, `10.0.2.15`, and `192.168.56.14`

### 4. Test Connectivity

From the same VM, send a quick stats request via netcat:

```bash
echo stats | nc 127.0.0.1 11211
```

You should see Memcached statistics printed in the terminal, confirming the service is responding correctly.

## Security Considerations

Binding Memcached to `0.0.0.0` exposes it on all interfaces. This is acceptable in a development or lab environment, but in production it poses serious risks:

- Memcached has **no authentication** by default
- An exposed Memcached port can be abused in **UDP amplification DDoS attacks**
- It should never be reachable from untrusted networks

### Option 1: Bind to Localhost Only (Safest)

If only local applications on the same VM use Memcached:

```bash
sudo vi /etc/sysconfig/memcached
```

Set:

```
OPTIONS="-l 127.0.0.1"
```

Then restart:

```bash
sudo systemctl restart memcached
```

Verify:

```bash
ss -tulpn | grep 11211
# Expected: tcp LISTEN 0 1024 127.0.0.1:11211
```

### Option 2: Bind to a Specific Private Interface

If another VM needs remote access (e.g., the Tomcat server), bind to only the private network interface instead of all interfaces:

```bash
OPTIONS="-l 192.168.56.14"
```

This limits exposure compared to `0.0.0.0` while still allowing the necessary remote connection.
