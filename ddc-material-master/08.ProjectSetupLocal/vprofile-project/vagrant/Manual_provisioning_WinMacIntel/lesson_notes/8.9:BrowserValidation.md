# Browser Validation 

## Overview

With all five services configured and running, the final step is to validate the complete stack through the browser. This confirms that every service is connected and working end-to-end — not just running in isolation on its own VM.

The validation covers five services in sequence:

| Step | Service Tested |
|------|---------------|
| Page loads | Nginx + Tomcat |
| Login succeeds | MySQL (database) |
| RabbitMQ button | RabbitMQ |
| All Users list | MySQL (read) |
| Cached user data | Memcached |

---

## Step 1: Get the web01 IP Address

Check the `Vagrantfile` for the IP address assigned to `web01`. From your project directory on your host machine, run:

```bash
cat Vagrantfile
```

Look for the `web01` VM definition block:

```ruby
### Nginx VM ###
  config.vm.define "web01" do |web01|
    web01.vm.box = "ubuntu/jammy64"
    web01.vm.hostname = "web01"
    web01.vm.network "private_network", ip: "192.168.56.11"
    web01.vm.provider "virtualbox" do |vb|
      vb.memory = "800"
    end
  end
```

The IP address is on the `private_network` line: `192.168.56.11`.

For reference, the full VM IP map for this project is:

| VM | Service | IP Address |
|----|---------|------------|
| `web01` | Nginx | `192.168.56.11` |
| `app01` | Tomcat | `192.168.56.12` |
| `rmq01` | RabbitMQ | `192.168.56.13` |
| `mc01` | Memcached | `192.168.56.14` |
| `db01` | MySQL | `192.168.56.15` |

These IPs are what populate the `/etc/hosts` entries on each VM, allowing hostnames like `db01`, `mc01`, and `rmq01` to resolve correctly across the stack.

## Step 2: Access the Application in the Browser

Open a browser and enter the IP address:

```
http://192.168.56.11
```

You do not need to specify port 80 — browsers default to port 80 for `http://`. The following are all equivalent:

```
192.168.56.11
http://192.168.56.11
http://192.168.56.11:80
```

> For reference: `http://` defaults to port **80**, and `https://` defaults to port **443**.

**What a successful page load validates:**

- Nginx on `web01` received the request on port 80
- Nginx successfully forwarded it to Tomcat on `app01:8080`
- Tomcat is running and serving the vProfile application

If the page does not load, refer to the post-setup verification steps in the Nginx setup notes (`curl localhost`, `ping app01`, `ss -tulpn | grep nginx`).

---

## Step 3: Log In — Validates MySQL

On the login page, enter:

| Field | Value |
|-------|-------|
| Username | `admin_vp` |
| Password | `admin_vp` |

These credentials are stored in the `accounts` database on `db01`, loaded during MySQL setup via the DB dump file.

**What a successful login validates:**

- The vProfile application can connect to MySQL on `db01:3306`
- The database schema and user data were correctly imported
- The credentials in `application.properties` match those configured on `db01`

If login fails, verify the MySQL service is running on `db01` and that the `admin` database user and `accounts` schema were set up correctly.

---

## Step 4: Test RabbitMQ Connectivity

After logging in as `admin_vp`, a **RabbitMQ** button is available in the admin section. Click it.

If the connection is successful, a confirmation message will appear showing the queue connection was established.

**What this validates:**

- The application can connect to RabbitMQ on `rmq01:5672`
- The `test` user credentials in `application.properties` are correct
- Port 5672 is open and reachable from `app01`

If the message does not appear, check that the RabbitMQ service is running on `rmq01` and that the firewall allows port 5672.

---

## Step 5: Test Memcached — Database Read and Cache

### First click — data from database

Click **All Users** to load a list of all users from the MySQL database. Then click on any individual user (e.g. *Aejaaz Habeeb*).

You should see a message:

```
Data is from DB
Data is inserted in cache
```

This confirms the application read the user record from MySQL and stored it in Memcached.

### Second click — data from cache

Click **Back**, then click the **same user** again.

The page loads noticeably faster, and the message changes to indicate the data came from cache rather than the database.

**What this validates:**

- The application can connect to Memcached on `mc01:11211`
- Memcached is correctly storing and retrieving cached data
- The caching layer is functioning as designed — repeated reads hit the cache, not the database

## Full Validation Summary

| Service | How Validated | Expected Result |
|---------|--------------|----------------|

| **MySQL** | Login with `admin_vp` / `admin_vp` | Successfully logged in |

## Tearing Down the Stack

Once validation is complete, the VMs can be destroyed. They will be rebuilt automatically in the next stage of the course:

```bash
vagrant destroy --force
```

This removes all five VMs. The `--force` flag skips the confirmation prompt for each VM.

> Do not worry about losing the setup — the next stage of the course covers **automated provisioning**, where the entire stack is brought up without manually executing a single setup command.
