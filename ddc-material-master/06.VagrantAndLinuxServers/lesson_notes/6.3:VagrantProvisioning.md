# Vagrant Provisioning

---

## 1. What Is Provisioning?

Provisioning means automatically executing commands inside a VM when it boots. It is also called **bootstrapping** — setting up a system without manual intervention.

In Vagrant, provisioning typically runs on the **first boot**, when the VM is created for the first time with `vagrant up`. Common uses include:

- Installing packages and dependencies
- Starting and enabling services
- Creating directories and config files
- Running setup or deployment scripts
- Capturing system info to log files

---

## 2. The Shell Provisioner

The most common provisioner type is `shell`, which runs bash commands directly inside the VM as root.

### Syntax

```ruby
config.vm.provision "shell", inline: <<-SHELL
  # Your shell commands go here
SHELL
```

| Part | Meaning |
|------|---------|
| `"shell"` | The provisioner type — tells Vagrant to use the shell |
| `inline:` | Commands are written directly in the Vagrantfile (not in a separate script file) |
| `<<-SHELL ... SHELL` | A Ruby heredoc — everything between these markers is passed as input to the shell |

Commands run with **root privileges** inside the VM. Output can be redirected to files using `>` for later inspection.

### Minimal Example (Ubuntu/Debian) — Line by Line

```ruby
config.vm.provision "shell", inline: <<-SHELL
  apt-get update
  apt-get install -y apache2
SHELL
```

| Line | What it does |
|------|-------------|
| `config.vm.provision "shell"` | Tells Vagrant to use the shell provisioner to run commands inside the VM |
| `inline: <<-SHELL` | Specifies that commands are written directly here in the Vagrantfile, not in a separate script file |
| `apt-get update` | Updates the package list on Ubuntu/Debian so the latest versions are available |
| `apt-get install -y apache2` | Installs the Apache web server; `-y` automatically answers "yes" to any prompts |
| `SHELL` | Closes the heredoc block that opened with `<<-SHELL` |

**Purpose:** Automates Apache installation so the VM boots with the web server already installed — no manual steps needed every time.

### Extended Example (CentOS/RHEL)

```ruby
config.vm.provision "shell", inline: <<-SHELL
  yum install -y httpd wget unzip
  mkdir -p /opt/devops
  free -m > /opt/devops/memory.txt
  df -h  > /opt/devops/disk.txt
  systemctl start httpd
  systemctl enable httpd
  systemctl stop firewalld
  systemctl disable firewalld
SHELL
```

This example installs Apache, captures memory and disk info to files, starts the web server, and disables the firewall.

> **Note:** Use `apt-get` for Ubuntu/Debian boxes and `yum`/`dnf` for CentOS/RHEL boxes — the package manager must match your box OS.

---

This is a Vagrant shell provisioner block that automatically installs and configures Apache (`httpd`) inside your Linux VM when the VM is created or provisioned.

```ruby
config.vm.provision "shell", inline: <<-SHELL
  yum install -y httpd
  systemctl start httpd
  systemctl enable httpd
  systemctl stop firewalld
  systemctl disable firewalld
SHELL
end
```

### Explanation of each line

#### 1. Install Apache web server

```bash
yum install -y httpd
```

* `yum` → Package manager used in CentOS/RHEL.
* `install` → Installs a package.
* `-y` → Automatically answers “yes” to prompts.
* `httpd` → Apache web server package.

This installs the Apache web server inside the VM.

---

#### 2. Start Apache service

```bash
systemctl start httpd
```

* `systemctl` → Manages system services.
* `start` → Starts the service immediately.
* `httpd` → Apache service name.

This makes the web server begin running right away.

---

#### 3. Enable Apache at boot

```bash
systemctl enable httpd
```

This ensures Apache automatically starts whenever the VM boots.

Without this, the service would stop after reboot.

---

#### 4. Stop firewall service

```bash
systemctl stop firewalld
```

Stops the Linux firewall immediately.

This is commonly done in beginner labs so port 80 (HTTP) becomes accessible without configuring firewall rules.

---

#### 5. Disable firewall permanently

```bash
systemctl disable firewalld
```

Prevents the firewall from starting automatically after reboot.

---

## What this achieves

After `vagrant up`, your VM will:

* Have Apache installed
* Run a web server automatically
* Keep Apache enabled after reboot
* Disable the firewall so the website is reachable

## Typical full Vagrant example

```ruby
Vagrant.configure("2") do |config|

  config.vm.box = "centos/7"

  config.vm.network "private_network", ip: "192.168.33.10"

  config.vm.provision "shell", inline: <<-SHELL
    yum install -y httpd
    systemctl start httpd
    systemctl enable httpd
    systemctl stop firewalld
    systemctl disable firewalld
  SHELL

end
```

You could then access the website from your host machine using:

```text
http://192.168.33.10
```

---

## Important note

Disabling the firewall is okay for learning environments, but in real production systems you usually keep the firewall enabled and open only required ports, for example:

```bash
firewall-cmd --permanent --add-service=http
firewall-cmd --reload
```

instead of disabling it completely.

## 3. When Provisioning Runs

This is the most important thing to understand about provisioning — it does **not** run every time the VM starts.

| Command | Does provisioning run? |
|---------|----------------------|
| `vagrant up` on a **new, uncreated** VM | ✅ Yes — always |
| `vagrant up` on an existing (halted) VM | ❌ No |
| `vagrant reload` on an existing VM | ❌ No |
| `vagrant provision` | ✅ Yes — forces it on a running VM |
| `vagrant reload --provision` | ✅ Yes — reboots and runs provisioning |
| `vagrant up --provision` | ✅ Yes — starts and runs provisioning |

> If you add new commands to the provisioning block after the VM already exists, a plain `vagrant reload` will **not** run them. You must use one of the explicit provisioning commands below.

---

## 4. Running Provisioning on an Existing VM

### Run without rebooting

```bash
vagrant provision
```

Executes the provisioning block on the currently running VM. Useful for applying new commands without a full reboot.

### Run with a reboot

```bash
vagrant reload --provision
```

Reboots the VM and then runs the provisioning block. Use this when your new commands depend on a clean boot state.

### Run on first start (force)

```bash
vagrant up --provision
```

Starts a halted VM and forces the provisioning block to run, even though the VM already exists.

## 5. Practical Example — Web Server Setup

The following Vagrantfile provisions a CentOS VM with Apache running, accessible from your browser via a static IP.

```ruby
Vagrant.configure("2") do |config|
  config.vm.box = "eurolinux-vagrant/centos-stream-9"
  config.vm.network "private_network", ip: "192.168.56.15"
  config.vm.network "public_network"

  config.vm.provision "shell", inline: <<-SHELL
    yum install -y httpd wget unzip
    systemctl start httpd
    systemctl enable httpd
    systemctl stop firewalld
    systemctl disable firewalld
  SHELL
end
```

**Steps:**

1. Save the Vagrantfile
2. Run `vagrant up` — Vagrant creates the VM and immediately runs the provisioning commands
3. Watch the terminal output — you'll see each command execute in sequence
4. Open a browser and go to `http://192.168.56.15` — the default Apache page confirms the server is running

## 6. Verifying Provisioning Output Inside the VM

If you redirect command output to files during provisioning, SSH in after boot to inspect them:

```bash
vagrant ssh
sudo -i

cat /opt/devops/memory.txt   # RAM info captured at provisioning time
cat /opt/devops/disk.txt     # Disk info captured at provisioning time
```

## 7. Other Provisioner Types

`shell` is the most common provisioner, but Vagrant supports others for more advanced configuration management:

| Provisioner | Description |
|-------------|-------------|
| `shell` | Runs bash commands inline or from a script file |
| `ansible` | Runs an Ansible playbook |
| `puppet` | Applies a Puppet manifest |
| `chef_solo` | Runs a Chef cookbook |
| `docker` | Pulls images and runs containers |

For DevOps workflows, `shell` is sufficient for most basic setups. Ansible and Puppet become useful when managing many VMs with complex configurations.

## 8. Using GitHub Copilot to Understand Provisioning Blocks

If you're unsure what a provisioning block does, select the whole block in VS Code and use:

- `Ctrl + I` (Windows) / `Cmd + I` (macOS) → type `/explain` → Enter

Copilot will describe what each command does in plain English — useful for understanding unfamiliar package names or `systemctl` flags.

To generate a provisioning block, open the Copilot chat and describe what you need:

```
and disables the firewall on a CentOS VM.
```

Always review the output — verify the package manager matches your box (`yum` for CentOS/RHEL, `apt-get` for Ubuntu/Debian).

## 9. Quick Reference

| Command | Effect |
|---------|--------|
| `vagrant up` | Creates VM and runs provisioning (first time only) |
| `vagrant provision` | Re-runs provisioning on a running VM |
| `vagrant reload --provision` | Reboots VM and re-runs provisioning |
| `vagrant up --provision` | Starts a halted VM and forces provisioning |
| `vagrant validate` | Checks Vagrantfile syntax before running |

### Key Rules

1. Provisioning runs **automatically only on the first `vagrant up`** — when the VM is brand new.
2. Adding commands to the block and running `vagrant reload` alone will **not** execute them — use `vagrant provision` or `--provision`.
3. All provisioning commands run as **root** inside the VM.
4. The provisioner type `"shell"` with `inline:` keeps everything in one file — no external scripts needed.
5. Always match the package manager to your box: `yum`/`dnf` for CentOS/RHEL, `apt-get` for Ubuntu/Debian.
6. Save the Vagrantfile before running any `vagrant` command — unsaved changes are invisible to Vagrant.
