# Infrastructure as Code – Automating Website Deployment with Vagrant Provisioning

---

## 1. What Is Infrastructure as Code (IaC)?

Infrastructure as Code means defining your entire server setup — the OS, services, configuration, and deployed content — in a single file that can be run anywhere, any time, to reproduce the exact same environment automatically.

In this context, the **Vagrantfile** is the code. Everything done manually in previous lectures (installing packages, starting services, downloading templates) is written into the provisioning block once and executed automatically every time the VM is created.

**Benefits:**
- No manual steps — one command creates a fully configured server
- **Reusability** — the same file can provision the same environment on any machine
- **Consistency** — eliminates human error from repeated manual setup
- **Portability** — the scripts can be reused later on cloud platforms like AWS

> The rule: **automate only what you can already do manually**. You must understand each step before scripting it, because if provisioning fails you need to know where to look.

## 2. Setting Up the Project (Finance Website)

### Copy and Rename the Existing Project Folder

Rather than starting from scratch, copy the existing `deploy_website` Vagrantfile folder and rename the copy:

1. Open VS Code and open your `vagrant-vms` folder (`File → Open Folder`)
2. Right-click the `deploy_website` folder → **Copy**
3. Right-click in the explorer pane → **Paste**
4. Right-click the pasted copy → **Rename** → `deploy_website_IAC`

> **IAC** = Infrastructure as Code. The folder name signals that everything is defined in code.

### Clean Up the Copied Folder

If a `.vagrant` folder exists inside `financeIAC`, delete it — it contains the previous VM's state and will cause conflicts:

```
deploy_website_IAC/
├── Vagrantfile    ← keep this
└── .vagrant/      ← delete this entire folder
```

## 3. Writing the Vagrantfile

Open the Vagrantfile in `deploy_website_IAC`. Two things to update before adding provisioning:

### 3.1 Change the IP Address

The copied Vagrantfile will have the same IP as the original. Change it to avoid a collision with any other running VM:

```ruby
config.vm.network "private_network", ip: "192.168.33.41"
```

### 3.2 Uncomment the Provisioning Block

Scroll to the bottom of the Vagrantfile and uncomment the provisioning lines (remove the `#` from each line). Then add all the setup commands inside the block.

### 3.3 The Complete Vagrantfile

```ruby
Vagrant.configure("2") do |config|
  config.vm.box = "eurolinux-vagrant/centos-stream-9"
  config.vm.network "private_network", ip: "192.168.33.41"
  config.vm.network "public_network"

  config.vm.provider "virtualbox" do |vb|
    vb.memory = 1024
  end

  config.vm.provision "shell", inline: <<-SHELL
    # Install dependencies
    yum install -y httpd wget unzip vim

    # Start and enable Apache
    systemctl start httpd
    systemctl enable httpd

    # Download the website template
    mkdir -p /tmp/finance
    cd /tmp/finance
    wget https://www.tooplate.com/zip-templates/2135_mini_finance.zip
    unzip -o 2135_mini_finance.zip

    # Deploy to web root
    cp -r 2135_mini_finance/* /var/www/html/

    # Restart Apache to serve new content
    systemctl restart httpd

    # Clean up temporary files
    cd /tmp
    rm -rf /tmp/finance
  SHELL
end
```

## 4. Key Points About the Provisioning Commands

### Always Use `-y` on Install Commands

```bash
yum install -y httpd wget unzip vim
```

Without `-y`, the package manager will prompt for confirmation — this pauses and breaks automated provisioning. Always include `-y` to auto-confirm.

### Use `-p` When Creating Directories

```bash
mkdir -p /tmp/finance
```

`-p` means: create the directory if it doesn't exist, and don't fail if it already does. This makes the script safe to run multiple times.

### Use `-o` When Unzipping

```bash
unzip -o 2135_mini_finance.zip
```

`-o` means: overwrite existing files without asking. Without it, `unzip` will prompt for confirmation if files already exist — which breaks unattended provisioning.

### Clean Up From Outside the Target Directory

```bash
cd /tmp
rm -rf /tmp/finance
```

You cannot delete a directory while you are inside it. Always `cd` out first, then delete. This is the same principle as not cutting the branch of a tree while sitting on it.

### Get the Download URL From DevTools

The direct `.zip` download URL from tooplate.com must be retrieved via the browser's DevTools (F12 → Network tab → click Download → check Headers → copy the Request URL). The link on the page itself is not always a direct download link.

## 5. Running the Automated Setup

```bash
cd /f/vagrant-vms/deploy_website_IAC
vagrant up
```

Vagrant will:
1. Create the VM from the box
2. Apply network and hardware settings
3. Run all provisioning commands automatically in sequence

Watch the terminal output — each command's output will appear as it runs. The unzip step produces visible output; the copy and restart steps run silently.

If provisioning fails:
- **Syntax error** — the shell block will error immediately; check for typos in the Vagrantfile
- **Logical error** — provisioning completes but the website doesn't load; check each command manually by SSHing into the VM

### Test It

```bash
vagrant ssh
ip addr show   # Note the 192.x.x.x IP
```

Open [http://192.168.33.41](http://192.168.33.41) in your browser. The finance website should load automatically — no manual steps taken.

## 6. The Value of IaC — Reusability

```bash
vagrant destroy   # Delete the VM entirely
vagrant up        # Recreate it — fully provisioned website in minutes
```

The Vagrantfile is the asset, not the VM. As long as you keep the file, you can recreate the exact same environment anywhere, any time — on your laptop, a colleague's machine, or a cloud server.

> The provisioning commands written here are also directly reusable on cloud platforms like AWS. The same shell script that provisions the VM locally can provision a cloud instance with minimal changes.

## 7. Applying the Same Approach to WordPress

The exact same pattern applies to the WordPress/Ubuntu setup from the previous lecture. Create a new folder (e.g. `WordPressIAC`), copy the WordPress Vagrantfile, change the IP, and move every manual command from those steps into the provisioning block.

The provisioning block for WordPress would include, in order:

1. `apt update` and `apt install` for all LAMP dependencies
2. Create `/srv/www`, set ownership, download and extract WordPress
3. Create and write `/etc/apache2/sites-available/wordpress.conf`
4. `a2ensite`, `a2enmod rewrite`, `a2dissite 000-default`, `service apache2 reload`
5. MySQL database creation and user setup queries
6. Copy `wp-config-sample.php` to `wp-config.php`
7. `sed` commands to inject database name, username, and password
8. Replace salt keys

> The WordPress provisioning is more complex because it involves multi-line config file creation and database queries inside the shell script. These require careful syntax but follow exactly the same logic as the manual steps.

## 8. Summary

| Concept | Meaning |
|---------|---------|
| Infrastructure as Code | Server setup defined entirely in a text file — repeatable and version-controllable |
| Provisioning | Shell commands that run automatically on first `vagrant up` |
| Reusability | Same Vagrantfile recreates the same environment anywhere |
| `-y` flag | Auto-confirms package install prompts — required for unattended provisioning |
| `-p` flag | Safe directory creation — no error if directory already exists |
| `-o` flag | Safe unzip — overwrites without prompting |
| `cd` before `rm -rf` | You cannot delete a directory while inside it — always exit first |

### Key Rules

1. **Automate only what you understand manually** — if provisioning fails, you need to know which step broke and why.
2. Every command in the provisioning block must be **non-interactive** — no prompts, no confirmations.
3. **Save the Vagrantfile** before running `vagrant up` — unsaved changes are invisible to Vagrant.
4. The `.vagrant` folder contains VM state — delete it when copying a project to avoid conflicts.
5. Keep your Vagrantfiles — the VM is disposable, the code is the asset.
