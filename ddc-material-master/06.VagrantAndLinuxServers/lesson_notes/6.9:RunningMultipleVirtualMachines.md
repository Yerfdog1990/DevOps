# Running Multiple Virtual Machines with a Single Vagrantfile

---

## 1. Why Multi-VM?

In previous lectures, each VM lived in its own folder with its own Vagrantfile — one folder, one VM. Managing multiple VMs this way means switching between directories and running separate commands for each one.

A **Multi-VM Vagrantfile** solves this by defining multiple VMs in a single file, managed together from one location. This is particularly useful for application stacks where different services run on separate VMs but form one working system:

| VM | Role |
|----|------|
| `web01`, `web02` | Frontend / application servers |
| `db01` | Database server |

All three must run together for the application to work — a multi-VM Vagrantfile keeps them under one roof.

---

## 2. Multi-VM Vagrantfile Structure

The key difference from a single-VM Vagrantfile is `config.vm.define`, which creates a named block for each VM. Each block uses a local variable matching the VM name to prefix all its settings.

```ruby
Vagrant.configure("2") do |config|

  config.vm.define "web01" do |web01|
    web01.vm.box      = "ubuntu/focal64"
    web01.vm.hostname = "web01"
    web01.vm.network "private_network", ip: "192.168.56.41"
  end

  config.vm.define "web02" do |web02|
    web02.vm.box      = "ubuntu/focal64"
    web02.vm.hostname = "web02"
    web02.vm.network "private_network", ip: "192.168.56.42"
  end

  config.vm.define "db01" do |db01|
    db01.vm.box      = "eurolinux-vagrant/centos-stream-9"
    db01.vm.hostname = "db01"
    db01.vm.network "private_network", ip: "192.168.56.43"

    db01.vm.provision "shell", inline: <<-SHELL
      yum install -y wget unzip mariadb-server
      systemctl start mariadb
      systemctl enable mariadb
    SHELL
  end

end
```

### How the Naming Works

Whatever word appears between the pipe symbols (`| |`) in `do |name|` becomes the prefix for every setting inside that block:

```ruby
config.vm.define "web01" do |web01|
  web01.vm.box      = "ubuntu/focal64"   # prefix: web01
  web01.vm.hostname = "web01"
  web01.vm.network  "private_network", ip: "192.168.56.41"
end
```

> For programmers: this is a class object pattern. For non-programmers: whatever is in the pipes — use that word to start every line inside the block.

### IP Addresses Must Be Unique

Every VM on the same network must have a different IP address. The network portion (`192.168.56`) is shared — only the last octet changes:

```
192.168.56.41  ← web01
192.168.56.42  ← web02
192.168.56.43  ← db01
```

Duplicate IPs will cause networking failures.

### Package Names Differ by OS

| Package | Ubuntu/Debian | CentOS/RHEL |
|---------|--------------|-------------|
| MySQL / MariaDB | `mysql-server` | `mariadb-server` |
| Service name | `mysql` | `mariadb` |
| Web server | `apache2` | `httpd` |

Always match the package and service names to the box OS.

## 3. Creating the Project

1. Create a new folder: `multivm`
2. Inside it, create a new file named `Vagrantfile` (capital V, no extension)
3. Paste the multi-VM content and make your adjustments:
    - Set the correct IP addresses (no duplicates)
    - Set the correct box names for each VM
    - Add provisioning to whichever VMs need it

## 4. Multi-VM Vagrant Commands

When running commands against a multi-VM Vagrantfile, **always specify the VM name** unless you intend to act on all of them.

### Starting VMs

```bash
vagrant up           # Starts ALL VMs defined in the Vagrantfile
vagrant up web01     # Starts only web01
vagrant up web02     # Starts only web02
```

### Connecting via SSH

```bash
vagrant ssh          # ❌ Fails — must specify a VM in multi-VM environments
vagrant ssh web01    # ✅ Connects to web01
vagrant ssh db01     # ✅ Connects to db01
```

> SSH is the one command where specifying the VM name is mandatory — Vagrant will error if you don't.

### Stopping VMs

```bash
vagrant halt         # Powers off ALL VMs
vagrant halt web02   # Powers off only web02
```

### Deleting VMs

```bash
vagrant destroy               # Deletes ALL VMs (asks for confirmation)
vagrant destroy --force       # Deletes ALL VMs without confirmation
vagrant destroy web01         # Deletes only web01
```

### Bringing Up a Specific VM After Destruction

```bash
vagrant up web02    # Only creates/starts web02 — leaves others as-is
```

### Status

```bash
vagrant status                 # Status of all VMs in the current Vagrantfile
vagrant global-status --prune  # Status of all Vagrant VMs on your system
```

## 5. Adding a New VM to an Existing Vagrantfile

To add a new VM without disrupting existing ones:

1. Open the Vagrantfile
2. Copy an existing `config.vm.define` block
3. Paste it below the last VM block, inside the outer `end`
4. Change **all** the VM name references and the IP address:

```ruby
config.vm.define "web03" do |web03|   # ← change name here
  web03.vm.box      = "ubuntu/focal64"  # ← and here
  web03.vm.hostname = "web03"           # ← and here
  web03.vm.network "private_network", ip: "192.168.56.44"  # ← unique IP
end
```

5. Save the file
6. Bring up only the new VM:

```bash
vagrant up web03
```

Vagrant reads the Vagrantfile, finds the `web03` definition, and creates only that VM — existing VMs are unaffected.

## 6. Using ChatGPT to Generate Multi-VM Vagrantfiles

Writing a multi-VM Vagrantfile manually — especially with several VMs and provisioning blocks — is repetitive. ChatGPT can generate the boilerplate quickly from a plain-English description.

### How to Use It

Open ChatGPT and describe exactly what you need:

```
Write a multi-VM Vagrantfile with:
- web01: ubuntu/focal64, private IP 192.168.56.41, hostname web01
- web02: ubuntu/focal64, private IP 192.168.56.42, hostname web02
- db01: centos-stream-9, private IP 192.168.56.43, hostname db01,
  provisioning to install mariadb-server and enable the mariadb service
Set hostnames for all VMs.
```

ChatGPT will generate the full Vagrantfile and explain each section. Copy the output into a file named `Vagrantfile`.

### What You Must Know Before Using ChatGPT for This

ChatGPT is an assistant — it can only help if you know what to ask. To write this prompt, you already need to know:

- What a multi-VM Vagrantfile is
- What box names to use for each OS
- What private IPs are and that they must be unique
- What provisioning is and what commands to run
- What hostnames are for

> If you paste ChatGPT's output without understanding it, you will not be able to fix it when something goes wrong.

### Always Review the Output

After pasting the generated Vagrantfile, check:

- IP addresses are all different and in the `192.168.56.x` range
- VM names in the `define` block match the names used inside the block
- Package names match the OS (`mariadb-server` for CentOS, `mysql-server` for Ubuntu)
- Service names are correct (`mariadb` vs `mysql`)
- Provisioning block is only applied to the VMs that need it
- `end` keywords are correctly placed — a missing `end` will cause a Ruby syntax error

### Other Uses for ChatGPT in This Context

- Search for error messages when `vagrant up` fails
- Ask for explanations of specific Vagrantfile settings
- Later, use it to generate: Bash scripts, Ansible playbooks, Terraform configs, Jenkinsfiles

## 7. When to Use Multi-VM vs Separate Folders

Multi-VM Vagrantfiles are for **a specific project** where multiple VMs form one application stack. They are not a replacement for organising unrelated VMs.

| Situation | Recommended Approach |
|-----------|---------------------|
| Multiple VMs for one application (e.g. web + db) | One folder, one multi-VM Vagrantfile |
| Unrelated VMs for different projects | Separate folders, separate Vagrantfiles |
| Learning / experimenting with a single service | Single-VM Vagrantfile in its own folder |

---

## 8. Cleaning Up

```bash
vagrant destroy --force   # Deletes all VMs in the current Vagrantfile without prompting
vagrant global-status --prune   # Confirms all VMs are gone
```

Always destroy VMs you no longer need — each running VM consumes RAM and CPU on your host machine. Running three VMs simultaneously can strain a system with limited resources.

## 9. Quick Reference

### Commands Summary

| Command | Effect |
|---------|--------|
| `vagrant up` | Start all VMs |
| `vagrant up <name>` | Start a specific VM |
| `vagrant ssh <name>` | SSH into a specific VM (name required) |
| `vagrant halt` | Stop all VMs |
| `vagrant halt <name>` | Stop a specific VM |
| `vagrant destroy` | Delete all VMs (with confirmation) |
| `vagrant destroy --force` | Delete all VMs without confirmation |
| `vagrant destroy <name>` | Delete a specific VM |
| `vagrant status` | Show status of all VMs in this Vagrantfile |

### Key Rules

1. Every VM in a multi-VM Vagrantfile must have a **unique IP address**.
2. The name in the `define` block and the pipe variable must match — `config.vm.define "web01" do |web01|`.
3. `vagrant ssh` always requires a VM name in a multi-VM environment.
4. `vagrant halt` and `vagrant destroy` without a name act on **all** VMs — use with care.
5. Package and service names differ between Ubuntu and CentOS — always match to the box OS.
6. Multi-VM Vagrantfiles are project-specific — keep unrelated VMs in separate folders.
7. Before running AI-generated Vagrantfiles, verify IP uniqueness, name consistency, and OS-appropriate package names.
