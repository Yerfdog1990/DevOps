# Using GitHub Copilot to Generate Vagrant Projects

---

## 1. Overview

Rather than manually writing Vagrantfiles and provisioning scripts, GitHub Copilot can generate an entire project structure — folder, Vagrantfile, provisioning script, and README — from a plain-English description.

This lecture demonstrates using Copilot's `/new` workspace command to scaffold both a website deployment project and a WordPress deployment project from scratch.

> ⚠️ **Important:** Copilot-generated code is a starting point, not a finished product. You must review every line it writes — the more code generated at once, the harder it is to find mistakes. This is called **reverse engineering** your own output, and it is a necessary skill when working with AI tools.

---

## 2. When to Use Copilot for Code Generation

Copilot is best used for:

- Generating boilerplate structure you already understand
- Scaffolding projects based on patterns you have done manually before
- Speeding up repetitive parts of a known workflow

It is **not** a substitute for understanding. If Copilot writes a script you cannot read and verify, you will not be able to debug it when something goes wrong.

3. Click the **+** symbol to open a fresh chat window

## 4. Generating a Website Deployment Project

### The `/new` Command

To create an entire folder structure and files, use the `/new` workspace command. This triggers `@workspace /new` automatically and tells Copilot to scaffold a new project.

### Writing the Prompt

Be specific. Include every piece of information Copilot needs to produce the right output:

```
@workspace /new Create a folder structure with a Vagrantfile and provisioning script.
VM settings:
- Box: ubuntu/jammy64 (Windows and macOS Intel)
- Private network IP: 192.168.56.28
- Public network enabled
- Mention the path of the provisioning script in the Vagrantfile, not inline commands

Provisioning script should set up a website from tooplate.com.
```

**Key prompt details to include:**

| Detail | Why It Matters |
|--------|---------------|
| Box name | Different OS for Windows vs macOS M-series — be explicit |
| IP address | Must not collide with other VMs |
| "Mention path of script, not inline commands" | Separates the Vagrantfile from the shell script into two distinct files |
| What the script should do | Defines the purpose of the provisioning script |

> For **macOS M-series (ARM)** chips, specify a different box in the prompt, e.g. `box/arm64` or the appropriate ARM-compatible image.

### What Copilot Generates

Copilot will propose a folder structure such as:

```
my-website-vagrant/
├── Vagrantfile          ← VM configuration, references provision.sh
├── provision.sh         ← Shell script with all setup commands
└── README.md            ← Explanation of the project
```

The Vagrantfile will contain:

```ruby
config.vm.provision "shell", path: "provision.sh"
```

Instead of inline commands — meaning all the setup logic lives in `provision.sh` as a separate, readable file.

### Creating the Workspace

1. Click **Create Workspace**
2. When prompted, select the parent folder (e.g. your `vagrant-vms` folder)
3. Copilot creates the folder and all files automatically

## 5. Generating a WordPress Deployment Project

Use the same approach with an updated prompt:

```
@workspace /new Create a folder structure with a Vagrantfile and provisioning script.
VM settings:
- Box: ubuntu/jammy64
- Private network IP: 192.168.56.79
- Public network enabled
- Memory: 2GB
- CPUs: 2
- Mention the path of the provisioning script in the Vagrantfile

Provisioning script should set up WordPress.
```

**Changes from the website prompt:**
- Different IP address (`79` instead of `28`) — always use unique IPs
- Added memory (`2GB`) and CPU (`2`) — WordPress needs more resources than a basic HTML site
- Changed the script purpose to "set up WordPress"

Copilot will generate a similar structure:

```
my-wordpress-vagrant/
├── Vagrantfile          ← with private/public network, 2GB RAM, 2 CPUs
├── provision.sh         ← full LAMP + WordPress setup commands
└── README.md
```

## 6. Inline Commands vs. External Script File

In previous lectures, provisioning commands were written inline in the Vagrantfile:

```ruby
# Inline approach (previous method)
config.vm.provision "shell", inline: <<-SHELL
  apt install -y apache2
  ...
SHELL
```

Copilot generates a cleaner separation using an external script file:

```ruby
# External script approach (Copilot method)
config.vm.provision "shell", path: "provision.sh"
```

| Approach | Pros | Cons |
|----------|------|------|
| `inline:` | Everything in one file | Vagrantfile becomes long and harder to read |
| `path: "provision.sh"` | Clean separation — Vagrantfile stays concise, script is independently readable and editable | Two files to manage |

The external script approach is better practice for complex setups.

## 7. Reviewing Copilot's Output

Never execute Copilot-generated scripts without reviewing them. Work through this checklist:

**Vagrantfile review:**
- Correct box name for your OS?
- IP address unique and in the right range?
- Memory and CPU values sensible?
- Provisioner pointing to the correct script path?

**Provisioning script review:**
- Are all manual steps from the documentation present?
- Does every `apt install` have `-y`?
- Are MySQL queries using `-e` flag (non-interactive)?
- Is the heredoc `EOF` marker free of leading spaces?
- Are file paths correct (`/srv/www/wordpress`, `/etc/apache2/sites-available/`)?
- Do database credentials in the script match what the MySQL setup creates?

**If the output is wrong:**
- Refine your prompt and try again — be more specific about what was incorrect
- Ask Copilot to modify a specific section rather than regenerating everything
- The more you interact with it, the better you learn to phrase prompts for accurate results

---

## 8. Testing the Generated Project

Once reviewed, test it in your Vagrant environment:

```bash
cd /f/vagrant-vms/my-website-vagrant
vagrant up
```

Watch the output carefully. If provisioning fails:

1. Read the error message — it usually identifies the failing command
2. SSH into the VM and run the failing command manually to confirm the issue
3. Fix the script and re-run with `vagrant provision` or `vagrant reload --provision`

> Test environments like Vagrant are exactly the right place to run and iterate on AI-generated scripts. Never run unreviewed AI-generated scripts in production.

---

## 9. Key Takeaways

1. The `/new` command in Copilot chat scaffolds an entire project folder with files — use it for generating boilerplate structure.
2. Always specify: box name, IP address, network type, resources, and what the provisioning script should do.
3. Prefer `path: "provision.sh"` over inline commands for complex setups — it keeps the Vagrantfile readable and the script independently maintainable.
4. Copilot output is a **starting point** — review every line before executing.
5. The more manual steps you have done yourself, the better you can evaluate whether Copilot's output is correct.
6. Refine prompts iteratively — if the first result is wrong, describe what needs to change rather than starting over.
7. These skills — prompting, reviewing, testing — apply to every AI tool you will use in cloud, containers, Ansible, and Terraform workflows.
