# Managing Services with systemctl – Writing a systemd File for Apache Tomcat

---

## 1. Overview

`systemctl` is the standard Linux command for managing services. Most services installed through a package manager (like `dnf` or `apt`) come with a `systemd` configuration file automatically — but some services, like Apache Tomcat, do not. In those cases, you must write your own.

This lecture uses Apache Tomcat as a practical example to understand:

- How `systemctl` works under the hood
- What a `systemd` service file looks like
- Why running services without `systemctl` is problematic in DevOps
- How to write a `systemd` file from scratch

> **Focus:** The main topic is `systemctl` and `systemd` — not Tomcat itself. Focus on the process and concepts, not the Tomcat-specific commands.

---

## 2. Apache httpd vs Apache Tomcat

These are two completely separate services despite sharing the "Apache" name:

| | Apache httpd | Apache Tomcat |
|--|-------------|---------------|
| **Purpose** | Serves static websites and HTML | Hosts Java-based web applications |
| **Package** | `httpd` (CentOS) / `apache2` (Ubuntu) | Downloaded manually as a tarball |
| **Installed via** | Package manager (dnf/apt) | Manual download from apache.org |
| **systemd file** | Created automatically on install | Must be written manually |
| **Port** | 80 (HTTP) | 8080 |

---

## 3. How systemctl Works — The systemd File

When you run `systemctl start httpd`, Linux reads a configuration file that tells it what command to actually execute. These files live at:

```
/usr/lib/systemd/system/
```

View the httpd service file as an example:

```bash
cat /usr/lib/systemd/system/httpd.service
```

A service file has three sections (called **directives**):

```ini
[Unit]
Description=The Apache HTTP Server
After=network.target

[Service]
Type=forking
ExecStart=/usr/sbin/httpd $OPTIONS -DFOREGROUND
ExecStop=...
User=apache

[Install]
WantedBy=multi-user.target
```

| Section | Purpose |
|---------|---------|
| `[Unit]` | Global information — description, dependencies |
| `[Service]` | How to start, stop, and run the service |
| `[Install]` | When in the boot process this service should start |

When `dnf install httpd` runs, the package manager automatically creates this file along with config directories, log directories, and library files. Tomcat is not available via `dnf`, so none of that happens automatically.

## 4. Installing Tomcat Manually

### Step 1 — Download and Extract

Search for "download Tomcat 10" and go to the official Apache Tomcat site. Copy the `.tar.gz` link from the binary distribution section:

```bash
wget https://downloads.apache.org/tomcat/tomcat-10/v10.x.x/bin/apache-tomcat-10.x.x.tar.gz
tar xzvf apache-tomcat-10.x.x.tar.gz
ls   # Confirm the extracted folder exists
```

The extracted folder contains everything Tomcat needs:

```
apache-tomcat-10.x.x/
├── bin/          ← startup.sh and shutdown.sh scripts
├── conf/         ← configuration files
├── lib/          ← libraries
├── logs/         ← log output
└── temp/
```

### Step 2 — Install the Java Dependency

Tomcat requires Java to run:

```bash
dnf install -y java-17-openjdk
java -version   # Confirm: openjdk version 17
```

### Step 3 — Start Tomcat Manually (The Problem Way)

```bash
cd apache-tomcat-10.x.x
bin/startup.sh
```

Check it's running:

```bash
ps -ef | grep tomcat
```

Get the VM's IP and open `http://<IP>:8080` in a browser — you should see the default Tomcat page.

---

## 5. Why Manual Startup Is Not Acceptable in DevOps

Running Tomcat via `bin/startup.sh` works, but introduces serious problems:

| Problem | Detail |
|---------|--------|
| **No auto-start on reboot** | If the VM reboots, Tomcat stays down — you must manually run `startup.sh` again |
| **No `systemctl` integration** | Cannot use `systemctl start/stop/enable tomcat` |
| **Broken automation** | DevOps tools like Ansible manage services by calling `systemctl` — if the service isn't registered, it cannot be managed remotely |
| **Manual stop process** | Must find the process ID and use `kill` — messy if Tomcat spawns child processes |

```bash
# Stopping Tomcat manually — fragile
ps -ef | grep tomcat   # Find the process ID
kill 31251             # Kill it by PID — tedious and error-prone
```

The solution: write a `systemd` service file so Tomcat can be managed like any other service.

## 6. Setting Up Tomcat Properly

### Step 1 — Create a Dedicated System User

Services should never run as root. Create a non-login user specifically for Tomcat:

```bash
useradd -m -d /opt/tomcat -s /sbin/nologin tomcat
```

| Flag | Purpose |
|------|---------|
| `-m` | Create the home directory |
| `-d /opt/tomcat` | Set home directory to `/opt/tomcat` |
| `-s /sbin/nologin` | Prevent anyone from logging in as this user (security) |

### Step 2 — Copy Tomcat Files to the Home Directory

```bash
cp -r apache-tomcat-10.x.x/* /opt/tomcat/
```

### Step 3 — Set Ownership to the Tomcat User

```bash
chown -R tomcat: /opt/tomcat
```

`-R` applies ownership recursively to all files and subdirectories. Without this, Tomcat will fail with permission denied errors.

Verify:

```bash
ls -l /opt/tomcat   # All files should show tomcat as owner
```

## 7. Writing the systemd Service File

Service files for custom services go in:

```
/etc/systemd/system/
```

The filename becomes the service name — `tomcat.service` means `systemctl start tomcat`.

```bash
vim /etc/systemd/system/tomcat.service
```

### The Complete File

```ini
[Unit]
Description=Apache Tomcat Web Application Container
After=network.target

[Service]
Type=forking
User=tomcat
Group=tomcat
WorkingDirectory=/opt/tomcat

Environment=JAVA_HOME=/usr/lib/jvm/jre
Environment=CATALINA_HOME=/opt/tomcat
Environment=CATALINA_BASE=/opt/tomcat

ExecStart=/opt/tomcat/bin/startup.sh
ExecStop=/opt/tomcat/bin/shutdown.sh

[Install]
WantedBy=multi-user.target
```

### Line-by-Line Breakdown

**`[Unit]` section:**

| Line | Meaning |
|------|---------|
| `Description=` | Human-readable name shown in `systemctl status` |
| `After=network.target` | Tomcat only starts after networking is up — a dependency |

**`[Service]` section:**

| Line | Meaning |
|------|---------|
| `Type=forking` | The startup script launches child processes (forks) — tells systemd not to treat the parent script exiting as a failure |
| `User=tomcat` | Run the service as the `tomcat` user, not root |
| `Group=tomcat` | Run under the `tomcat` group |
| `WorkingDirectory=` | The working directory when the service starts |
| `Environment=JAVA_HOME=...` | Tells Tomcat where Java is installed |
| `Environment=CATALINA_HOME=...` | Tells Tomcat where its own home directory is |
| `Environment=CATALINA_BASE=...` | Base directory for Tomcat configuration |
| `ExecStart=` | The command that starts the service |
| `ExecStop=` | The command that stops the service |

**`[Install]` section:**

| Line | Meaning |
|------|---------|
| `WantedBy=multi-user.target` | Start this service when the OS boots into normal multi-user mode (non-GUI, full services) — this is what enables auto-start on reboot |

> **`multi-user.target`** is the normal operating mode of a Linux server — all services running, no graphical interface. When you run `systemctl enable tomcat`, this target is what Tomcat gets linked to.

### Setting Environment Variables in systemd

Unlike a shell script where you use `export VARIABLE=value`, in a systemd file you use:

```ini
Environment=VARIABLE_NAME=value
```

These are requirements of Tomcat itself, not systemd — Tomcat needs to know where Java is and where its own files are.

## 8. Activating the Service

After writing or modifying any systemd file, reload the daemon so systemd picks up the changes:

```bash
systemctl daemon-reload
```

Then start and enable the service:

```bash
systemctl start tomcat      # Start immediately
systemctl status tomcat     # Confirm it's active (running)
systemctl enable tomcat     # Enable auto-start on reboot
```

Test from the browser: `http://<VM-IP>:8080`

---

## 9. Why This Matters in DevOps — Ansible Example

Automation tools like Ansible manage services through `systemctl`. A typical Ansible task looks like:

```yaml
- name: Start Tomcat service
  service:
    name: tomcat
    state: started
    enabled: yes
```

When this runs, Ansible calls `systemctl start tomcat` in the background. If no `systemd` file exists for Tomcat, this fails — there is no standard way for the automation tool to manage the service.

> Writing `systemd` files is an essential DevOps skill for any service that doesn't come with one. Without it, services cannot be managed by orchestration tools, cannot auto-start on reboot, and cannot be reliably monitored.

```bash
systemctl enable tomcat
systemctl status tomcat

ls /usr/lib/systemd/system/
cat /usr/lib/systemd/system/httpd.service
```

---

## 11. Key Takeaways

1. Every service managed by `systemctl` needs a `.service` file — installed services get one automatically, manual installs do not.
2. `systemd` files live in `/usr/lib/systemd/system/` (package-managed) or `/etc/systemd/system/` (custom).
3. The three directives are `[Unit]` (description and dependencies), `[Service]` (how to run it), and `[Install]` (when to start it during boot).
4. Always run `systemctl daemon-reload` after creating or modifying a `systemd` file.
5. Services should always run as a **non-root, no-login user** — create a dedicated system user for each service.
6. Set file ownership with `chown -R` so the service user can read and write its own files.
7. `WantedBy=multi-user.target` is what makes `systemctl enable` work — it links the service into the normal boot sequence.
8. Without `systemctl` integration, automation tools like Ansible cannot manage the service.
