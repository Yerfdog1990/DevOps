# EC2 Part 1 — Best Practices, Key Pairs, Security Groups, Launching & Deploying

---

## 1. Best Practice — The Right Order to Launch an EC2 Instance

Before clicking "Launch Instance," follow this structured approach:

```
Step 1: Gather Requirements
        ↓
Step 2: Create Key Pair
        ↓
Step 3: Create Security Group
        ↓
Step 4: Launch the Instance
        (select key pair + security group during launch wizard)
```

> Creating the key pair and security group **before** launching keeps things organized and avoids confusion during the wizard.

---

## 2. Requirement Gathering

Before launching any EC2 instance, collect the following:

| Requirement | What It Determines |
|---|---|
| **Operating System** | Which AMI to select (Amazon Linux, Ubuntu, CentOS, Windows) |
| **RAM / CPU / Network** | Which instance type (t2.micro, m4.large, etc.) |
| **Storage size** | EBS volume size — OS storage + application data |
| **Services / Applications** | Which ports to open in the security group (SSH=22, HTTP=80, MySQL=3306) |
| **Environment** | Dev / QA / Staging / Pre-prod / Production — drives tagging and key decisions |
| **Login user / Owner** | Who manages the instance — used for tagging and tracking |
| **Project name** | Used for naming conventions on keys, security groups, and tags |

> This is a minimum list — real projects may require more or less.

## 3. Key Pairs — Best Practices

### What is a Key Pair?
- A **public key + private key** combination for secure login to EC2 instances
- **Public key** → injected into the instance (the lock)
- **Private key** (`.pem` file) → downloaded to your machine (the key)
- Keys are **region-specific** — a key created in us-east-1 only works in us-east-1

### Correct Key Strategy

| ❌ Wrong | ✅ Right |
|---|---|
| One key for ALL instances | One key per **environment** (dev, qa, staging, prod) |
| A separate key for EVERY instance | Group instances logically by environment |
| Random or unclear key names | Use a consistent naming convention |

### Recommended Naming Convention

```
<project-name>-<environment>-<region>

Example: moso-dev-us-east-1
```

This immediately tells you: **project** (Moso), **environment** (Dev), **region** (N. Virginia).

### Key File Formats

| Format | Use With |
|---|---|
| `.pem` | macOS Terminal, Linux terminal, Git Bash |
| `.ppk` | PuTTY (Windows) |

### Creating a Key Pair — Step by Step

```
1. EC2 Dashboard → Network & Security → Key Pairs
2. Click "Create key pair"
3. Name: moso-dev-us-east-1
4. Format: .pem (terminal) or .ppk (PuTTY)
5. Add a Name tag (same as key name)
6. Click "Create key pair"
7. Private key (.pem) downloads automatically
8. ⚠️ Save securely — this is the ONLY time you can download it
```

> When you delete a key pair in AWS, the downloaded private key also becomes **useless**. Delete both together to avoid confusion.

## 4. Security Groups — Best Practices

### What is a Security Group?
> A **virtual firewall** that controls **inbound and outbound traffic** at the instance level.

Think of it as a **bouncer with a register**:
- Checks what is **allowed in** (inbound rules)
- Checks what is **allowed out** (outbound rules)
- Checks **where traffic is coming from** (source IP)

### Key Properties
- One security group can be applied to **multiple instances**
- **Stateful** — allowing inbound traffic on port 22 automatically allows the return outbound traffic
- Rule changes apply **immediately** to all associated instances

### Correct Security Group Strategy

| ❌ Wrong | ✅ Right |
|---|---|
| One security group for ALL instances | One per environment + service type |
| Separate security group for EVERY instance | Group by role: web, database, app servers |
| Allow "All Traffic" from anywhere | Allow only specific ports from specific sources |
| No naming convention | Use clear, consistent naming |

> Allowing "All Traffic" from `0.0.0.0/0` means **no restrictions at all — no doors, no gates, anyone can enter.** Seen even in sophisticated projects, but always wrong.

### Recommended Naming Convention

```
<project-name>-<service-type>

Example: moso-dev-web
```

### Inbound vs. Outbound Rules

| Rule Type | Direction | Description |
|---|---|---|
| **Inbound** | Traffic → your instance | Control who can access your server |
| **Outbound** | Traffic ← your instance | Control what your server can reach externally |

### ⚠️ Do NOT touch the Outbound Rule

> The default outbound rule allows **all traffic out** — this is required for internet connectivity (package installs, updates, API calls). Changing it will break internet access on the instance.
> Only modify outbound rules if explicitly instructed.

### Rule-Adding Best Practice

> **Only add rules for services that are actually running.** Never pre-add rules in advance.

| Is the service running? | Add the rule? |
|---|---|
| SSH — yes, needed for admin access | ✅ Add port 22 immediately |
| HTTP — web server not installed yet | ❌ Don't add port 80 yet |
| HTTP — web server installed and running | ✅ Add port 80 now |

### Creating a Security Group — Step by Step

```
1. EC2 Dashboard → Network & Security → Security Groups
2. Click "Create security group"
3. Name: moso-dev-web
4. Add Inbound Rules:
   → SSH | TCP | Port 22 | Source: My IP (corporate/admin access only)
5. Leave Outbound Rules as default (All traffic → 0.0.0.0/0)
6. Add Name tag (same as security group name)
7. Click "Create security group"
```

## 5. Launching the EC2 Instance

### Recommended Tags (Apply to Instance, Volume, and Network Interface)

| Tag Key | Example Value | Purpose |
|---|---|---|
| `Name` | web01 | Identifies the instance |
| `Project` | Moso | Tracks which project it belongs to |
| `Environment` | Dev | Identifies the environment |
| `Owner` | Godfrey | Tracks who is responsible |

> Tagging volumes and network interfaces helps you identify what resources belong to which project and instance — critical in large environments.

### Launch Wizard — Step by Step

```
1. EC2 Dashboard → Instances → Launch Instances

2. Add Tags:
   → Keys: Name, Project, Environment, Owner
   → Apply to: Instance + Volume + Network Interface

3. Choose AMI:
   → Ubuntu Server 24.04 LTS (Free Tier eligible)

4. Choose Instance Type:
   → t2.micro (1 vCPU, 1 GiB RAM — Free Tier eligible)

5. Key Pair:
   → Select: moso-dev-us-east-1
   → Easy to identify with proper naming convention

6. Network Settings → Edit → Security Group:
   → Select existing: moso-dev-web
   → Proper naming makes selection easy even with 50+ groups

7. Storage:
   → Keep default (8 GB EBS for Linux)

8. User Data:
   → Leave blank — commands will be run manually via SSH

9. Click "Launch Instance"
```

## 6. Connecting to the Instance via SSH

### Fix Key Permissions First

```bash
chmod 400 moso-dev-us-east-1.pem

# Verify:
ls -l moso-dev-us-east-1.pem
# → -r--------@ 1 user staff 1678 Jun 8 21:06 moso-dev-us-east-1.pem
```

### SSH Connection Command

```bash
# Ubuntu AMI — username is "ubuntu"
ssh -i moso-dev-us-east-1.pem ubuntu@<PUBLIC_IP>
```

**Successful login output:**
```
,     #_
~\_  ####_        Amazon Linux 2023
~~  \_#####\
...
ubuntu@ip-172-31-16-47:~$
```

### Switch to Root

```bash
sudo -i
# Prompt: root@ip-172-31-16-47:~#
```

## 7. Installing Apache Web Server (Ubuntu)

### Common Mistake — Wrong Command

```bash
# ❌ WRONG — "install" is a Linux file-copy utility, not apt
apt update && install apache2 -y
# Error: unexpected argument '-y' found
```

### Correct Command

```bash
# ✅ CORRECT
apt update && apt install apache2 -y
```

### What Happens During Installation

```
Installing: apache2
Installing dependencies:
  apache2-bin, apache2-utils, libapr1t64, libaprutil1t64,
  libaprutil1-dbd-sqlite3, libaprutil1-ldap, liblua5.4-0, ssl-cert

Enabling modules: mpm_event, authz_core, authz_host, auth_basic,
  access_compat, alias, dir, autoindex, env, mime, filter, deflate,
  status, reqtimeout...

Enabling site 000-default.
Created symlink: apache2.service → multi-user.target.wants
```

> On Ubuntu, Apache **starts automatically** and is **enabled on boot** after installation — no manual start needed.

### Verify Installation

```bash
systemctl status apache2
```

**Expected output:**
```
● apache2.service - The Apache HTTP Server
     Loaded: loaded (/usr/lib/systemd/system/apache2.service; enabled)
     Active: active (running) since Tue 2026-06-09 11:07:07 UTC; 25s ago
   Main PID: 2207 (apache2)
     Status: "Total requests: 0; Idle/Busy workers 100/0..."
```

### Enable Apache on Boot (if needed)

```bash
systemctl enable apache2
systemctl start apache2
```

## 8. Deploying a Website Template

### Download and Extract the Template

```bash
# Download the zip file using wget
wget <template-download-url>
# Example: downloaded as 2158_forge_reality.zip

# Install unzip if not present
apt install unzip -y

# Extract the zip
unzip 2158_forge_reality.zip
```

**Extraction output:**
```
Archive: 2158_forge_reality.zip
  creating: 2158_forge_reality/
  creating: 2158_forge_reality/images/
  inflating: 2158_forge_reality/images/toopate-forge-hero-01.jpg
  inflating: 2158_forge_reality/index.html
  inflating: 2158_forge_reality/tooplate-forge-script.js
  inflating: 2158_forge_reality/tooplate-forge-style.css
  ...
```

### Deploy to Apache Web Root

```bash
# Copy all website files to Apache's document root
cp -r 2158_forge_reality/* /var/www/html/

# Restart Apache to serve the new content
systemctl restart apache2
```

### Verify Deployment

```bash
# Check Apache processes are running
ps -ef | grep apache2
# → root 2757 1 0 11:12 ? /usr/sbin/apache2 -k start -DFOREGROUND
# → www-data 2760 2757 ... /usr/sbin/apache2 -k start -DFOREGROUND

# Confirm website files are in place
ls /var/www/html/
# → images  index.html  templates.html  tooplate-forge-script.js  tooplate-forge-style.css

# Verify Apache is listening on port 80
ss -tunlp | grep 2757
# → tcp LISTEN 0 511 *:80 *:* users:(("apache2",pid=2761,...))
```

### Test Locally on the Server

```bash
curl http://127.0.0.1
# → Returns HTML of the Forge Reality website (not the default Apache page)
```

## 9. Common `ss` Command Mistakes

```bash
# ❌ Wrong — missing dash before flags
ss tunlp | grep 2757
# Error: an inet prefix is expected rather than "tunlp"

# ❌ Wrong — passing PID directly as argument
ss -tunlp 2757
# Error: bison bellows (while parsing filter): "syntax error!"

# ✅ Correct — filter by port
ss -tunlp | grep :80

# ✅ Correct — filter by process name
ss -tunlp | grep apache2

# ✅ Correct — filter by PID using pipe
ss -tunlp | grep 2757
```

## 10. Opening Port 80 in the Security Group

Apache is running and listening on port 80, but the website won't load from a browser yet — the security group only allows port 22.

```
EC2 Dashboard
  → Instances → Select running instance (web01)
  → Security tab → Click the Security Group link
  → Edit Inbound Rules
  → Add Rule:
      Type: HTTP | Protocol: TCP | Port: 80 | Source: 0.0.0.0/0  (IPv4)
      Type: HTTP | Protocol: TCP | Port: 80 | Source: ::/0        (IPv6)
  → Save Rules
```

> Allowing port 80 from anywhere is **appropriate for public-facing websites**. For internal services, restrict the source IP.

### Final Security Group Inbound Rules

| Type | Protocol | Port | Source |
|---|---|---|---|
| SSH | TCP | 22 | My IP (admin access only) |
| HTTP | TCP | 80 | 0.0.0.0/0 (public web traffic) |
| HTTP | TCP | 80 | ::/0 (IPv6 public web traffic) |

### Test from Browser

```
http://<PUBLIC_IP>
```

If the Forge Reality website loads → **deployment is complete** ✅

## 11. Ubuntu vs. Amazon Linux — Key Differences

| Feature | Ubuntu | Amazon Linux 2023 |
|---|---|---|
| Package manager | `apt` | `dnf` / `yum` |
| Web server package name | `apache2` | `httpd` |
| Default SSH username | `ubuntu` | `ec2-user` |
| Web server auto-start | ✅ Yes (after install) | ❌ No (manual `systemctl start`) |
| Web root | `/var/www/html/` | `/var/www/html/` |
