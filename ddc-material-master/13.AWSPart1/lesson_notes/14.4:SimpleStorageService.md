# AWS S3 (Simple Storage Service) 

---

## 1. What is Amazon S3?

> **Amazon S3 (Simple Storage Service)** is an object storage service that offers industry-leading scalability, data availability, security, and performance. Store and retrieve any amount of data from anywhere.

- Every object (file) in S3 is stored in a **bucket**
- Customers of all sizes and industries use S3 for: data lakes, cloud-native applications, mobile apps, backups, archives
- Scales automatically — no storage limits, no upfront investment
- **99.999999999% (11 nines) durability** — data is replicated across multiple AZs

### Key Benefits

| Benefit | Description |
|---|---|
| **Scalability** | Scale to any amount of data — petabytes, exabytes — without pre-provisioning |
| **Durability** | 11 nines durability — data protected against failures, errors, and threats |
| **Security** | Encryption at rest and in transit, fine-grained access control via IAM and bucket policies |
| **Flexible storage** | Multiple storage classes for different access patterns and cost requirements |
| **Granular control** | Lifecycle rules, event notifications, access logs, automated workflows |

### Common Use Cases

| Use Case | Description |
|---|---|
| **Backup and restore** | Scalable, durable backup replacing on-premises storage |
| **Disaster recovery** | Protect critical data without a second physical site |
| **Archive** | Long-term data retention at lowest possible cost |
| **Data lakes** | Central repository for structured and unstructured data |
| **Hybrid cloud storage** | Bridge between on-premises and cloud via AWS Storage Gateway |
| **Web/app hosting** | Store static assets, media files, application data |

## 2. Core S3 Concepts

### Buckets and Objects

| Term | Definition |
|---|---|
| **Bucket** | Top-level logical container where data is stored — like a top-level folder |
| **Object** | The actual data stored — a file, document, picture, video, etc. |
| **Key** | The full path/name of an object within a bucket |
| **Object URL** | Publicly accessible link to an object (if permissions allow) |

### Bucket Name Rules
- Must be **3 to 63 characters**
- Must be **globally unique** — across ALL AWS accounts worldwide
- Only lowercase letters `a-z`, numbers `0-9`, periods `.`, and hyphens `-`
- Must begin and end with a letter or number
- No uppercase letters

> **Why globally unique?** Every bucket gets a publicly accessible DNS endpoint that includes the bucket name (e.g., `s3.amazonaws.com/your-bucket-name`). Since the name is in the URL, it must be unique on the internet.

### Bucket Types

| Type | Description | Use Case |
|---|---|---|
| **General purpose** (default) | Objects replicated across multiple AZs; supports all storage classes | Most use cases |
| **Directory** | Single AZ, S3 Express One Zone only; lower latency | Low-latency, high-throughput workloads |

### S3 vs. EFS — Key Difference

| Feature | EFS | S3 |
|---|---|---|
| **Access method** | Mount at OS level — appears as a folder | Programmatic access via API/SDK in application code |
| **Protocol** | NFS (file system protocol) | HTTP/HTTPS (object storage) |
| **Use case** | OS-level file sharing between EC2 instances | Application-level storage, web assets, backups |
| **Mounting** | `mount -a` / fstab | Can be mounted via S3FS driver (different approach) |

> S3 can be mounted to a folder using **S3FS** driver, but the typical and recommended approach is **programmatic access** through AWS SDKs in your application code.

## 3. Creating an S3 Bucket

```
AWS Console → S3 → Create Bucket

Step 1: General Configuration
  Region:       Select based on user location and compliance
  Bucket type:  General purpose (for most use cases)
  Bucket name:  Must be globally unique
                Tip: Add numbers to make unique (e.g., devops-imran-623)

Step 2: Object Ownership
  ACLs disabled (recommended): Access controlled via bucket policies only
  ACLs enabled:                 Other AWS accounts can own objects in the bucket
                                Required if you want to make objects public via ACL

Step 3: Block Public Access
  ✅ Block all public access (default) — AWS safety net against accidental exposure
  Uncheck only when you specifically need public access (e.g., hosting a website)

Step 4: Bucket Versioning
  Disable: Objects are overwritten/deleted permanently
  Enable:  Multiple versions kept — easy recovery from accidental deletes/overwrites

Step 5: Default Encryption
  SSE-S3: Amazon manages encryption keys — cheapest option ✅ (default)
  SSE-KMS: You manage keys via AWS KMS — compliance use cases, not free
  DSSE-KMS: Dual-layer encryption — highest security, highest cost

→ Create Bucket
```

### S3 Bucket Tabs (Console Overview)

| Tab | Purpose |
|---|---|
| **Objects** | View, upload, download, delete objects and folders |
| **Metadata** | S3 managed metadata tables (Apache Iceberg — for analytics) |
| **Properties** | Versioning, encryption, static website hosting, event notifications, transfer acceleration, Object Lock |
| **Permissions** | Block public access, bucket policy (JSON), ACLs, CORS |
| **Metrics** | Storage class analysis, replication metrics, request metrics |
| **Management** | Lifecycle rules, replication rules, inventory configurations |
| **File systems** | S3 Files — high-performance file system access to S3 data |
| **Access Points** | Per-application entry points with individual policies |

## 5. Object Access — Private by Default

> **Every object uploaded to S3 is private by default** — even if you are the bucket owner, the object cannot be accessed via its public URL until you explicitly grant public access.

### Two Ways to Access Objects

| Method | Who Can Access | URL |
|---|---|---|
| **Open** (console button) | AWS user (owner) — uses IAM credentials | Pre-signed URL (temporary) |
| **Object URL** | Public internet — only if object is made public | `https://bucket.s3.amazonaws.com/key` |

### Testing Access — "Access Denied"

```bash
# Copy the Object URL from the console:
https://s3.amazonaws.com/bucket-name/object-key

# Paste in browser → Access Denied ❌
# Even if you can open it in the console, the public URL is blocked
```

## 6. Making Objects Public (Step-by-Step)

To make an object publicly accessible, **three things must all be true**:

```
1. Block Public Access must be OFF (at bucket level)
   AND
2. ACLs must be ENABLED (Object Ownership setting)
   AND
3. Object must be made public using ACL
```

### Step-by-Step Process

```
Step 1: Disable Block Public Access
  S3 → Bucket → Permissions → Block public access → Edit
  → Uncheck "Block all public access"
  → Save Changes → Confirm

Step 2: Enable ACLs
  S3 → Bucket → Permissions → Object Ownership → Edit
  → Select "ACLs enabled" (Bucket owner preferred)
  → Acknowledge → Save Changes

Step 3: Make Object(s) Public
  S3 → Bucket → Select object(s)
  → Actions → Make public using ACL
  → Make public

Step 4: Verify
  Copy the Object URL → paste in browser → object loads ✅
```

> ⚠️ AWS blocks public access by default as a safety net. Only disable it if you specifically need public access. Never accidentally expose sensitive data.

### Object-Level vs. Bucket-Level Public Access

```
Bucket public access: OFF (blocked)
Object: "Make public" → ❌ Error — blocked by bucket setting

Bucket public access: ON (unblocked)
Object: Not yet made public → ❌ Access Denied (private by default)

Bucket public access: ON
Object: Made public using ACL → ✅ Publicly accessible
```

## 7. Bucket Versioning

> **Versioning** keeps multiple variants of an object in the same bucket. Enable it to recover from accidental deletes and overwrites.

### Enabling Versioning

```
S3 → Bucket → Properties → Bucket Versioning → Edit
→ Enable → Save Changes
```

### How Versioning Works

**Normal upload (no overwrite):**
```
Upload file.txt (v1) → Only one version
```

**Overwrite:**
```
Upload file.txt (v1)
Upload file.txt again (v2)
→ Both versions stored
→ Latest version (v2) shown by default
→ Toggle "Show versions" to see v1
```

**Delete in a versioned bucket:**
```
Delete file.txt
→ A "delete marker" is placed on top
→ File appears deleted (hidden)
→ File is NOT permanently removed — it's still there as a version
→ Toggle "Show versions" → you see the file + delete marker
→ Delete the delete marker → file comes back!
```

**Permanently delete a version:**
```
Toggle "Show versions" ON
→ Select the specific version
→ Delete → "Permanently delete" option appears
→ Confirm → that version is permanently gone
```

### Versioning Warning — Storage Costs

```
⚠️ Every overwrite creates a new version — all versions stored, all cost money
⚠️ Deleting a file in a versioned bucket does NOT free storage
⚠️ To actually reduce storage: delete the versions themselves

Best practice:
  → Use versioning only when recovery is really required
  → Combine with lifecycle rules to auto-delete old versions after N days
```

## 8. Hosting a Static Website on S3

> One of S3's most popular use cases — host a static website without any EC2 instances, load balancers, or Apache servers.

### Steps to Host a Static Website

```
Step 1: Create a bucket
  Name: barista908  (will be part of the website URL)
  Enable versioning: ✅ (recommended)

Step 2: Upload website files
  Upload: index.html, css/, js/, images/, etc.
  Drag and drop all files into the bucket

Step 3: Make all objects public
  Permissions → Uncheck Block public access → Confirm
  Object Ownership → Enable ACLs → Save
  Select all objects → Actions → Make public using ACL → Make public

Step 4: Enable Static Website Hosting
  Properties → Static website hosting → Edit
  → Enable
  → Index document: index.html
  → Error document: error.html (or any error page)
  → Save changes
  → Copy the website URL provided

Step 5: Access the website
  Paste the S3 website URL in browser → Website loads ✅
```

### Static Website URL Format

```
http://bucket-name.s3-website-region.amazonaws.com
Example:
http://barista908.s3-website-us-east-1.amazonaws.com
```

> You can point your custom domain (e.g., `barista.example.com`) to this URL using a CNAME record in your domain provider. This is covered in project lectures.

### Static vs. Dynamic Websites on S3

| Website Type | S3 Hosting? | Notes |
|---|---|---|
| **Static** (HTML, CSS, JS, images) | ✅ Yes | No server-side code — pure S3 |
| **Dynamic** (user login, database) | ❌ Not directly | But S3 can serve the static assets (images, videos, documents) that dynamic apps need |

## 10. S3 Bucket Charges

S3 charges are based on four components:

| Charge | Description |
|---|---|
| **Storage** | Amount of data stored × storage class rate |
| **Requests** | Number of GET, PUT, DELETE, LIST operations |
| **Data transfer** | Outbound data transfer to internet or other regions |
| **Region replication** | Cross-region replication traffic |

> **Free Tier:** 5 GB Standard storage, 20,000 GET requests, 2,000 PUT requests per month.

## 12. S3 Storage Classes

S3 offers multiple storage classes designed for different access patterns. Choosing the right class saves significant cost.

| Storage Class | Designed For | AZs | Min Storage | Min Object Size | Retrieval |
|---|---|---|---|---|---|
| **Standard** | Frequently accessed data (daily/weekly) | ≥ 3 | None | None | Milliseconds |
| **Intelligent-Tiering** | Unknown/changing access patterns | ≥ 3 | None | 128 KB (monitoring fee) | Milliseconds |
| **Standard-IA** | Infrequently accessed (once/month) | ≥ 3 | 30 days | 128 KB | Milliseconds |
| **One Zone-IA** | Infrequent access, recreatable data | 1 | 30 days | 128 KB | Milliseconds |
| **Glacier Instant Retrieval** | Archive accessed quarterly | ≥ 3 | 90 days | 128 KB | Milliseconds |
| **Glacier Flexible Retrieval** | Archive accessed yearly | ≥ 3 | 90 days | None | Minutes to hours |
| **Glacier Deep Archive** | Rarely accessed, longest retention | ≥ 3 | 180 days | None | Hours |

### Storage Class Cost Hierarchy (Most to Least Expensive)

```
Standard
  ↓ (lower access → lower cost)
Intelligent-Tiering
  ↓
Standard-IA
  ↓
One Zone-IA
  ↓
Glacier Instant Retrieval
  ↓
Glacier Flexible Retrieval (formerly Glacier)
  ↓
Glacier Deep Archive  ← cheapest
```

> **Key insight:** You pay for storage + retrieval. Cheaper storage classes charge per retrieval. Standard has no retrieval fee. Choose based on how often you'll need the data.

## 13. S3 Lifecycle Rules

> **Lifecycle rules** define automatic transitions of objects from one storage class to another based on their age — saving cost by moving data to cheaper storage as it ages and is accessed less frequently.

**Why use lifecycle rules?**
- Newly uploaded objects are accessed frequently → keep in Standard
- After 30 days they're accessed rarely → move to Standard-IA (cheaper)
- After 90 days they're accessed almost never → archive to Glacier
- After 450 days you don't need them at all → delete

Lifecycle rules run **once per day**.

---

### Creating a Lifecycle Rule — Step by Step

```
S3 → Your Bucket → Management tab → Lifecycle rules → Create lifecycle rule
```

**Rule configuration:**

```
Lifecycle rule name: CostEffectiveTransitions

Scope:
  ○ Limit scope using prefix/tags  → applies to specific files
  ✅ Apply to all objects in the bucket → applies to everything

Actions to enable:
  ✅ Transition current versions of objects between storage classes
  ✅ Transition noncurrent versions of objects between storage classes
  ✅ Expire current versions of objects
  ✅ Permanently delete noncurrent versions of objects
  ✅ Delete incomplete multipart uploads
```

> ⚠️ If your bucket is **versioned**, you MUST configure rules for both **current** AND **non-current** versions. Otherwise, old versions pile up and cost money even as current versions move to cheaper storage.

---

### Lifecycle Transitions — Current Version

| Transition | After (Days) | Description |
|---|---|---|
| Standard → Standard-IA | Day 30 | Not accessed frequently — move to cheaper class |
| Standard-IA → One Zone-IA | Day 60 | Even less access — single AZ, cheaper |
| One Zone-IA → Glacier Flexible Retrieval | Day 90 | Rarely accessed — archive tier |
| Glacier Flexible → Glacier Deep Archive | Day 180 | Almost never accessed — cheapest storage |
| **Expire (delete marker)** | Day 450 | Object "expires" — delete marker placed |

> **In a versioned bucket:** "Expire" places a **delete marker**, it does NOT permanently delete. The old version is retained as a non-current version.
> **In a non-versioned bucket:** "Expire" permanently deletes the object.

---

### Lifecycle Transitions — Non-Current Versions

| Transition | After (Days Non-current) |
|---|---|
| Standard → Standard-IA | Day 35 |
| Standard-IA → One Zone-IA | Day 65 |
| One Zone-IA → Glacier Flexible Retrieval | Day 95 |
| Glacier Flexible → Glacier Deep Archive | Day 185 |
| **Permanently delete** | Day 455 |

> ⚠️ **Glacier Deep Archive requires 90-day gap** from the previous Glacier class. If Glacier is at day 90, Deep Archive must be day 180 or later.

---

### Incomplete Multipart Uploads

```
Delete incomplete multipart uploads after: 15 days
```

When large file uploads fail midway, the parts remain stored and cost money. This rule cleans them up.

---

### Full Lifecycle Timeline Visualization

```
Current Version:
Day 0    → Object uploaded (Standard)
Day 30   → Moves to Standard-IA
Day 60   → Moves to One Zone-IA
Day 90   → Moves to Glacier Flexible Retrieval
Day 180  → Moves to Glacier Deep Archive
Day 450  → Object expires (delete marker in versioned bucket)

Non-Current Versions:
Day 0    → Becomes noncurrent (replaced by newer version)
Day 35   → Moves to Standard-IA
Day 65   → Moves to One Zone-IA
Day 95   → Moves to Glacier Flexible Retrieval
Day 185  → Moves to Glacier Deep Archive
Day 455  → Permanently deleted

Incomplete uploads:
Day 15   → Deleted
```

---

### Important Notes on Lifecycle Rules

| Rule | Detail |
|---|---|
| **Objects < 128 KB** | Not recommended to transition — transition costs can exceed storage savings |
| **Minimum duration** | Standard-IA and One Zone-IA require 30-day minimum; Glacier requires 90-day minimum |
| **Transition charges** | Each object transition costs a per-request fee |
| **Versioned buckets** | Must handle both current and non-current versions |
| **Rules can be edited** | Modify or delete lifecycle rules at any time |

## 14. S3 Replication

> **S3 Replication** enables automatic, asynchronous copying of objects across S3 buckets — for disaster recovery, compliance, latency reduction, or log aggregation.

### Types of Replication

#### Live Replication (Automatic — new objects only)

**Cross-Region Replication (CRR):**
- Copies objects to a bucket in a **different AWS Region**
- Use cases:
    - **Disaster recovery** — data in a geographically separate location
    - **Compliance** — regulations require data in multiple countries/continents
    - **Latency** — serve users from a region closer to them
    - **Operational efficiency** — compute clusters in multiple regions need the same data

**Same-Region Replication (SRR):**
- Copies objects to a bucket in the **same AWS Region**
- Use cases:
    - **Log aggregation** — replicate logs from multiple buckets to one central bucket
    - **Production/test separation** — keep test environment in sync with production
    - **Data sovereignty** — regulatory requirement to keep copies within the same country

#### On-Demand Replication (Batch Replication)

- Replicates **existing objects** that were uploaded before replication was configured
- Can retry objects with **FAILED** replication status
- Replicate objects that were **already replicated** to additional destinations
- Replicate **replicas** (replication-to-replication chains)

> **Live replication only applies to NEW objects.** Objects uploaded before you set up replication will NOT be automatically copied. Use Batch Replication for existing objects.

---

### Two-Way (Bi-Directional) Replication

- Keeps objects and metadata in sync across multiple regions
- Used before configuring **Multi-Region Access Point failover**
- With **replica modification sync** — metadata changes (ACLs, tags, object locks) are also replicated back
- Ensures data written to the failover bucket is replicated back to the source

---

### Workload Requirements — Which Replication to Use

| Workload Requirement | S3 RTC (15-min SLA) | CRR | SRR |
|---|---|---|---|
| Replicate across different AWS accounts | ✅ | ✅ | ✅ |
| Replicate within same Region (24-48 hrs) | ❌ | ❌ | ✅ |
| Replicate across Regions (24-48 hrs) | ❌ | ✅ | ❌ |
| Predictable 15-minute SLA | ✅ | ❌ | ❌ |

---

### Creating a Replication Rule — Step by Step

#### Step 1 — Create Destination Bucket (Different Region)

```
Switch to target region (e.g., Oregon / us-west-2)
S3 → Create bucket → Name: barista908dr
→ Enable versioning on destination bucket (required for replication)
→ Create bucket
```

> **Versioning must be enabled on BOTH source and destination buckets** before setting up replication.

#### Step 2 — Create Replication Rule on Source Bucket

```
S3 → Source bucket → Management tab → Replication rules → Create replication rule

Replication rule name: DisasterRecoveryBarista908
Status: Enabled

Source:
  ○ Limit scope with prefix/tags
  ✅ Apply to all objects in the bucket

Destination:
  ✅ Choose a bucket in this account
  → Browse S3 → Select: barista908dr (Oregon region)
  (If bucket doesn't appear: refresh the page — cross-region takes a moment)

IAM role:
  ✅ Create new IAM role
  (Automatically creates permissions for source to copy to destination)

Encryption:
  Replicate SSE-KMS encrypted objects (optional — for KMS-encrypted buckets)

Destination storage class:
  ✅ Change the storage class for replicated objects
  → Select: Standard-IA or One Zone-IA
  (DR bucket won't be accessed frequently — no need for Standard)
```

#### Additional Replication Options

| Option | Description | Cost |
|---|---|---|
| **Replication Time Control (RTC)** | Replicates 99.99% of objects within 15 minutes — backed by SLA | Extra charge |
| **Replication metrics** | Monitor pending replication count, size, max time via CloudWatch | CloudWatch fees |
| **Delete marker replication** | Replicates delete markers created by S3 delete operations | Included |
| **Replica modification sync** | Replicates metadata changes from destination back to source | Included |

#### Step 3 — Handle Existing Objects

```
When saving the replication rule, AWS asks:
  "Do you want to replicate existing objects?"

  ○ Yes, replicate existing objects (Batch Replication) → ⚠️ Charges apply
  ✅ No, do not replicate existing objects → Free, only new objects replicate

→ Submit
```

> For practice labs: choose "Do not replicate existing objects" — only new uploads will be replicated, avoiding batch replication charges.

## 15. S3 Management Features Overview

### Inventory Configurations
- Generate flat file lists of all objects and their metadata on a schedule
- Useful for auditing, compliance reporting, and large-scale management
- Output as CSV or Apache ORC to a destination S3 bucket

### Metrics and Analysis
- **Replication metrics** — monitor replication lag, failures via CloudWatch
- **Storage class analysis** — identify objects suitable for lifecycle transitions
- **Request metrics** — view GET, PUT, DELETE request counts and latency

### Access Points
- Application-specific entry points into S3 buckets with individual permissions
- Enables **private access within a VPC** (covered in AWS VPC — Part 2)
- Each access point has its own hostname and access policy

## 16. S3 Cleanup

Deleting an S3 bucket requires two steps:

```
Step 1: Delete Lifecycle and Replication Rules
  Bucket → Management → Lifecycle rules → Delete
  Bucket → Management → Replication rules → Delete

Step 2: Empty the Bucket
  S3 → Select bucket → Empty
  → Type "permanently delete" → Confirm
  (Bucket still exists but has no objects)

Step 3: Delete the Bucket
  S3 → Select bucket → Delete
  → Type the bucket name → Confirm delete
  (Bucket is now gone — name becomes available again)
```

> **Order matters:** You cannot delete a non-empty bucket. Empty it first, then delete.

├── Lifecycle Rules (Cost Optimization)
│   ├── Runs once per day
│   ├── Transition current versions: Standard → IA → Glacier → Deep Archive
│   ├── Transition non-current versions: Same progression (slightly later)
│   ├── Expire objects: Delete marker at day 450 (versioned)
│   ├── Permanently delete non-current: Day 455
│   └── Delete incomplete multipart uploads: Day 15
│
├── Replication (Disaster Recovery)
│   ├── Types:
│   │   ├── Live (automatic, new objects only)
│   │   │   ├── CRR → different regions
│   │   │   └── SRR → same region
│   │   ├── Batch Replication → existing objects, on-demand
│   │   └── Two-way → bi-directional sync for failover
│   ├── Requirements:
│   │   ├── Versioning must be enabled on BOTH buckets
│   │   └── IAM role needed (create new role during setup)
│   ├── Options:
│   │   ├── RTC → 15-min SLA (extra cost)
│   │   ├── Delete marker replication
│   │   └── Replica modification sync
│   └── DR Design:
│       Source (N. Virginia, Standard) → Replicate → DR (Oregon, Standard-IA)
│
├── Other Management Features
│   ├── Server access logging → separate log bucket
│   ├── Inventory configurations → object audit reports
│   ├── Replication and storage class metrics
│   ├── Additional features → Transfer Acceleration, Object Lock, CORS, MFA Delete, ABAC
│   └── Access points → per-app access (VPC private access in Part 2)
│
└── Cleanup Order
    Delete lifecycle/replication rules → Empty bucket → Delete bucket
