# AWS Elastic File System (EFS) 

---

## 1. The Problem — Why Shared Storage?

Consider a website hosted on a **cluster of web servers** behind a load balancer where users upload images:

```
User uploads image
     ↓
Load Balancer
     ↓
Routes to Web01 → Image saved on Web01's local hard disk

User comes back later
     ↓
Load Balancer
     ↓
Routes to Web02 → Web02's hard disk has NO image → ❌ Image not found
```

> **This is the core problem with block storage (EBS / local disk)** — each server has its own isolated storage. Files uploaded to one server are not visible to another.

### The Solution — Shared (Centralized) Storage

```
Web01 ──┐
        ├──→ Shared Storage (NFS / EFS)
Web02 ──┘         ↑
Web03 ────────────┘  All servers read/write to the SAME location
```

- Each server keeps its **own block storage** for: OS, application, services
- **Shared files** (images, videos, documents that need to be accessible from any server) go into the **centralized shared storage**

### NFS — The Linux Shared Storage Protocol

In Linux, **NFS (Network File System)** is the standard shared storage protocol. Traditionally:
- You had to set up and manage an **NFS server** with its own hardware and disks
- Extra overhead: maintain the server, manage capacity, ensure availability

**Enter Amazon EFS** — NFS as a fully managed cloud service.

---

## 2. What is Amazon EFS?

> **Amazon Elastic File System (EFS)** is a simple, scalable, fully managed elastic NFS file system for use with AWS cloud services and on-premises resources.

- Provides **shared file storage** accessible from multiple EC2 instances simultaneously
- Scales **automatically to petabytes** — no capacity planning needed
- Works with **NFSv4 protocol** — standard Linux file sharing
- Accessible from **EC2 instances across AZs and Regions**, and from **on-premises** via AWS Direct Connect or VPN

### Key Benefits

| Benefit | Description |
|---|---|
| **Dynamic elasticity** | Automatically scales up/down as files are added/removed — no pre-provisioning |
| **Fully managed** | AWS manages the infrastructure — no patching, no maintenance |
| **Scalable performance** | Scales throughput and IOPS as file system grows; bursts for unpredictable needs |
| **Shared access** | Thousands of EC2 instances can access simultaneously |
| **Multi-AZ availability** | Regional file system spans multiple Availability Zones |
| **Performance** | Supports over 10 GB/sec and up to 500,000 IOPS for demanding workloads |

### EBS vs. EFS

| Feature | EBS (Elastic Block Store) | EFS (Elastic File System) |
|---|---|---|
| **Type** | Block storage | Shared file storage (NFS) |
| **Instances** | One EC2 instance at a time | Multiple EC2 instances simultaneously |
| **Protocol** | Block device (like a hard disk) | NFS (network file system) |
| **Scaling** | Fixed size (you choose) | Automatic — grows/shrinks |
| **Use case** | OS, databases, application storage | Shared files: images, videos, documents |
| **Zone** | Tied to one AZ | Regional (all AZs) or One Zone |

## 3. Architecture — EFS with Web Servers

```
                    Internet Users
                          ↓
                    Load Balancer
                   /             \
              Web01              Web02
         (EC2 Instance)    (EC2 Instance)
              |                   |
         /dev/xvda1          /dev/xvda1
         (EBS - OS)          (EBS - OS)
              |                   |
         /var/www/html/      /var/www/html/
              |                   |
              └─────── NFS ───────┘
                         ↓
              Amazon EFS File System
              (Shared - images stored here)
              /var/www/html/images  ← both servers mount this
```

Both servers see the same `/var/www/html/images` folder — any image uploaded through either server is immediately available to both.

## 4. EFS Security Group

> EFS is a **network service** — it requires its own security group to control which instances can connect to it.

### Why a Separate Security Group for EFS?

The EFS security group acts as a firewall controlling which EC2 instances can mount the file system. The rule should allow NFS traffic **only from the EC2 instances' security group**.

### Creating the EFS Security Group

```
EC2 → Security Groups → Create Security Group

Name:        inner-peace-efs-SG
Description: EFS security group for inner peace web servers

Inbound Rules:
  Type:     NFS
  Protocol: TCP
  Port:     2049
  Source:   [inner-peace-web-SG]  ← the EC2 instances' security group
  Description: Allow NFS access from web server security group

→ Create Security Group
```

> **Critical:** The source must be the **security group ID** of your EC2 instances — not an IP address. This means only instances in that security group can mount the EFS.

### Common Mistake — Security Group Mismatch

```
Problem: mount -a times out with:
  "Mount attempt 1/3 failed due to timeout after 15 sec"

Root Cause: Security group mismatch
  EFS SG allows NFS from: sg-0e7d8e188ed7969dd (old SG)
  EC2 instance uses:       sg-0a93cef736c97e238 (different SG)
  → EFS blocks the connection on port 2049

Fix: Edit EFS security group inbound rule
  → Change source to the ACTUAL security group of your EC2 instances
  → Run: mount -a  (no reboot needed)
```

## 5. Creating the EFS File System

```
AWS Console → EFS → File Systems → Create File System
→ Click "Customize" to see all options
```

### Step 1 — File System Settings

| Setting | Recommended | Description |
|---|---|---|
| **Name** | inner-peace-images | Descriptive name for the file system |
| **File system type** | Regional | Data stored across multiple AZs — highest availability |
| **One Zone** | (alternative) | Single AZ — lower cost but less resilient |
| **Automatic backups** | Off (for lab) | AWS Backup integration — extra cost |
| **Lifecycle → IA** | None (for lab) | Auto-move files to Infrequent Access after 30 days |
| **Lifecycle → Archive** | None | Auto-move to Archive after 90 days |
| **Encryption at rest** | ✅ On | All data stored encrypted (uses AWS KMS) |
| **Throughput mode** | Bursting | Scales with storage size; cheaper for most workloads |
| **Performance mode** | General Purpose | Ideal for web servers and most workloads |
| **Max I/O** | (alternative) | For highly parallelized workloads tolerating higher latency |

**Throughput Modes:**

| Mode | Description | Use Case |
|---|---|---|
| **Bursting** | Scales with storage; bursts when needed | Standard workloads — saves cost |
| **Enhanced** | Higher throughput regardless of storage size | Demanding workloads with consistent high throughput |

### Step 2 — Network Access (Mount Targets)

- EFS creates a **mount target** in each Availability Zone
- Each mount target needs a **security group** — use the EFS security group you created

```
Network access settings:
  VPC: default VPC (vpc-0a992fcd83f99cd60)

  Mount targets (one per AZ):
  us-east-1a → subnet → Security Group: inner-peace-efs-SG
  us-east-1b → subnet → Security Group: inner-peace-efs-SG
  us-east-1c → subnet → Security Group: inner-peace-efs-SG
  us-east-1d → subnet → Security Group: inner-peace-efs-SG
  us-east-1f → subnet → Security Group: inner-peace-efs-SG

  → Remove default security group from all subnets
  → Add your EFS security group to all subnets
```

### Step 3 — File System Policy (Optional)

Common policy options:
- Prevent root access by default
- Enforce read-only access by default
- Prevent anonymous access
- **Enforce in-transit encryption for all clients** ← recommended for production

## 6. Creating an Access Point

> An **Access Point** is an application-specific entry point into the EFS file system. It makes it easier to manage application access to shared datasets.

```
EFS → File Systems → Your file system → Access Points → Create Access Point

Settings:
  File system:         fs-07a5f040d8b06e501  (your EFS ID)
  Name:                inner-peace-images-ap
  Root directory path: /  (or specify a subdirectory)
  POSIX user:          (optional — for access control)
  Tags:                Name = inner-peace-ap

→ Create Access Point → Status: Available ✅
```

Note the **Access Point ID** (e.g., `fsap-0b801442161a6d0e2`) — you need this for fstab.

## 7. Installing EFS Client on EC2

The EC2 Linux OS doesn't understand EFS/NFS by default. You need the **amazon-efs-utils** package:

### Installation by OS

**Amazon Linux 2023 / Amazon Linux 2:**
```bash
sudo yum install -y amazon-efs-utils
```

**Ubuntu / Debian:**
```bash
sudo apt update
sudo apt install -y amazon-efs-utils
```

**Other Linux distributions (RHEL, CentOS):**
- Download from the AWS efs-utils GitHub repository
- Build and install as RPM package

### Successful Installation Output

```
Installing: amazon-efs-utils x86_64 3.1.2-1.amzn2023  amazonlinux  6.8 M
Installing dependencies: stunnel x86_64 5.58-1.amzn2023.0.2  156 k

Installed:
  amazon-efs-utils-3.1.2-1.amzn2023.x86_64
  stunnel-5.58-1.amzn2023.0.2.x86_64

Complete!
```

> `stunnel` is installed as a dependency — it provides **encryption in transit (TLS)** for the NFS connection.

## 8. Mounting EFS — Full Hands-On Lab

### Step 1 — Navigate to Web Root and Move Images

```bash
cd /var/www/html
ls
# → ABOUT THIS TEMPLATE.txt  css  fonts  images  index.html  js

# Move images to temp (frees the folder to become a mount point)
mv images /tmp/images/

# Restart web server
systemctl restart httpd

# Verify images folder is gone
ls
# → css  fonts  index.html  js  (no images)
```

### Step 2 — Create Empty Mount Point Directory

```bash
mkdir /var/www/html/images
cd /var/www/html/images
```

### Step 3 — Install EFS Client

```bash
sudo yum install -y amazon-efs-utils
```

### Step 4 — Get EFS IDs from Console

```
EFS → File Systems → Your file system
  File System ID:  fs-07a5f040d8b06e501

EFS → Access Points → Your access point
  Access Point ID: fsap-0b801442161a6d0e2
```

### Step 5 — Add Entry to /etc/fstab

```bash
vi /etc/fstab
```

Add this line at the end:
```
fs-07a5f040d8b06e501:/ /var/www/html/images efs _netdev,noresvport,tls,accesspoint=fsap-0b801442161a6d0e2 0 0
```

**Complete fstab example:**
```
UUID=5b3a24a5-c9d3-4d32-bb03-a87204afcc22  /          xfs   defaults,noatime  1  1
UUID=3AA3-AF31  /boot/efi  vfat  defaults,noatime,uid=0,gid=0,umask=0077,shortname=winnt  0  2
fs-07a5f040d8b06e501:/ /var/www/html/images efs _netdev,noresvport,tls,accesspoint=fsap-0b801442161a6d0e2 0 0
```

### fstab Field Explanation

| Field | Value | Description |
|---|---|---|
| `fs-07a5f040d8b06e501:/` | EFS File System ID + path | The EFS file system and root path |
| `/var/www/html/images` | Mount point | Local directory where EFS is mounted |
| `efs` | Filesystem type | Always `efs` when using EFS mount helper |
| `_netdev` | Option | Wait for network before mounting — **prevents boot lockup** |
| `noresvport` | Option | Use new TCP source port on reconnect — better availability |
| `tls` | Option | Encrypt data in transit |
| `accesspoint=fsap-...` | Option | Use EFS access point for this mount |
| `0` | Dump | Always 0 for EFS — no dump backup |
| `0` | fsck order | Always 0 for EFS — no filesystem check at boot |

> ⚠️ **`_netdev` is critical** — without it, your EC2 instance may become **unresponsive at boot** because it tries to mount the network file system before the network interface is up.

### Step 6 — Mount and Verify

```bash
# Before mount
df -h
# → No EFS entry

# Mount all filesystems from fstab
mount -a

# After successful mount
df -h
```

**Successful output:**
```
Filesystem        Size  Used  Avail  Use%  Mounted on
/dev/xvda1        8.0G  1.7G  6.3G   22%  /
tmpfs             481M     0  481M    0%  /dev/shm
127.0.0.1:/       8.0E     0  8.0E    0%  /var/www/html/images  ← EFS mounted ✅
```

> The `8.0E` (exabytes) shown as the size reflects EFS's **virtually unlimited elastic capacity** — it automatically grows as you add files.

### Step 7 — Restore Images

```bash
# Copy images back to the mount point (now stored in EFS)
cp -r /tmp/images/* /var/www/html/images/

# Restart Apache
systemctl restart httpd

# Access website → images load from EFS ✅
```

## 9. Troubleshooting — Mount Timeout

If `mount -a` fails with:
```
Mount attempt 1/3 failed due to timeout after 15 sec, wait 0 sec before next attempt.
Mount attempt 2/3 failed due to timeout after 15 sec, wait 0 sec before next attempt.
```

**Diagnosis and Fix:**

```
Cause: Security group mismatch
  EFS SG (sg-034f65bbeae4d1a38) allows port 2049 from wrong security group
  EC2 instance SG (sg-0a93cef736c97e238) is not allowed through

Fix — Option 1 (Recommended): Update EFS Security Group
  EC2 → Security Groups → Select EFS security group (sg-034f65bbeae4d1a38)
  → Edit Inbound Rules
  → Add: NFS | TCP | 2049 | Source: sg-0a93cef736c97e238 (EC2 SG)
  → Save Rules
  → Run: mount -a (no reboot needed)

Fix — Option 2: Attach secondary SG to EC2
  → Add the SG that EFS already allows as a secondary security group on the EC2 instance
```

## 10. Automatic Mounting on Reboot

The `/etc/fstab` entry with `_netdev` ensures EFS automounts when the instance reboots:

```
Boot sequence:
1. Instance powers on
2. Network interface comes up
3. OS reads /etc/fstab → sees efs entry with _netdev
4. Waits for network → connects to EFS mount target → mounts
5. Apache starts → serves images from EFS ✅
```

**Test before relying on it:**
```bash
# Unmount
umount /var/www/html/images

# Re-mount via fstab
mount -a

# Verify
df -h | grep images
```

## 11. Creating AMI with EFS Mount Configured

After setting up EFS, create an AMI so future instances automatically connect:

```
EC2 → Instances → Select instance (with EFS mounted and /etc/fstab configured)
→ Actions → Image and Templates → Create Image

Name: inner-peace-EFS
Description: AMI with EFS mount point for shared images

→ Create Image → Wait for: available ✅
```

When launching new instances from this AMI:
- `/etc/fstab` entry already exists
- On boot, instance **automatically mounts EFS** — no manual steps needed
- All instances in the cluster share the same EFS files

## 12. EFS Storage Classes and Lifecycle Management

| Storage Class | Access Pattern | Cost vs Standard |
|---|---|---|
| **Standard** | Frequently accessed files | Baseline cost |
| **Infrequent Access (IA)** | Files not accessed for 30 days | ~92% cheaper |
| **Archive** | Rarely accessed (90+ days) | Lowest cost |

**Configure lifecycle transitions:**
```
EFS → File System → Edit → Lifecycle management
  Transition to IA:       30 days since last access
  Transition to Archive:  90 days since last access (optional)
  Transition back to Standard: On first access
```
