# AWS Systems Manager (SSM) & CloudShell

---

## 1. What is AWS Systems Manager?

> **AWS Systems Manager (SSM)** is a powerful operations management service that helps you **manage and operate nodes at scale** — on AWS, on-premises, and in hybrid and multicloud environments.

- Provides a **centralized view** of your entire infrastructure
- Enables **secure remote management** without needing SSH or open ports
- Can **execute commands on one or hundreds of instances simultaneously**
- Automates operational tasks: patching, user management, software installation, registry edits

### Key Use Cases

| Use Case | Description |
|---|---|
| **Browser-based shell access** | SSH into EC2 instances without keys or open port 22 |
| **Run commands at scale** | Execute shell commands/scripts on one or many instances at once |
| **Patch management** | Automatically apply OS security patches across your fleet |
| **Inventory collection** | Collect metadata from managed nodes every 12 hours |
| **Parameter Store** | Store configuration variables and secrets securely |
| **Compliance management** | Track and enforce operational standards |
| **Incident management** | Centralized operations center for alerts and issues |

### Real-World Scale Example

> Imagine managing **hundreds of EC2 instances** and needing to restart a service or apply a patch on all of them simultaneously — instead of SSH-ing into each one, you run **one command** through Systems Manager and it executes on all instances at once.

### Enhance Visibility Across Infrastructure

- **Inventory metadata** collected from managed nodes every 12 hours
- **SSM Agent** updated automatically every 14 days
- Automated OS patching at scale

## 3. How EC2 Connects to SSM — IAM Role

For an EC2 instance to be managed by SSM, it needs **permission to communicate with the SSM service**. This is granted through an **IAM Role** attached to the instance.

```
EC2 Instance
     │
     │  Needs permission to connect to SSM
     ↓
IAM Role (SSMManagedInstanceCore)
     │
     │  Grants the EC2 instance the right to register and communicate
     ↓
AWS Systems Manager Service
```

> Unlike IAM users (which are for humans), **IAM Roles are for services communicating with other services**.

## 4. Setting Up SSM Access — Step by Step

### Step 1 — Create the IAM Role

```
AWS Console → IAM → Roles → Create Role

1. Trusted entity: AWS Service
2. Use case: EC2
3. Click Next → Search for policy:
   → "AmazonSSMManagedInstanceCore"
   → Select this policy
4. Click Next → Give role a name:
   → "SSMManagedInstanceCore"
5. Add description (same as name)
6. Click "Create role"
```

### Step 2 — Launch EC2 Instance

```
EC2 → Launch Instance
→ Name: Server1
→ AMI: Ubuntu Server 24.04 LTS (Free Tier eligible)
→ Instance Type: t2.micro or t3.micro
→ Key Pair: Select existing (optional — not needed for SSM login)
→ Security Group: Select existing
→ Launch Instance
```

> ⚠️ For SSM access, you **don't need port 22 open** in the security group — SSM uses outbound HTTPS (port 443) which is allowed by the default outbound rule.

### Step 3 — Attach the IAM Role to the Instance

```
EC2 → Instances → Select your instance
→ Actions → Security → Modify IAM Role
→ Select "SSMManagedInstanceCore" from the dropdown
→ Click "Update IAM Role"
```

### Step 4 — Verify in Systems Manager

```
AWS Systems Manager → Session Manager → Start Session

(Wait a few minutes for the instance to register)

→ Your instance should appear in the list
```

> If the instance doesn't appear, verify the IAM role is correctly attached and wait a few minutes — the SSM Agent needs time to register.

## 5. Session Manager — Browser-Based SSH

**Session Manager** allows you to start an interactive shell session with an EC2 instance **directly from the browser** — no SSH keys, no bastion hosts, no port 22 required.

### Starting a Session

```
Systems Manager → Session Manager → Start Session

1. Select your instance (e.g., Server1)
2. (Optional) Enter a reason: "shell access"
3. Click Next → Next → Start Session
4. A new browser tab opens with an interactive terminal
```

**Example session:**

```bash
# Switch to root user
sudo -i

# Verify OS
cat /etc/os-release
# → NAME="Ubuntu", VERSION="24.04"

# Run any command you need
whoami
# → root

hostname
# → ip-172-31-20-186
```

### SSH vs. Session Manager

| Feature | Traditional SSH | Session Manager |
|---|---|---|
| **Port 22 required** | ✅ Yes | ❌ No |
| **Key pair required** | ✅ Yes | ❌ No |
| **Security group rule needed** | ✅ Yes (port 22) | ❌ No |
| **Works from browser** | ❌ No | ✅ Yes |
| **Audit logging** | ❌ Manual | ✅ Built-in (CloudWatch/S3) |
| **IAM role required** | ❌ No | ✅ Yes (SSMManagedInstanceCore) |

## 6. Run Command — Execute Commands on Multiple Instances

**Run Command** lets you execute shell commands or scripts on **one or many EC2 instances simultaneously** — without logging into each one.

### Starting a Run Command

```
Systems Manager → Run Command → Run a Command

1. Command document: Search "AWS-RunShellScript"
   → Select "AWS-RunShellScript"

2. Commands field: Enter your commands
   Example:
   hostname
   whoami
   uptime

3. Targets:
   ├── By tag: Execute on all instances with a specific tag
   │   Example: Key=Project, Value=DevOps
   │   → Runs on ALL instances with that tag
   └── Manual: Select specific instances from a list

4. (Optional) Output:
   ├── S3 bucket: Store full output for long commands
   └── CloudWatch Logs: Stream output to log groups

5. Click "Run"
```

### Successful Run Command Output

```
Command ID: 2292cefd-eedf-4561-b789-d970431d6bbf

Instance: i-03bac81c03bbbece8 (Server1)
Status: Success
Detailed status: Success
Response code: 0
Start time: Tue, 09 Jun 2026 22:28:32 GMT
Finish time: Tue, 09 Jun 2026 22:28:34 GMT
```

> **Response code 0** = command executed successfully. Any non-zero response code indicates an error.

### Example Commands

**Basic verification:**
```bash
hostname
whoami
systemctl is-active apache2
```

**Install and start a web server:**
```bash
apt update
apt install apache2 -y
systemctl enable apache2
systemctl start apache2
systemctl status apache2 --no-pager
```

**Verify web server locally:**
```bash
curl -I http://127.0.0.1
# Expected: HTTP/1.1 200 OK
```

### Understanding the Output Warning

```
WARNING: apt does not have a stable CLI interface. Use with caution in scripts.
```

> This is a **harmless Ubuntu warning** when `apt` is used inside automation/scripts. It is **not an error** and does not cause failure — `Response code: 0` confirms success.

### Output Limit

> Systems Manager truncates console output at **24,000 characters**. For long commands (like `apt update`), store output in an **S3 bucket** or **CloudWatch Logs** to view the complete result.

### Targeting Instances by Tag

```
Target selection: Specify instance tags
Key:   Project
Value: DevOps

→ Command will execute on ALL instances tagged Project=DevOps
→ Could be 1 instance or 1,000 — same single Run Command
```

## 8. AWS CloudShell

**CloudShell** is a browser-based command line environment built directly into the AWS Console — with AWS CLI pre-installed and automatically authenticated with your current account.

### Key Advantages

| Feature | Traditional AWS CLI | CloudShell |
|---|---|---|
| **AWS CLI installation** | ❌ Must install manually | ✅ Pre-installed |
| **Access key setup** | ❌ Must configure manually | ✅ Auto-authenticated |
| **Authentication** | Access Key ID + Secret | Your console login session |
| **Availability** | Your local machine | Any browser, anywhere |
| **Amazon Q access** | Separate tool | ✅ Built-in |

### Using CloudShell

```
AWS Console → Click the CloudShell icon (terminal icon in top navigation)
OR
Open in a new tab for a larger workspace
```

**Run any AWS CLI command immediately — no setup needed:**

```bash
# List EC2 instances
aws ec2 describe-instances

# List S3 buckets
aws s3 ls

# Get account identity
aws sts get-caller-identity
```

### When to Use CloudShell

- Quick one-off AWS CLI commands from the browser
- When you don't have AWS CLI installed locally
- Learning and testing CLI commands before scripting
- Using alongside Amazon Q for instant command generation and execution

## 9. The Three Tools — When to Use Which

| Tool | Best For |
|---|---|
| **Session Manager** | Interactive shell access to a specific EC2 instance without SSH |
| **Run Command** | Execute commands across one or many instances simultaneously |
| **CloudShell** | Run AWS CLI commands from the browser — no local setup needed |

> As a DevOps engineer, knowing **all three** tools and choosing the right one for the situation is what matters.
