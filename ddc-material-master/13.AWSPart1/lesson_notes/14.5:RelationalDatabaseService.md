# AWS RDS (Relational Database Service) 

---

## 1. What is Amazon RDS?

> **Amazon Relational Database Service (RDS)** is a managed web service that makes it easier to set up, operate, and scale a relational database in the AWS Cloud. It provides cost-efficient, resizable capacity and manages common database administration tasks automatically.

### The Database Administration Problem RDS Solves

Traditional database administration requires handling many time-consuming tasks:

| Task | Why It's Hard |
|---|---|
| **Initial setup** | Installing and configuring the DB engine |
| **Regular patching** | OS and database software updates |
| **Continuous monitoring** | Watching performance, catching issues early |
| **Performance tuning** | Query optimization, index management |
| **Backups** | Regular backups to recover from failure — critical for business |
| **Scaling** | Adding capacity as business grows — very difficult for SQL databases |
| **Security** | Keeping data secure — breaches are extremely damaging |
| **Hardware upgrades** | Physical server lifecycle management |
| **Storage management** | Scaling storage as data grows |

> **AWS RDS automates most of these tasks for you.**

---

## 2. Advantages of Amazon RDS

| Advantage | Description |
|---|---|
| **Familiar engines** | Use database engines you already know: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, IBM Db2 |
| **Managed operations** | AWS handles backups, software patching, automatic failure detection, and recovery |
| **Automated backups** | Turn on automated backups or create manual snapshots — reliable restore process |
| **High availability** | Primary + synchronous secondary instance you can fail over to |
| **Read scaling** | Use read replicas to distribute read traffic and improve performance |
| **Access control** | IAM integration for users/permissions, plus VPC isolation |

## 3. Responsibility Comparison — On-Premises vs. EC2 vs. RDS

| Feature | On-Premises | Amazon EC2 | Amazon RDS |
|---|---|---|---|
| Application optimization | Customer | Customer | Customer |
| Scaling | Customer | Customer | **AWS** |
| High availability | Customer | Customer | **AWS** |
| Database backups | Customer | Customer | **AWS** |
| DB software patching | Customer | Customer | **AWS** |
| DB software install | Customer | Customer | **AWS** |
| OS patching | Customer | Customer | **AWS** |
| OS installation | Customer | Customer | **AWS** |
| Server maintenance | Customer | AWS | AWS |
| Hardware lifecycle | Customer | AWS | AWS |
| Power, network, cooling | Customer | AWS | AWS |

> **Running a database on EC2 yourself** means you're prone to user errors — manually patching the OS or database software can accidentally cause downtime, and troubleshooting takes hours. **RDS eliminates this risk** by managing the database layer entirely.

### RDS Shared Responsibility Model

```
AWS Responsibility:
  → Hosting software components and infrastructure of DB instances/clusters

Your Responsibility:
  → Query tuning (adjusting SQL queries for performance)
  → Database design, data distribution
  → Monitoring with Performance Insights and other tools
```

## 4. DB Instances — The Basic Building Block

> A **DB instance** is an isolated database environment in the AWS Cloud. It can contain one or more user-created databases, and you access it using the same tools you'd use with a standalone database.

```
VPC (spans 2 Availability Zones)
├── AZ-1: DB Instance, DB Instance
└── AZ-2: DB Instance, DB Instance
```

You can create and manage DB instances via: **AWS Management Console**, **AWS CLI**, or the **Amazon RDS API**.

## 5. Typical RDS Application Architecture

```
Internet Users
     ↓
Elastic Load Balancer
     ↓ (distributes traffic)
Application Servers (EC2 — Public Subnets, multiple AZs)
     ↓ (private connection)
RDS DB Instances (Private Subnets, multiple AZs)
     ↓ (replication)
Read Replica (Private Subnet)
```

| Component | Role |
|---|---|
| **Elastic Load Balancer** | Routes user traffic to application servers |
| **Application Servers (EC2)** | Reside in public subnets, interact with RDS |
| **RDS DB Instances** | Reside in private subnets — **no direct internet access** |
| **Read Replica** | Receives replicated data from primary — improves read performance |

> **Key security design:** RDS instances live in **private subnets**, meaning internet users cannot access them directly — only application servers within the same VPC can connect.

## 7. Amazon Aurora — RDS's Premium Engine

> **Amazon Aurora** is a separate, AWS-built database service — a serverless, relational database compatible with MySQL and PostgreSQL, designed for higher performance and lower cost than the standard engines.

### Aurora Key Stats

| Metric | Aurora Advantage |
|---|---|
| **Cost** | ~1/10th the cost of commercial databases |
| **Throughput (MySQL)** | 5x faster than standard MySQL |
| **Throughput (PostgreSQL)** | 3x faster than standard PostgreSQL |
| **Throughput (general)** | Up to 6x the throughput of PostgreSQL and MySQL |
| **Availability** | Up to 99.99% single-Region, 99.999% multi-Region |
| **Scaling** | Removes the difficulty of scaling SQL databases — near-instant |

### Aurora Benefits

| Benefit | Description |
|---|---|
| **High performance** | Powers internet-scale apps; fastest distributed SQL with Aurora DSQL |
| **High availability** | Fault-tolerant distributed storage for continuous access |
| **Easy scaling** | Automatically scales to any workload demand |
| **Cost-effective** | Serverless option — pay only for capacity consumed, save up to 90% |
| **Easy migration** | Standard tools to migrate MySQL/PostgreSQL; Babelfish for SQL Server compatibility |

### Aurora Use Cases

- **Modernizing enterprise applications** — CRM, ERP, supply chain, billing
- **Building SaaS applications** — multi-tenant, flexible scaling
- **Globally distributed apps** — mobile games, social media, online services
- **Going serverless** — hands-off capacity management

### Real-World Aurora Examples

| Company | Use Case |
|---|---|
| **BMW** | Increased scalability and reduced costs with Aurora Serverless |
| **Samsung** | Migrated 1.1 billion users from Oracle to Aurora |
| **Coinbase** | Built an ultra-low-latency cryptocurrency exchange |

> **When to choose Aurora vs. standard RDS:** If you already use MySQL or PostgreSQL and want better performance at lower cost without managing licensing, Aurora is the better choice. Standard RDS MySQL/PostgreSQL is simpler and has free tier options.

## 8. DB Instance Classes

> The **DB instance class** determines the compute and memory capacity of your database — similar to choosing an EC2 instance type.

| Class Type | Prefix | Best For |
|---|---|---|
| **General purpose** | db.m* | Balanced workloads |
| **Memory optimized** | db.z*, db.x*, db.r* | High-performance production databases |
| **Compute optimized** | db.c* | CPU-intensive workloads |
| **Burstable performance** | db.t* | Dev/test, free tier, low/variable load |

> Example: `db.m7g.2xlarge` — 7th generation, general purpose, powered by AWS Graviton3, size 2xlarge. You can resize your instance class later (e.g., scale up from 2xlarge to 4xlarge).

---

## 9. DB Instance Storage Types

| Storage Type | Best For | Notes |
|---|---|---|
| **General Purpose (gp3/gp2)** | Dev/test, medium workloads | Cost-effective, most common choice |
| **Provisioned IOPS (io1/io2)** | I/O-intensive production databases | Low latency, consistent throughput, not free |
| **Magnetic** | Backward compatibility only | Not recommended for new workloads |

> **Minimum allocated storage: 20 GiB.** Storage requirements vary by engine and storage type.

## 10. Multi-AZ Deployment Options

RDS offers three deployment models for availability:

### Single-AZ DB Instance (1 instance)
```
Primary instance only — no standby
Uptime: 99.5%
No data redundancy
```

### Multi-AZ DB Instance Deployment (2 instances)
```
Primary instance (Write/Read endpoint)
     ↓ synchronous replication
Standby instance (different AZ, no endpoint — not readable)

Uptime: 99.95%
If primary fails → standby takes over
```

### Multi-AZ DB Cluster Deployment (3 instances)
```
Primary instance (Write/Read endpoint)
     ↓ replication
Readable Standby #1 (different AZ)
Readable Standby #2 (different AZ)

Uptime: 99.95%
Both standbys CAN serve read traffic
Up to 2x faster transaction commit latency
Automatic failover typically under 35 seconds
```

| Deployment | Instances | Standby Readable? | Uptime SLA |
|---|---|---|---|
| Single-AZ | 1 | N/A | 99.5% |
| Multi-AZ DB instance | 2 | ❌ No | 99.95% |
| Multi-AZ DB cluster | 3 | ✅ Yes (both) | 99.95% |

### Multi-AZ vs. Read Replicas — Key Distinction

| Concept | Purpose | Behavior |
|---|---|---|
| **Multi-AZ** | High availability | Secondary takes over (becomes primary) if primary fails |
| **Read Replica** | Performance scaling | Continuously synced copy; handles READ queries only; doesn't take over on failure |

> Multi-AZ = availability/failover. Read replica = read performance scaling. Developers point read queries at the read replica endpoint in their application code — since most application traffic is reads, this dramatically improves performance.

## 12. Access Control with Security Groups

A common architecture: RDS instance privately accessible only from an application's EC2 instance.

```
EC2 Instance (web server)
  Security Group: ec2-rds-sg
  ├── Inbound: HTTP from internet (public web traffic)
  └── This EC2 instance belongs to security group "ec2-rds-sg"

RDS Instance
  Security Group: rds-ec2-sg
  └── Inbound: Port 3306 (MySQL) allowed FROM "ec2-rds-sg"

Result:
  ✅ EC2 can access RDS (allowed by RDS's security group rule)
  ❌ Internet users CANNOT access RDS directly (no public inbound rule)
```

> This is the same security group pattern seen with ALB → EC2 instances: **the source of an inbound rule is another security group ID**, not an IP range.

## 13. Creating a MySQL RDS Instance — Step by Step

### Step 1 — Choose Database Creation Method

```
RDS → Databases → Create Database

Method:
  ○ Easy create   → quick setup, fewer options
  ✅ Standard create → full control over all settings
```

### Step 2 — Engine Options

```
Engine type: MySQL
  (Alternatives: Aurora MySQL/PostgreSQL-Compatible, PostgreSQL,
   MariaDB, Oracle, SQL Server, IBM Db2)

Engine version: 8.4.8 (or latest default)
```

### Step 3 — Templates

| Template | Use Case | Cost |
|---|---|---|
| **Production** | High availability, multi-AZ, optimized storage | Not free |
| **Dev/Test** | Single instance, general purpose storage | Can select free options manually |
| **Free Tier** | Learning, hands-on practice | Free (with eligible instance class) |

> For learning: select **Free Tier**, or **Dev/Test** if you want to see more configuration options while staying within free tier eligible settings.

### Step 4 — Availability and Durability

```
Deployment options:
  ○ Multi-AZ DB cluster deployment (3 instances)
  ○ Multi-AZ DB instance deployment (2 instances)
  ✅ Single DB instance (1 instance) ← select this for free tier/learning
```

### Step 5 — Settings

```
DB instance identifier: vprofileMySQLServer

Credentials:
  Master username: admin (default, can change)
  Credentials management:
    ○ Managed in AWS Secrets Manager (most secure, not free)
    ✅ Self managed → Auto generate password (recommended for learning)
```

> ⚠️ **Save your credentials immediately** after creation — view via "View credential details" in the creation banner. You cannot retrieve the password again later (only reset it).

### Step 6 — Instance Configuration

```
DB instance class:
  Standard classes (db.m*)       → general workloads
  Memory optimized (db.r*, db.x*) → high-performance production
  ✅ Burstable classes (db.t3.micro) → free tier eligible

Instance type: db.t3.micro (2 vCPUs, 1 GiB RAM)
```

### Step 7 — Storage

```
Storage type: General Purpose SSD (gp3)
Allocated storage: 20 GiB (minimum)

Additional storage configuration:
  Storage autoscaling: Optional (off for learning — no load expected)
  Maximum storage threshold: set if autoscaling enabled
```

### Step 8 — Connectivity

```
Compute resource:
  ○ Connect to an EC2 compute resource (auto-configures security group)
  ✅ Don't connect to an EC2 compute resource (manual setup — more learning)

VPC: Default VPC
DB subnet group: default (covered in detail in AWS VPC — Part 2)

Public access:
  ○ Yes → RDS gets a public IP — accessible from outside VPC
  ✅ No  → Private only — most common for production security

VPC security group (firewall):
  ✅ Create new → name it (e.g., vproMySQLRDS-sg)

Availability Zone: No preference (single instance)

Additional configuration:
  Database port: 3306 (default for MySQL)
```

### Step 9 — Database Authentication

```
○ Password authentication ✅ (simplest, used for CLI access)
○ Password and IAM database authentication
○ Password and Kerberos authentication
```

### Step 10 — Monitoring

```
Enhanced Monitoring: Off (for learning — adds cost, ~1 second granularity)
Log exports to CloudWatch Logs:
  ☐ Audit log
  ☐ Error log
  ☐ General log
  ☐ Slow query log
  (Select based on what you need to troubleshoot later)
```

### Step 11 — Additional Configuration

```
Initial database name: accounts
  (If you don't specify a name, RDS does not create a database automatically)

DB parameter group: default.mysql8.4 (advanced engine settings)
Option group: default:mysql-8-4

Encryption: ☐ Disabled for learning (KMS keys take 7 days to fully delete — hassle for labs)

Backup:
  ✅ Enable automated backups (recommended for production)
  Retention period: up to 35 days
  Backup window: select or no preference

Maintenance:
  Auto minor version upgrade: optional
  Maintenance window: no preference

Deletion protection: ☐ Off for learning (prevents accidental deletion when on)
```

> ⚠️ The console shows an **estimated monthly cost** before creation (e.g., ~$14.71/month for db.t3.micro + 20GB gp3). This doesn't apply if you're within free tier — but make sure to delete the instance after your lab to avoid charges.

### Step 12 — Create Database

```
→ Click "Create Database"
→ Click "View credential details" → SAVE username and password immediately
→ Wait for status: creating → available
```

## 14. Connecting to RDS from an EC2 Instance

### Step 1 — Launch a Client EC2 Instance

```
EC2 → Launch Instance
  Name: MySQL-client
  AMI: Amazon Linux 2023 (or Ubuntu)
  Type: t2.micro
  Key pair: rdssqlclient
  Security group: rdssqlclient-sg (allow SSH port 22 from My IP)
→ Launch
```

### Step 2 — Update RDS Security Group

```
RDS Instance → Security group → Edit inbound rules

Add rule:
  Type:   MySQL/Aurora
  Port:   3306
  Source: [EC2 client instance's security group ID]
          (NOT "My IP" — the EC2 instance connects from within the VPC)

→ Save rules
```

> ⚠️ The default rule (port 3306 from "My IP") is useless for this setup — your RDS is **private**, so it can only be reached from inside the VPC. The source must be the **EC2 instance's security group**, not your personal IP.

### Step 3 — SSH to the EC2 Instance

```bash
ssh -i rdssqlclient.pem ec2-user@<public-ip>
# (use ubuntu@ instead of ec2-user@ if using Ubuntu AMI)
```

### Step 4 — Install MySQL Client

**On Amazon Linux 2023:**
```bash
sudo dnf update -y

# Note: "mysql-client" package name does NOT exist on Amazon Linux 2023
sudo dnf install mysql-client -y
# → Error: Unable to find a match: mysql-client

# Correct package for Amazon Linux 2023:
sudo dnf install mariadb105 -y
```

**Successful installation:**
```
Installing: mariadb105 x86_64 3:10.5.29-1.amzn2023.0.1  1.5 M
Installing dependencies: mariadb-connector-c, mariadb105-common, perl-Sys-Hostname

Installed:
  mariadb105-3:10.5.29-1.amzn2023.0.1.x86_64

Complete!
```

```bash
# Verify
mysql --version
# → mysql Ver 15.1 Distrib 10.5.29-MariaDB, for Linux (x86_64)
```

**On Ubuntu:**
```bash
sudo apt update
sudo apt install mysql-client -y
```

> ⚠️ **Common confusion:** `apt` is for Ubuntu/Debian; `dnf` is for Amazon Linux 2023; `yum` is for Amazon Linux 2. Running `apt` on Amazon Linux gives: `-bash: apt: command not found`. Check your OS first with `cat /etc/os-release`.

### Step 5 — Connect to RDS

```bash
mysql -h <RDS-ENDPOINT> -u admin -p
# Example:
mysql -h vprofilemysqlserver.c6ns68ok2vxd.us-east-1.rds.amazonaws.com -u admin -p
# → Enter password: ********
```

> ⚠️ **Security note:** Passing the password directly on the command line (`-pYourPassword` with no space) is convenient for labs but **not recommended in real environments** — it can be exposed in shell history and process lists. Use `-p` alone and enter it at the interactive prompt instead.

**Successful connection:**
```
Welcome to the MariaDB monitor.  Commands end with ; or \g.
Your MySQL connection id is 56
Server version: 8.4.8 Source distribution
```

```sql
MySQL [(none)]> show databases;
+--------------------+
| Database           |
+--------------------+
| accounts           |
| information_schema |
| mysql              |
| performance_schema |
| sys                |
+--------------------+
5 rows in set (0.005 sec)
```

> The `accounts` database is the one you specified during RDS creation (Initial database name).

## 15. Troubleshooting Connection Issues

| Error | Cause | Fix |
|---|---|---|
| `Access denied for user 'root'@...` | Wrong username, or username not specified | Use `-u admin` (or your master username) |
| `Unknown database '<password>'` | Password typed without `-p` prefix attached correctly | Use `-p<password>` with NO space, or just `-p` and enter interactively |
| **Connection timeout** | Security group not allowing access | Add inbound rule on RDS SG: port 3306 from EC2 instance's SG |
| **Authentication error** | Wrong username/password | Double check credentials saved during creation |

```
Decision tree:
  Timeout?           → Security group problem (port 3306 not allowed from EC2 SG)
  Authentication error? → Username/password problem (check saved credentials)
```

## 20. Billing

```
Charged by:
  → DB instance hours (on-demand or reserved)
  → Storage (GB allocated)
  → I/O requests (for certain storage types)
  → Backup storage beyond free allowance
  → Data transfer
```

> **On-demand** instances charge by the hour with no commitment. **Reserved** instances offer discounts for 1 or 3-year commitments — useful for predictable, long-running production workloads.

## 21. Cleanup

```
Step 1: Delete the RDS instance
  RDS → Databases → Select instance → Actions → Delete

  Final snapshot prompt:
    ☐ Uncheck "Create final snapshot" (for lab/practice — no production data)
    ✅ Check "I acknowledge..."
    Type: delete me
  → Delete

Step 2: Terminate the EC2 client instance
  EC2 → Select instance → Instance State → Terminate

Step 3: Verify cleanup
  RDS → Snapshots → delete any automated/manual backups if present
  EC2 → Confirm 0 running instances
```

> ⚠️ If you enabled automated backups, check the **Snapshots** section after deleting the instance — leftover snapshots can still incur storage charges.
