# AWS CloudWatch

---

## 1. What is AWS CloudWatch?

> **Amazon CloudWatch** is a monitoring and observability service that monitors AWS resources and the applications you run on AWS in **real time**. It provides system-wide visibility into application performance, operational health, and resource utilization.

CloudWatch has expanded far beyond basic monitoring. It now includes:

| Capability | Description |
|---|---|
| **Metrics** | Collect and track key performance data at user-defined intervals |
| **Alarms** | Monitor metrics against thresholds and trigger notifications or automated actions |
| **Dashboards** | Unified visualization of metrics and logs in a single place |
| **Logs** | Collect, store, and query logs from AWS services and applications |
| **Events** | Real-time stream of changes happening in your AWS environment |
| **Application Performance Monitoring (APM)** | Detect and monitor latency, error rates, request rates |
| **Infrastructure Monitoring** | Database Insights, Lambda Insights, Container Insights |
| **Network Monitoring** | Internet Monitor, Network Flow Monitor |

---

## 2. How CloudWatch Works — The Architecture

```
AWS Services (EC2, EBS, S3, RDS, ALB, etc.)
     ↓  Automatically send metrics
CloudWatch (Collects & stores metrics)
     ↓  Alarms evaluate metrics against thresholds
Alarm State → Notification / Action
     ↓
SNS (Simple Notification Service)
     ↓
Email / SMS / Lambda / EC2 Action
```

**Three services in a typical monitoring setup:**

```
EC2 Instance        →    CloudWatch        →    SNS
(generates metrics)     (collects + alarms)     (sends notification)
```

## 3. CloudWatch Metrics

> **Metrics** are the primary thing in CloudWatch — they are the numerical measurements of performance collected over time.

- Every AWS service you use **automatically generates standard metrics** — no setup required
- You can also create **custom metrics** to track application-specific data
- Metrics are collected at regular **periods** (intervals)

### Default EC2 Metrics

When you launch an EC2 instance, CloudWatch automatically collects these metrics:

| Metric | Description |
|---|---|
| **CPU Utilization** | Percentage of allocated compute units in use |
| **Network In** | Bytes received on all network interfaces |
| **Network Out** | Bytes sent on all network interfaces |
| **Network Packets In** | Count of packets received |
| **Network Packets Out** | Count of packets sent |
| **Disk Read Ops** | Completed disk read operations |
| **Disk Write Ops** | Completed disk write operations |
| **Disk Read Bytes** | Bytes read from disk |
| **Disk Write Bytes** | Bytes written to disk |
| **CPU Credit Usage** | CPU credits consumed (T2/T3 burst instances) |
| **CPU Credit Balance** | CPU credits available for burst |

### Default EBS Volume Metrics

| Metric | Description |
|---|---|
| **Read Bandwidth** | Bytes read per second |
| **Write Bandwidth** | Bytes written per second |
| **Read Throughput** | Read operations per second |
| **Write Throughput** | Write operations per second |

> Other services like S3, RDS, ALB, Lambda all have their own default metrics. Whenever you use a service, CloudWatch sets up metrics for it automatically.

## 4. Monitoring Intervals

| Monitoring Type | Collection Interval | Cost |
|---|---|---|
| **Basic Monitoring** (default) | Every **5 minutes** | ✅ Free |
| **Detailed Monitoring** | Every **1 minute** | ❌ Additional charge |

> For learning and labs, use basic monitoring — just wait a bit longer for data to appear. Detailed monitoring is useful in production when you need faster alerting.

**Enable Detailed Monitoring:**
```
EC2 → Select Instance → Monitoring tab
→ Manage Detailed Monitoring → Enable → Confirm
```

## 6. CloudWatch Events

> CloudWatch **Events** provide a **real-time stream** of changes happening in your AWS environment.

**Example events captured:**
- Launching an EC2 instance
- Terminating an EC2 instance
- Taking a snapshot
- Creating a volume
- State changes in any AWS service

**What you can do with events:**
- Set **triggers** based on events
- Integrate with **Lambda functions** — automatically execute code when an event occurs
- Route events to **SNS, SQS, or other targets**

---

## 7. CloudWatch Logs

> CloudWatch **Logs** provides comprehensive log management — collect, store, search, and analyze logs from AWS services and custom applications.

**Key features:**
- Logs stored in **Log Groups** and **Log Streams**
- **CloudWatch Logs Insights** — interactive fast queries (SQL, PPL query languages)
- **Log anomaly detection** — finds unusual patterns automatically
- **Metric filters** — extract numbers from logs and generate CloudWatch metrics
- **Subscription filters** — route logs in real time to S3, Kinesis Firehose

**EC2 log collection:**
> EC2 instances don't stream logs automatically. You install the **CloudWatch Agent** on the OS, which streams logs to CloudWatch. (Covered in AWS Part 2 of the course.)

## 8. CloudWatch Alarms

> **Alarms** continuously monitor metrics against user-defined thresholds. When a threshold is breached, they can send notifications or trigger automated actions.

### Alarm States

| State | Meaning |
|---|---|
| **OK** | Metric is within the defined threshold — no issue |
| **ALARM** | Metric has breached the threshold — action triggered |
| **INSUFFICIENT DATA** | Not enough data yet to evaluate the alarm |

### Alarm Actions Available

| Action Type | Description |
|---|---|
| **SNS Notification** | Send email, SMS, or trigger Lambda |
| **EC2 Action** | Stop, terminate, reboot, or recover the instance |
| **Auto Scaling** | Scale out or scale in your Auto Scaling group |
| **Systems Manager** | Trigger SSM Run Command or Automation |
| **Lambda** | Execute a Python/Node script to take custom action |

## 9. SNS — Simple Notification Service

> **SNS (Simple Notification Service)** is used by CloudWatch to deliver alarm notifications.

- CloudWatch alarms send to an **SNS Topic**
- An SNS Topic can have multiple **subscribers** (email addresses, Lambda functions, SQS queues, etc.)
- When the alarm triggers, SNS fans out the notification to all subscribers

### SNS Subscription Confirmation

When you create a new SNS topic with your email, AWS sends a **confirmation email**:

```
Subject: AWS Notification - Subscription Confirmation

You have chosen to subscribe to the topic:
arn:aws:sns:us-east-1:948425238772:Web012_CloudWatch_Alarm

To confirm this subscription, click or visit the link below:
[Confirm subscription]
```

> ⚠️ **You MUST click "Confirm subscription"** in the email before you will receive alarm notifications. Without confirmation, no emails are sent.

**Verify subscription status:**
```
SNS → Subscriptions
→ Status: PendingConfirmation → Confirmed ✅
```

## 10. Hands-On Lab — CPU Alarm with SNS Notification

### Overview

This lab demonstrates:
1. Installing `stress` on EC2 to generate artificial CPU load
2. Setting a CloudWatch alarm on CPU utilization
3. Receiving an email notification via SNS when the alarm triggers

### Step 1 — Launch EC2 Instance

```
EC2 → Launch Templates → Actions → Launch Instance from Template
  Name: web012 (unique name for easy identification)
→ Launch Instance
```

---

### Step 2 — Connect to Instance and Install Stress

```bash
# SSH to instance (Amazon Linux 2023)
ssh -i key.pem ec2-user@<PUBLIC_IP>

# Switch to root
sudo -i

# Verify OS
cat /etc/os-release
# → NAME="Amazon Linux", VERSION="2023"

# Install stress tool
dnf install stress -y     # Amazon Linux / CentOS
# OR
apt install stress -y     # Ubuntu
```

**Successful installation output:**
```
Installing: stress x86_64 1.0.7-2.amzn2023.0.1  amazonlinux  34 k
Complete!
```

---

### Step 3 — Understand the Stress Tool

Running `stress` without arguments shows the help:

```bash
stress
```

```
stress: imposes certain types of compute stress on your system

Usage: stress [OPTION [ARG]] ...
  -c, --cpu N     spawn N workers spinning on sqrt()
  -i, --io N      spawn N workers spinning on sync()
  -m, --vm N      spawn N workers spinning on malloc()/free()
  -d, --hdd N     spawn N workers spinning on write()/unlink()
  -t, --timeout N timeout after N seconds
```

### Stress Command Examples

**Check CPU count:**
```bash
nproc
# → 1 (for t2.micro)
```

**Stress CPU for 60 seconds:**
```bash
stress --cpu $(nproc) --timeout 60s
# OR manually:
stress --cpu 2 --timeout 60s
```

**Stress memory:**
```bash
stress --vm 1 --vm-bytes 512M --timeout 60s
```

**Stress disk I/O:**
```bash
stress --hdd 1 --timeout 60s
```

**Stress CPU + Memory + Disk together:**
```bash
stress \
  --cpu 2 \
  --vm 1 \
  --vm-bytes 512M \
  --hdd 1 \
  --timeout 60s
```

**For CloudWatch alarm testing (5 minutes of high CPU):**
```bash
stress --cpu $(nproc) --timeout 300s
```

---

### Step 4 — Run Stress in Background (Random Intervals)

Create a script that runs stress randomly (simulates real-world load spikes):

```bash
# Create script file
vi stress.sh
```

```bash
#!/bin/bash
# Run stress at random intervals to simulate real-world CPU spikes
while true; do
  DURATION=$((RANDOM % 60 + 30))     # Random 30-90 seconds of stress
  INTERVAL=$((RANDOM % 30 + 10))     # Random 10-40 seconds of rest
  stress -c 35 -t ${DURATION}s
  sleep $INTERVAL
done
```

```bash
# Make executable
chmod +x stress.sh

# Run in background (survives SSH session close)
nohup ./stress.sh &

# Verify it's running
ps -ef | grep '[s]tress'
# → Shows stress worker processes
```

**Monitor CPU in real time:**
```bash
top
# → CPU utilization showing high load
```

### Step 6 — Create CloudWatch Alarm

```
CloudWatch → Alarms → All Alarms → Create Alarm

Step 1: Select Metric
  → Browse → EC2 → Per-Instance Metrics
  → Search with your Instance ID
  → Select: CPUUtilization
  → Select Metric

Step 2: Configure Conditions
  Metric name:  CPUUtilization
  Period:       1 minute (or 5 minutes for basic monitoring)
  Threshold:    Greater than or equal to 60%
  Alarm when:   ALARM (threshold breached)

  → Next

Step 3: Configure Actions
  Alarm state trigger: In Alarm
  Send notification to: Create new SNS topic
    Topic name:   Web012_CloudWatch_Alarm
    Email:        your-email@example.com
    → Create Topic

  (Optional EC2 Actions — for automation):
    Stop instance
    Terminate instance
    Reboot instance  ← useful for auto-recovery from high load

  → Next

Step 4: Add Name and Description
  Alarm name:    Warning | High load on web012 server
  Description:   CPU utilization above 60% for 1 minute

  → Next → Create Alarm
```

> **Important:** After creating the alarm, you will receive a **subscription confirmation email**. You MUST click "Confirm subscription" to activate email notifications.

---

### Step 7 — Understanding Alarm Thresholds

```
Typical Threshold Strategy:
  Below 50%  → OK        (normal operation)
  60%+       → WARNING   (alert, monitor closely)
  80%+       → CRITICAL  (immediate action required)
```

> Setting the right threshold comes with **experience and knowledge of your application**. Work with your monitoring team to determine when CPU utilization actually indicates a problem vs. normal load spikes.

**The key insight:**
```
CPU going UP then DOWN quickly = Normal (like blood pressure during exercise)
CPU going UP and STAYING HIGH = Problem (requires investigation)
```

## 12. CloudWatch Advanced Features (Overview)

### Application Performance Monitoring (APM)
- **Application Signals** — auto-detects latency, error rates, request rates
- **CloudWatch Synthetics** — canary scripts simulate user behavior to detect issues proactively
- **CloudWatch RUM** — real user monitoring from actual sessions
- **Service Level Objectives (SLOs)** — define and track reliability targets

### Infrastructure Monitoring
- **Database Insights** — SQL query performance, database load for RDS
- **Lambda Insights** — memory, CPU, cold start detection for Lambda functions
- **Container Insights** — metrics from ECS, EKS, and Kubernetes clusters

### CloudWatch Agent
- Install on EC2 instances to collect **detailed system metrics** not available by default
- Collects: processes, CPU, memory, disk, network from OS level
- Streams **application logs** from EC2 to CloudWatch Logs
- Supports both Windows and Linux
- Integrates with Systems Manager for centralized configuration

### Cross-Account Monitoring
- Set up a **central monitoring account** to view metrics, logs, and traces from multiple accounts
- Create cross-account dashboards and alarms

### OpenTelemetry Support
- Native OTLP endpoints for metrics, logs, and traces
- Use any OpenTelemetry-compatible SDK without proprietary agents

## 13. Viewing and Customizing CloudWatch Graphs

### Accessing Metrics Graphs

**From the EC2 Console:**
```
EC2 → Instances → Select instance → Monitoring tab
→ View graphs for: CPU, Disk, Network, Status Checks
→ Data range: last hour to last two weeks
```

**From CloudWatch directly:**
```
CloudWatch → Metrics → All Metrics
→ AWS Namespaces → EC2 → Per-Instance Metrics
→ Search by Instance ID
→ Select CPUUtilization → Graph selected
```

### Customizing the Time Range

On any CloudWatch graph, you can adjust the view:

| View Option | Description |
|---|---|
| **1h / 3h / 12h / 1d / 1w / 2w** | Quick relative time presets |
| **Custom → Relative** | Define your own relative period (e.g., "last 15 minutes") |
| **Custom → Absolute** | Set specific start and end dates/times |

> Use **custom → relative** for real-time monitoring; use **absolute** when reviewing an incident that happened at a specific time.

## 14. Monitoring AWS Billing with CloudWatch

> You can set up a **billing alarm** to receive notifications when your estimated AWS charges exceed a defined threshold — preventing unexpected bills.

### Step 1 — Enable Billing Alerts

```
AWS Console → Your Account (top right) → Billing Dashboard
→ Billing Preferences
→ ✅ Check "Receive billing alerts"
→ Save Preferences
```

> This step must be done **before** you can create billing alarms in CloudWatch. Billing data is only available in **us-east-1 (N. Virginia)** region.

### Step 2 — Create a Billing Alarm

```
CloudWatch → Alarms → Create Alarm
→ Select Metric → Billing → Total Estimated Charge

Settings:
  Metric:     EstimatedCharges
  Currency:   USD
  Threshold:  Greater than $X (e.g., $5 for learning account)

Actions:
  Send notification to: [existing SNS topic or create new]
  Email: your-email@example.com

Alarm name: AWS-Billing-Alarm-$5-threshold

→ Create Alarm
```

### What You Receive

When your estimated charges exceed the threshold:

```
Subject: ALARM: "AWS-Billing-Alarm-$5-threshold"

Your AWS account estimated charges have exceeded $5.00
Current estimated charge: $7.23

View your billing details at:
https://console.aws.amazon.com/billing/
```

### Best Practices for Billing Alarms

| Recommendation | Why |
|---|---|
| Set alarm on Day 1 of your AWS account | Prevents surprise bills from the start |
| Set threshold low for learning accounts | Catch issues before they grow |
| Check billing dashboard regularly | Identify which services are costing money |
| Use AWS Free Tier alerts | AWS also sends free tier usage alerts |

> ⚠️ **Always set a billing alarm** when learning AWS. Forgotten running instances, Elastic IPs, and data transfer charges can add up quickly.

## 15. Cleanup

After completing the CloudWatch lab:

```
Step 1: Stop the stress test
  pkill stress

Step 2: Delete CloudWatch Alarm
  CloudWatch → Alarms → Select alarm → Actions → Delete
  (Alarm persists even after instance is terminated — must delete manually)

Step 3: Terminate EC2 Instance
  EC2 → Instances → Select → Instance State → Terminate

Step 4: Optional — Delete SNS Topic
  SNS → Topics → Select → Delete
```

> Even after terminating the EC2 instance, the alarm will remain in CloudWatch with "Insufficient Data" state. No charges for alarms under 10, but clean up to keep your environment tidy.
