# EBS Snapshots — Backup, Restore & Resize

---

## 1. What are EBS Snapshots?

> **EBS Snapshots** are **point-in-time backups of EBS volumes**, stored in Amazon S3. They allow you to protect your data and recover from data loss, corruption, or accidental deletion.

### How Snapshots Work — Incremental Backup

```
Snapshot 1 (First ever snapshot)
  → Full copy of ALL data on the volume (e.g., 100 GB)

Snapshot 2 (After changes)
  → Only the CHANGED blocks are copied (e.g., 5 GB changed)
  → You are billed only for the 5 GB of changed data

Snapshot 3 (After more changes)
  → Only the NEW changed blocks since Snapshot 2
```

**Example:**
- Volume: 100 GB total data
- Only 5 GB changed since last snapshot
- The next snapshot uses only **5 GB of additional storage**
- Yet both snapshots appear as **complete, full backups** when you restore

> **Important:** When you delete a snapshot, only the data that is **not referenced by any other snapshot** is removed. All active snapshots contain **all the information needed to restore the volume** to that exact point in time.

### Key Features of EBS Snapshots

| Feature | Description |
|---|---|
| **Immediate access** | New volumes created from snapshots are immediately accessible |
| **Resize volumes** | Create a new volume larger than the original snapshot |
| **Share snapshots** | Share with other AWS accounts or make public |
| **Copy across regions** | Move data between AWS regions via snapshot copy |
| **Change volume type** | Restore as a different volume type (e.g., gp2 → gp3 → io1) |
| **Encrypt unencrypted volumes** | Create an encrypted volume from an unencrypted snapshot |
| **Change Availability Zone** | Move a volume to a different AZ via snapshot |

## 3. Setting Up the Volume and Database

### Step 1 — Create and Attach EBS Volume

```
EC2 → Elastic Block Store → Volumes → Create Volume

Settings:
  Volume type:        gp3
  Size:               5 GB (or 100 GB for lab)
  Availability Zone:  Same zone as your instance (e.g., us-east-1c)
  Tag:                Name = db01-mysql-vol

→ Create Volume
→ Select volume → Actions → Attach Volume
→ Select instance → Device name: /dev/sdh → Attach
```

### Step 2 — Partition the Volume

```bash
# List all disks — find your new volume
fdisk -l
# → Shows /dev/xvdh (new, unpartitioned)

# Create partition
fdisk /dev/xvdh
# Commands inside fdisk:
#   n  → new partition
#   p  → primary
#   1  → partition number 1
#   (Enter) → first sector (default)
#   (Enter) → last sector (use entire disk)
#   w  → write and exit

# Verify partition created
fdisk -l
# → Shows /dev/xvdh1  100G  83 Linux
```

**Real output:**
```
Disk /dev/xvdh: 100 GiB, 107374182400 bytes, 209715200 sectors
Device     Boot Start       End   Sectors  Size Id Type
/dev/xvdh1       2048 209715199 209713152  100G 83 Linux
```

### Step 3 — Format the Partition

```bash
# Format with XFS filesystem
mkfs.xfs /dev/xvdh1
```

> ⚠️ **Common mistake:** Running `mkfs.xfs /dev/xvdh` (whole disk) instead of `mkfs.xfs /dev/xvdh1` (partition) gives:
> ```
> mkfs.xfs: /dev/xvdh appears to contain a partition table (dos).
> mkfs.xfs: Use the -f option to force overwrite.
> ```
> **Always format the partition (`/dev/xvdh1`), not the whole disk (`/dev/xvdh`).**

**Successful output:**
```
meta-data=/dev/xvdh1    isize=512    agcount=4, agsize=6553536 blks
data     =              bsize=4096   blocks=26214144, imaxpct=25
log      =internal log  bsize=4096   blocks=16384, version=2
```

### Step 4 — Create Mount Point and Mount

```bash
# Create the directory (MariaDB stores data here by default)
mkdir /var/lib/mysql

# Mount partition to directory
mount /dev/xvdh1 /var/lib/mysql

# Verify mount
df -h
```

**Output:**
```
Filesystem      Size  Used Avail Use% Mounted on
/dev/xvda1      8.0G  1.7G  6.3G  21% /
/dev/xvdh1      100G  746M  100G   1% /var/lib/mysql
```

### Step 5 — Install and Start MariaDB

```bash
# Before install — directory is empty
ls /var/lib/mysql
# → (nothing)

# Install MariaDB (Amazon Linux)
dnf install mariadb105-server -y

# Start the service
systemctl start mariadb

# MariaDB initializes data files on the mounted volume
ls /var/lib/mysql
# → aria_log.00000001  ib_buffer_pool  ibdata1  mysql  performance_schema ...
```

**This confirms:**
- ✅ EBS volume mounted correctly at `/var/lib/mysql`
- ✅ XFS filesystem working
- ✅ MariaDB initialized its databases on the new EBS volume

```bash
# Enable auto-start on reboot
systemctl enable mariadb

# Check status
systemctl status mariadb
# → Active: active (running)
```

## 4. Taking a Snapshot (Backup)

> **Best practice:** Stop the instance before taking a snapshot of the **root volume**. For data volumes (like `/var/lib/mysql`), stopping the service is recommended.

### Via AWS Console

```
EC2 → Elastic Block Store → Volumes
→ Select your data volume (db01-mysql-vol)
→ Actions → Create Snapshot

Settings:
  Name:        db01-mysql-snapshot
  Description: MariaDB data volume snapshot before changes
  Tags:        Name = db01-mysql-snapshot

→ Create Snapshot
```

### Monitor Snapshot Progress

```
EC2 → Elastic Block Store → Snapshots
→ Status: pending → (wait) → completed
```

> The **first snapshot** copies all data (full backup). All subsequent snapshots are **incremental** — only changed blocks.

## 5. Simulating Data Loss / Corruption

```bash
# Delete all data from the database volume
rm -rf /var/lib/mysql/*

# Attempt to restart MariaDB
systemctl restart mariadb
# → FAILED — data missing

# Check status — shows errors
systemctl status mariadb
# → Failed with exit-code, errors about missing data files
```

**We now have a broken service and lost data — exactly the scenario where snapshots save us.**

## 6. Recovering Data — Create Volume from Snapshot

### Unmount the Corrupted Volume

```bash
# Check for processes using the directory
lsof /var/lib/mysql
# If any process is listed, kill it:
# kill -9 <PID>

# Unmount
umount /var/lib/mysql

# Verify it's unmounted
df -h
# → /dev/xvdh1 should no longer appear
```

### Rename the Corrupted Volume (for clarity)

```
EC2 → Volumes → Select your data volume
→ Edit Name tag: "db01-mysql-vol-corrupted"
```

### Create New Volume from Snapshot

```
EC2 → Elastic Block Store → Snapshots
→ Select your snapshot
→ Actions → Create Volume from Snapshot

Options available:
  Volume Type:        gp3 (can change from gp2/gp3 to io1 etc.)
  Size:               9 GB (increased from original 5 GB) ← can only increase
  Availability Zone:  Same as your instance (e.g., us-east-1c)
  Encryption:         Can encrypt an unencrypted volume here
  Name tag:           db01-mysql-vol-recovered

→ Create Volume
```

**Key options when creating from snapshot:**

| Option | What You Can Do |
|---|---|
| **Volume type** | Change from general purpose to provisioned IOPS (better I/O for DB) |
| **Size** | Increase only — decreasing risks data loss |
| **Availability Zone** | Change to move volume to a different AZ |
| **Encryption** | Encrypt a previously unencrypted volume |

> **To move a volume between regions:** Take a snapshot → Copy snapshot to target region → Create volume from snapshot in that region.

### Detach the Corrupted Volume

```
EC2 → Volumes → Select "db01-mysql-vol-corrupted"
→ Actions → Detach Volume
→ Wait for "available" state
→ Actions → Delete Volume
```

### Attach the Recovered Volume

```
EC2 → Volumes → Select "db01-mysql-vol-recovered"
→ Actions → Attach Volume
→ Instance: select your instance
→ Device name: /dev/sdh (or same as before)
→ Attach Volume
```

### Verify Partition Exists

```bash
fdisk -l
# → Shows /dev/xvdh with /dev/xvdh1 partition intact
# The snapshot preserved the partition table and data
```

### Mount the Recovered Volume

```bash
mount /dev/xvdh1 /var/lib/mysql

# Verify mount
df -h
# → /dev/xvdh1 appears at /var/lib/mysql

# Check data is restored
ls /var/lib/mysql
# → aria_log.00000001  ib_buffer_pool  ibdata1  mysql  performance_schema ...
# DATA IS BACK! ✅

# Restart MariaDB
systemctl restart mariadb
# → SUCCESS

# Check status
systemctl status mariadb
# → Active: active (running) ✅
```

## 7. Resizing the Filesystem After Volume Increase

When you create a volume from a snapshot with a **larger size** (e.g., 5 GB → 9 GB), the EBS volume is 9 GB but the **filesystem still shows 5 GB** — because it was created from a 5 GB snapshot.

```bash
df -h /var/lib/mysql
# → /dev/xvdh1   5G   ...   /var/lib/mysql  ← still shows old size!
```

You need to **resize the filesystem** to use the full new volume size.

### Resize Steps for XFS

```bash
# Unmount first
umount /var/lib/mysql

# Delete old partition and recreate with full size
fdisk /dev/xvdh
#   d  → delete partition
#   n  → new partition
#   p  → primary
#   1  → partition number
#   (Enter) → first sector
#   (Enter) → last sector (uses full disk size now)
#   w  → write

# Remount (no need to reformat — data is preserved in XFS)
mount /dev/xvdh1 /var/lib/mysql

# Grow the XFS filesystem to fill the partition
xfs_growfs /var/lib/mysql

# Verify new size
df -h /var/lib/mysql
# → /dev/xvdh1   9G   ...   /var/lib/mysql  ← now shows full 9 GB ✅
```

### Resize for ext4 Filesystem

```bash
# After remounting:
resize2fs /dev/xvdh1
# (May prompt you to run e2fsck first if needed)
```

> **Note:** If the new volume is the **same size** as the original, no filesystem resize is needed — just mount it.

## 8. Making the Mount Persistent

After recovery, ensure the volume remounts automatically on reboot:

```bash
# Get the UUID of the partition
blkid /dev/xvdh1
# → /dev/xvdh1: UUID="7c6d3c6d-1234-5678-9abc-def012345678" TYPE="xfs"

# Backup fstab
cp /etc/fstab /etc/fstab.bak

# Edit fstab
vi /etc/fstab
# Add this line:
UUID=7c6d3c6d-1234-5678-9abc-def012345678 /var/lib/mysql xfs defaults,nofail 0 2

# Test fstab entry
umount /var/lib/mysql
mount -a

# Verify
df -h
# → /dev/xvdh1 should be mounted again
```

## 9. Additional Snapshot Features

### Copy Snapshot to Another Region

Use case: Move data between regions or set up disaster recovery.

```
Snapshots → Select snapshot
→ Actions → Copy Snapshot
→ Destination Region: (select target region)
→ Copy

Go to target region → Snapshots → Create Volume from Snapshot
```

> Not included in free tier — charges apply for snapshot storage and data transfer.

### Share Snapshot with Another AWS Account

Use case: Transfer data between AWS accounts.

```
Snapshots → Select snapshot
→ Actions → Snapshot Settings → Modify Permissions
→ Add account ID of the target account
→ Save

Target account can now see the snapshot and create volumes from it
```

### Make a Snapshot Public

```
Snapshots → Modify Permissions
→ Public → Save
```

> ⚠️ Making snapshots public means anyone can access your data. Only use for intentional public distributions.

### Create AMI from Snapshot

```
Snapshots → Select snapshot → Actions → Create Image from Snapshot
→ Creates a bootable AMI (Amazon Machine Image) from the snapshot
```

## 10. lsof — Finding Processes Using a Directory

Before unmounting, always check if any process is using the directory:

```bash
# Check what is using the directory
lsof /var/lib/mysql

# Example output if a process is using it:
# COMMAND  PID   USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
# bash     1234  root  cwd  DIR   202,1   ...       cwd  /var/lib/mysql
# (cwd = current working directory — someone cd'd into it)

# If nothing appears — safe to unmount
# If processes appear — kill them first:
kill -9 <PID>

# Then unmount
umount /var/lib/mysql
```

> If you try to unmount while a process is using the directory, you get: `umount: target is busy`
