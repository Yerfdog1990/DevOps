# AWS Auto Scaling Groups (ASG) 

---

## 1. What is Auto Scaling?

> **AWS Auto Scaling** automatically adjusts the number of EC2 instances in your group based on demand — adding instances when load increases and removing them when load decreases.

Auto Scaling integrates with **CloudWatch** to monitor metrics (like CPU utilization) and triggers scaling actions based on alarms you define.

### Why Auto Scaling?

| Problem | Auto Scaling Solution |
|---|---|
| Traffic spike causes server overload | Automatically adds more instances |
| Low traffic wastes money on idle servers | Automatically removes unnecessary instances |
| A server crashes or becomes unhealthy | Automatically replaces it with a healthy one |
| Manual scaling is slow and reactive | Scaling happens automatically in minutes |

## 2. Key Concepts

### Capacity Settings

| Setting | Description |
|---|---|
| **Desired Capacity** | The number of instances ASG tries to maintain at all times |
| **Minimum Capacity** | ASG will never scale below this — always keeps at least this many instances |
| **Maximum Capacity** | ASG will never scale above this — prevents runaway cost |

**Example:**
```
Min: 1   Desired: 2   Max: 4

  Load increases above 50% CPU:
    ASG adds instances → 3, 4 (max)

  Load decreases below 50% CPU:
    ASG removes instances → 2, 1 (min, never goes below)
```

### Stateless vs. Stateful Applications

> ⚠️ **Critical concept when using ASG:** ASG can delete and replace instances at any time. If your instance stores data locally, that data will be lost.

| Type | Description | Safe with ASG? |
|---|---|---|
| **Stateless** | Instance stores no local data — data lives in shared storage (EFS, S3, RDS) | ✅ Yes |
| **Stateful** | Instance stores data on local disk (EBS) | ❌ No — data lost when instance is replaced |

> **Design your application as stateless** when using ASG: use EFS for shared files, RDS for databases, S3 for objects. Your instances become compute resources only — CPU, memory, OS, application.

## 3. Prerequisites Before Creating an ASG

ASG needs several components already in place:

```
Required Before Creating ASG:
│
├── 1. Launch Template
│   → Defines instance settings: AMI, instance type, key pair, security group
│
├── 2. Target Group (if using a load balancer)
│   → Empty — ASG will populate it with instances
│   → Do NOT manually add instances
│
└── 3. Application Load Balancer (if serving web traffic)
    → Must be in ACTIVE state before creating ASG
    → Load balancer is NOT mandatory for ASG — only needed for web traffic
```

> **Load balancer is not mandatory for ASG** — some use cases (batch processing, internal jobs, background workers) don't need one. Only required for web-facing traffic.

### Step 3 — Integrate with Other Services

```

  ✅ Attach to an existing load balancer
  → Choose from existing load balancer target groups
  → Select: inner-peace-ASG-TG

Health Checks:
  ✅ EC2 health checks (always on)     → Checks hardware/VM health
  ✅ ELB health checks (recommended)   → Checks if service responds on port 80
  ✅ EBS health checks (optional)      → Checks attached volumes

Health check grace period: 300 seconds
  (Gives new instances time to fully start before health checks begin)
```

### Health Check Types Explained

| Health Check | What It Checks | When to Use |
|---|---|---|
| **EC2** (always enabled) | Hardware and VM health | Always — basic check |
| **ELB** | HTTP response on port 80 — is the service actually running? | ✅ Recommended for web servers |
| **EBS** | Root and attached volume health | When data integrity is critical |

> **Why ELB health check matters:** EC2 health check only detects VM-level issues. If Apache crashes but the instance is still "running," EC2 reports it as healthy. ELB health check actually hits port 80 — if no response, it's unhealthy and ASG replaces it.

---

### Step 4 — Configure Group Size and Scaling

```
Group Size:
  Desired capacity: 2
  (ASG immediately launches 2 instances)

Scaling Limits:
  Min desired capacity: 1  (never go below 1 instance)
  Max desired capacity: 4  (never go above 4 instances)

Automatic Scaling:
  ✅ Target tracking scaling policy
  
  Policy name:   Target Tracking Policy
  Metric type:   Average CPU Utilization
  Target value:  50%
  
  → If group CPU > 50% → add instances (up to max 4)
  → If group CPU < 50% → remove instances (down to min 1)
  
  Instance warmup: 300 seconds
  (New instance metrics excluded from group avg for 5 min — avoids premature scaling)
  
  Disable scale in: (optional — check to prevent instance removal)
```

**Scaling Decision Examples:**

```
Desired: 2, Min: 1, Max: 4, Target: 50% CPU

Scenario 1: CPU at 80%
  → ASG adds instances → 3 instances
  → Still high → 4 instances (at max)

Scenario 2: CPU drops to 20%
  → ASG removes instances → 3 → 2 → 1 (at min, stops here)

Scenario 3: Instance crashes
  → ELB health check detects unhealthy
  → ASG launches replacement
  → Total stays at desired capacity
```

**Instance Maintenance Policy:**

| Policy | Behavior | Trade-off |
|---|---|---|
| **No policy** | Launch before terminating, but doesn't wait for readiness | Balanced |
| **Prioritize availability** | Launch and wait for healthy before terminating old | Higher cost temporarily |
| **Control costs** | Terminate and launch at the same time | Temporary reduced capacity |
| **Flexible (custom)** | Set min/max available capacity percentages | Full control |

## 9. Updating Your Application (Instance Refresh)

When you need to deploy application changes:

```
Old way (WRONG): SSH into each instance and change manually
ASG way (CORRECT): Build a new AMI → update launch template → instance refresh
```

### Workflow for Updates

```
1. Build new AMI with your changes
        ↓
2. Update launch template (new version or different template)
        ↓
3. Start Instance Refresh in ASG
        ↓
4. ASG replaces all instances with new ones from updated template
```

### Updating the Launch Template

```
Auto Scaling Groups → Select ASG → Details tab → Edit
→ Launch template: select updated template or version
→ Update
```

### Starting Instance Refresh

```
Auto Scaling Groups → Instance Refresh → Start Instance Refresh

Replacement type:
  ✅ Replace instances (rolling update)
  (or "Replace root volume" — replaces only disk, keeps instance)

Replacement method:
  ├── Prioritize availability: Launch new, wait, then terminate old (costs more)
  ├── Control costs: Terminate and launch at same time (less available briefly)
  └── Flexible: Custom min/max healthy percentages

Additional options:
  Skip matching: ✅ Don't replace instances already using the desired config
  CloudWatch alarm: Fail the refresh if alarm triggers
  Auto rollback: Revert changes if instance refresh fails
  Checkpoints: Pause at defined intervals for validation

→ Start Instance Refresh
```

> During instance refresh, watch the **Activity** tab — you'll see terminations and launches happening in sequence.

## 10. Instance Management in ASG

### Instance Actions

Select an instance in the Instance Management tab:

| Action | Description |
|---|---|
| **Detach** | Remove instance from ASG — ASG launches a replacement |
| **Set to Standby** | Instance excluded from scaling events — useful for troubleshooting |
| **Set Scaling Protection** | Prevents this specific instance from being terminated by ASG |

> **Set scaling protection** when: you need to SSH in and debug, run maintenance, or investigate an issue — prevents ASG from terminating the instance while you work.

## 11. Scaling Policies — Types

### Target Tracking (Recommended — Simplest)

```
ASG automatically adds/removes instances to maintain your target metric
  Metric: Average CPU Utilization
  Target: 50%
  → ASG does all the math for you
```

### Step Scaling

```
You define specific steps based on alarm thresholds:
  CloudWatch Alarm: CPU >= 50% → Add 1 instance
  CloudWatch Alarm: CPU >= 70% → Add 2 instances
  CloudWatch Alarm: CPU >= 90% → Add 4 instances

Step scaling creation:
  Auto Scaling Group → Automatic Scaling → Create Dynamic Scaling Policy
  → Policy type: Step scaling
  → Select CloudWatch alarm
  → Define steps: Add N instances when capacity is X
```

> Step scaling requires pre-created CloudWatch alarms. Numbers should be based on **real performance testing** — know when your application actually struggles.

### Scheduled Scaling

```
Pre-schedule capacity changes for known traffic patterns:

Auto Scaling Group → Automatic Scaling → Scheduled Actions

Example — Black Friday sale:
  Start time: November 29, 00:00 UTC
  End time:   December 1, 00:00 UTC
  Min: 5, Desired: 10, Max: 12
  Recurrence: Once (or cron for recurring)
```

Use case: you know a sale, event, or weekly peak is coming — pre-scale before the traffic hits.

### Predictive Scaling

```
Auto Scaling Group → Automatic Scaling → Predictive Scaling Policies

→ Uses historical CloudWatch data to forecast and scale BEFORE demand increases
→ Requires sufficient historical data (2+ weeks recommended)
→ Best for workloads with predictable, cyclical patterns
```

## 12. Troubleshooting — Common Issues

### 504 Gateway Timeout on Load Balancer

```
Symptom: http://alb-dns-name → 504 Gateway Time-out

Root Cause: No healthy targets in target group
  → Target group has 0 registered targets
  → OR all registered targets are unhealthy

Diagnosis:
  1. Check target group → Targets tab → 0 targets or all unhealthy

Fix (if ASG is configured):
  → Check ASG desired capacity is > 0
  → Check ASG activity log for launch failures
  → Check instances are in "InService" state

Fix (Security Group):
  → Instance SG must allow port 80 from Load Balancer SG
  → EFS SG (port 2049) only ≠ HTTP SG (port 80)
  → Wrong SG attached → health checks timeout → 0 healthy targets
```

### Security Group Mismatch

```
Problem: Instances using Web01-EFS SG (only allows port 2049)
  → Load balancer cannot reach port 80

Error metrics in CloudWatch:
  UnhealthyRoutingRequestCount
  UnhealthyStateRouting
  UnhealthyStateDNS

Fix:
  Option A: Add HTTP (port 80) from LB SG to the EFS SG (not recommended)
  Option B: Update launch template to use correct web SG, not EFS SG
  → Correct SG for web instances: allows port 80 from LB SG
```

### Target Registration Failures

```
Error: "Your selected targets failed to register"

Check:
  ✅ Instances are in Running state (not terminated/stopping)
  ✅ Instances are in the same VPC as the target group
  ✅ Instances are in the same region
  ✅ Security groups allow traffic from LB on port 80
  ✅ Web server is running and listening on port 80
  ✅ Target type matches (instance vs IP vs Lambda)
```

## 13. ASG + EFS — The Complete Architecture

```
Users (Internet)
     ↓
Application Load Balancer
  → inner-peace-ASG-ALB
  → Listener: HTTP:80
  → Target Group: inner-peace-ASG-TG
     ↓
Auto Scaling Group (NRP-ASG)
  → Min: 1  Desired: 2  Max: 4
  → Launch Template: inner-peace-shared
    (AMI with EFS fstab configured)
  ┌──────────────────────────────┐
  │  Web01 (us-east-1c)         │
  │  /var/www/html/images → EFS │
  ├──────────────────────────────┤
  │  Web02 (us-east-1d)         │
  │  /var/www/html/images → EFS │
  └──────────────────────────────┘
           ↓ both mount
     Amazon EFS
     (images shared across all instances)

CloudWatch Monitors:
  → CPU Utilization across group
  → If > 50% → ASG adds instance
  → If < 50% → ASG removes instance
  → New instance mounts EFS on boot
     → immediately serves the same images ✅
```

## 14. Cleanup

```
Step 1: Delete Load Balancer
  Load Balancers → Select → Actions → Delete

Step 2: Delete Auto Scaling Group
  Auto Scaling Groups → Select → Delete
  (This terminates all instances in the ASG)

  OR to keep ASG structure but remove instances:
  → Set desired=0, min=0 → ASG removes all instances → no cost

Step 3: Verify instances terminated
  EC2 → Instances → all in "terminated" state

Step 4: Delete Target Group (optional — no charge)
  Target Groups → Select → Delete

Step 5: Keep AMI for future lectures
  Deregister old AMIs you don't need
  Keep EFS AMI (inner-peace-EFS)
  Keep EFS file system and access point (free tier)

Step 6: Verify EC2 Dashboard
  ✅ 0 Running instances
  ✅ 0 Load balancers
  ✅ 1 AMI (EFS AMI kept)
  ✅ 0 Elastic IPs
```

> **You cannot manually delete ASG instances** — if you terminate one, ASG immediately launches a replacement to maintain desired capacity. You must set desired=0 or delete the ASG itself.
