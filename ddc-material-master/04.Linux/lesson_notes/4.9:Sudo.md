# Linux sudo

## 1. What is `sudo`?

`sudo` (superuser do) allows a normal user to **execute commands with root privileges** without actually being or logging in as root. Think of it as a power of attorney — a regular user can act on behalf of root for specific commands.

Common uses:
- Run a single command as root: `sudo yum install git`
- Switch entirely to the root user: `sudo -i`

Only users who are **listed in the sudoers file** can use `sudo`. By default, only the `vagrant` user has this privilege on a Vagrant-created VM.

---

## 2. `sudo` vs No `sudo`

```bash
# As vagrant user — WITHOUT sudo (fails)
yum install git
# Error: You need to be root to perform this command

useradd testuser
# Error: Permission denied

# As vagrant user — WITH sudo (works)
sudo yum install git
sudo useradd testuser
sudo -i              # Switch to root user entirely
```

---

## 3. What Happens When a Non-Sudo User Tries

If a user is **not in the sudoers file** and tries to use `sudo`:

```bash
[ansible@localhost ~]$ sudo useradd test12
[sudo] password for ansible:
ansible is not in the sudoers file. This incident will be reported.
```

Key points:
- It asks for the **user's own password** (not root's password)
- It then denies access and logs the attempt
- The incident is recorded in the system logs

---

## 4. The Sudoers File — `/etc/sudoers`

This file controls who can use `sudo` and what they can do with it.

```bash
cat /etc/sudoers        # View the file
```

**You cannot edit it directly with vim**, even as root — it has no write permission by design:

```bash
vim /etc/sudoers        # Will fail or throw write error — do NOT do this
```

This is intentional. A syntax error in this file can **break sudo entirely**, locking you out of root access.

---

## 5. `visudo` — The Safe Way to Edit Sudoers

`visudo` opens `/etc/sudoers` in write mode **with syntax checking**. If you make a mistake, it catches it before saving.

```bash
visudo
```

If you accidentally introduce a syntax error:
```
>>> sudoers file: syntax error, line 9 <<<
What now?
```
Type `e` to go back and fix the error before saving. This prevents a broken sudoers file.

### Finding the Right Line

Inside `visudo`, set line numbers and search for `root`:
```vim
:se nu
/root
```

You'll find a line like this around line 100:
```
root    ALL=(ALL)       ALL
```

---

## 6. Granting `sudo` Privilege to a User

### Step 1 — Add the User Entry in `visudo`

Copy the root line and add a new line for the user below it:

```
root    ALL=(ALL)       ALL
ansible ALL=(ALL)       ALL
```

Save and quit (`:wq`).

### Step 2 — Test

```bash
su - ansible
sudo -i          # Prompts for ansible's own password
# Switches to root — success!
```

### Step 3 — Remove the Password Prompt (NOPASSWD)

When running scripts in the background, interactive password prompts aren't practical. To allow sudo without a password:

Open `visudo` again and update the ansible line:

```
ansible ALL=(ALL)       NOPASSWD: ALL
```

Now test again:
```bash
su - ansible
sudo -i           # No password prompt — switches to root immediately
sudo useradd test12   # Works without any password prompt
```

---

## 7. Sudoers Entry Format Explained

```
ansible   ALL=(ALL)    NOPASSWD: ALL
   ^        ^     ^        ^       ^
   |        |     |        |       └── Commands allowed (ALL = everything)
   |        |     |        └────────── No password required
   |        |     └─────────────────── Run as any user
   |        └───────────────────────── From any host
   └────────────────────────────────── Username (or %groupname)
```

| Part | Meaning |
|---|---|
| `ansible` | The user this rule applies to |
| `ALL=` | Applies from any host |
| `(ALL)` | Can run commands as any user |
| `NOPASSWD:` | Don't prompt for password |
| `ALL` | Can run any command |

## 8. The Safer Way — `/etc/sudoers.d/`

Directly editing `/etc/sudoers` carries risk. A syntax error there can break `sudo` completely — and if no root password is set (common in production), you could be locked out entirely.

The safer approach is to **create a separate file** inside `/etc/sudoers.d/`. Files here are automatically included by the main sudoers file.

```bash
ls /etc/sudoers.d/
# vagrant    ← this is how vagrant user gets sudo access by default
cat /etc/sudoers.d/vagrant
```

### Create Your Own File

```bash
vim /etc/sudoers.d/devops
```

Add the entry for a **group** (use `%` prefix for groups):
```
%devops    ALL=(ALL)    NOPASSWD: ALL
```

Save and quit. Now every user in the `devops` group can use `sudo` without a password.

To grant an individual user instead:
```
ansible    ALL=(ALL)    NOPASSWD: ALL
```

### Why This is Safer

| Method | Risk |
|---|---|
| Edit `/etc/sudoers` directly | Syntax error breaks all `sudo` |
| Use `visudo` | Syntax checked before saving |
| Create file in `/etc/sudoers.d/` | Safest — isolated file, main sudoers untouched |

> **Best practice:** Always use `/etc/sudoers.d/` for adding new sudo rules. Reserve `visudo` for editing existing entries in the main file only.

---

## 9. Adding a Group vs a User to Sudoers

```bash
# Grant sudo to a specific user
ansible    ALL=(ALL)    NOPASSWD: ALL

# Grant sudo to an entire group (% prefix means group)
%devops    ALL=(ALL)    NOPASSWD: ALL
```

With the group entry, **any user added to `devops` group automatically gets sudo access** — no need to update the sudoers file for each new user.

```bash
usermod -aG devops jenkins     # jenkins now has sudo access via devops group
```

## 10. Full Practical Walkthrough

```bash
# Step 1: Set a password for ansible (needed for su - ansible)
passwd ansible

# Step 2: Switch to ansible and test — should fail
su - ansible
sudo useradd test12
# ansible is not in the sudoers file. This incident will be reported.
exit

# Step 3: As root, open visudo and add ansible
visudo
# Add below root line:
# ansible ALL=(ALL) NOPASSWD: ALL
# Save and quit :wq

# Step 4: Switch to ansible and test again
su - ansible
sudo -i               # No password asked — switches to root
exit
sudo useradd test12   # Works without password

# ALTERNATIVELY — Safer method using sudoers.d
exit  # back to root
vim /etc/sudoers.d/devops
# Add: %devops ALL=(ALL) NOPASSWD: ALL

# Now all devops group members have sudo
```

## 11. Quick Reference Summary

| Command | What it does |
|---|---|
| `sudo <command>` | Run a command with root privilege |
| `sudo -i` | Switch to root user (interactive login) |
| `visudo` | Safely edit `/etc/sudoers` with syntax checking |
| `cat /etc/sudoers` | View the sudoers file |
| `ls /etc/sudoers.d/` | List custom sudoers drop-in files |
| `vim /etc/sudoers.d/devops` | Create a custom sudoers rule file |

### Sudoers Entry Patterns

| Entry | Effect |
|---|---|
| `ansible ALL=(ALL) ALL` | ansible can sudo (password required) |
| `ansible ALL=(ALL) NOPASSWD: ALL` | ansible can sudo (no password) |
| `%devops ALL=(ALL) NOPASSWD: ALL` | All devops group members can sudo |

---

## 12. Key Takeaways

- `sudo` lets normal users run commands with root privileges without knowing the root password.
- Only users listed in `/etc/sudoers` (or files in `/etc/sudoers.d/`) can use `sudo`.
- When a user runs `sudo`, it asks for **their own password**, not root's.
- **Never edit `/etc/sudoers` with a regular editor** — always use `visudo`, which validates syntax before saving.
- A syntax error in `/etc/sudoers` without `visudo` can break `sudo` entirely and lock you out.
- The **safest method** is to create a new file under `/etc/sudoers.d/` — this keeps the main file untouched.
- Use `%groupname` (with `%` prefix) to grant sudo to an entire group — much more scalable than per-user entries.
- `NOPASSWD: ALL` is needed for scripts and automation that run in the background without user interaction.
- In production environments, root passwords are often not set — `sudo` is the only path to root. Protect the sudoers file carefully.
