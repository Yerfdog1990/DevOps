## 1. The Build Process

Developers write **source code** (web app, mobile app, etc.) and commit changes regularly. Each change must be verified through a **build process**:

```
Source Code → Compile → Unit/Integration Test → Package → Health Check / Code Analysis
```

| Step | Description |
|------|-------------|
| **Source** | Code written/changed in a language like Java, .NET, C, C# |
| **Compile** | Compiler (e.g., `javac` for Java) converts source into output files (`.class` files) |
| **Unit Test** | Tests written by developers to test their own code (not QA/software testing) |
| **Package** | Compiled output archived into a distributable format |
| **Health Check / Code Analysis** | Finds upcoming bugs or security vulnerabilities |

### Packaging formats by target

| Target | Format |
|--------|--------|
| Windows software | `.exe`, `.msi` |
| Java | `.jar` / `.war` (web apps usually WAR) |
| Interpreted languages (Python, Ruby) | `.zip`, `.tar` |

Doing all this manually on every commit is too much work → **build tools automate the build process**.

## 2. Build Tools

| Tool | Notes |
|------|-------|
| **Maven** | For Java; XML-based (`pom.xml`) — declare dependencies, versions, packaging; Maven executes build phases automatically |
| **Ant** | For Java; more scripting involved; generally superseded by Maven |
| **MSBuild** | Microsoft Build Engine, for Microsoft products |
| **Gradle** | Groovy/Kotlin-based; faster (incremental builds) |
| **NAnt** | For Windows/.NET |
| **Make** | Builds executable programs (e.g., RPM packages) for the OS |

The build tool is chosen by developers/architects based on the programming language. This course uses **Java**, so **Maven**.

## 3. What is Maven?

Apache Maven is a **declarative, open-source build automation and project management tool** primarily for Java. It automates compiling, dependency management, testing, and packaging (JAR/WAR).

Unlike procedural tools (Ant), Maven follows **convention over configuration** — standard project layouts and lifecycles, no complex custom scripts.

### Core concepts

- **POM (`pom.xml`)** — Project Object Model; XML file at project root with project details, metadata, dependencies, and build plugins.
- **Dependency management** — dependencies listed in `pom.xml` are auto-downloaded from Maven repositories, including transitive dependencies.
- **Repositories**:
    - **Local** — on your machine (`~/.m2/repository`)
    - **Central** — default online community repository
    - **Remote** — private/company servers (e.g., Nexus, Artifactory)
- **Standard directory structure**:

```
src/main/java        # application source
src/main/resources   # config files, static assets
src/test/java        # unit tests (JUnit/TestNG)
target/              # build output: .class files, packaged artifacts
```

## 4. Maven Build Lifecycles

Maven has **three built-in lifecycles**:

| Lifecycle | Purpose |
|-----------|---------|
| **default** | Build and deployment of the project |
| **clean** | Remove artifacts of previous builds (deletes `target/`) |
| **site** | Generate project documentation/site |

### Key rule: sequential execution

Running any phase executes **all preceding phases** of that lifecycle first.
Example: `mvn package` runs `validate → compile → test → package`.

### Default lifecycle — main phases

```
validate → compile → test → package → verify → install → deploy
```

| Phase | Description |
|-------|-------------|
| **validate** | Project structure is correct; all necessary information available |
| **compile** | Compile source code (`.java` → `.class` in `target/`) |
| **test** | Run unit tests via the unit testing framework (no packaging/deployment needed) |
| **package** | Package compiled code into distributable format (JAR/WAR — defined in `pom.xml`) |
| **verify** | Run checks on integration test results; ensure quality criteria are met |
| **install** | Install the package into the **local repository** (`~/.m2`) for use by other local projects; dependencies are downloaded and cached locally |
| **deploy** | Copy final package to a **remote repository** to share with other developers/teams |

### Clean lifecycle

`pre-clean → clean → post-clean`

### Site lifecycle

`pre-site → site → post-site → site-deploy`

### Lifecycle vs Phase vs Goal

| Concept | What it is | Example |
|---------|-----------|---------|
| **Lifecycle** | Broad sequence of stages | `default` |
| **Phase** | A stage within a lifecycle | `compile` |
| **Goal** | Actual plugin task doing the work | `compiler:compile`, `surefire:test` |

Phases are just steps; **plugin goals bound to phases do the real work**. A phase with no bound goals doesn't execute. Bindings depend on `<packaging>` (jar, war, ear, pom — default is `jar`).

Hyphenated phases (`pre-*`, `post-*`, `process-*`) aren't usually called directly from the command line.

## 5. pom.xml Essentials

Minimal structure:

```xml
<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.app</groupId>
  <artifactId>myapp</artifactId>
  <version>0.0.1-SNAPSHOT</version>
  <packaging>jar</packaging>   <!-- jar (default), war, ear, pom -->

  <dependencies>
    <!-- libraries the project needs; downloaded automatically -->
  </dependencies>

  <build>
    <plugins>
      <!-- e.g., maven-compiler-plugin, spring-boot-maven-plugin -->
    </plugins>
  </build>
</project>
```

Compiler plugin example (set Java version):

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <version>3.13.0</version>
  <configuration>
    <release>17</release>
  </configuration>
</plugin>
```

## 6. Common Maven Commands

| Command | What it does |
|---------|--------------|
| `mvn validate` | Check project structure and configuration |
| `mvn compile` | Compile source code |
| `mvn test` | Compile and run unit tests |
| `mvn package` | Compile, test, and bundle into JAR/WAR |
| `mvn verify` | Run full lifecycle through integration test checks (preferred if unsure) |
| `mvn install` | Full build + copy artifact to local repo (`~/.m2`) |
| `mvn deploy` | Push artifact to remote repository |
| `mvn clean` | Delete `target/` (fresh start) |
| `mvn clean install` | Clean, then full build and local install (most common dev command) |
| `mvn clean deploy` | Clean build + deploy — typical in build/CI environments |
| `mvn package -DskipTests` | Package without running tests |
| `mvn clean install -Dmaven.test.skip=true` | Skip test compilation and execution |

Phases and goals can be mixed: `mvn clean dependency:copy-dependencies package`.

## 7. Key Takeaways for DevOps

- Developers/architects define the build process and phases; DevOps engineers mainly need to know **which phase to run and what to expect**.
- `mvn clean install` = clean old artifacts, run entire lifecycle, save output to local repo.
- Reference: Google "Build Lifecycle Maven" for official Apache docs on phases, plugins, and lifecycle bindings.
