## 1. The Source Code — vProfile Project

Repository: `github.com/<user>/vprofile-project`

- Presence of **`pom.xml`** at the root → it's a **Maven project**.
- `src/` — Java code written by developers.
- Developers initialize the Maven project (which generates `pom.xml`), then keep updating it and pushing to the repo.
- Every Maven command reads its information from `pom.xml`.

### pom.xml syntax basics

```xml
<version>v2</version>                <!-- opening tag, value, closing tag (/) -->

<properties>                          <!-- variables -->
  <spring.version>6.0.1</spring.version>
  <mysql-connector.version>8.0.33</mysql-connector.version>
</properties>

<dependencies>
  <dependency>                        <!-- one dependency -->
    <groupId>org.springframework</groupId>
    <artifactId>spring-core</artifactId>
    <version>${spring.version}</version>   <!-- references the property above -->
  </dependency>
</dependencies>
```

- Opening/closing tags with data in between; nested (cascading) tags.
- `${var}` references a variable from `<properties>`.
- Developers maintain this file — DevOps needs only a working knowledge of the syntax to make changes when required.
- Artifact name, version, and packaging (e.g., `vprofile-v2.war`) all come from `pom.xml`.

## 3. Install JDK and Maven

**JRE vs JDK:** JRE (Java Runtime Environment) only runs Java apps; **JDK (Java Development Kit) is required to build** them.

```bash
apt update
apt search jdk | grep 17          # find available packages
apt install openjdk-21-jdk -y     # install JDK 21
java -version                     # verify → 21
apt install maven -y              # install Maven
mvn -version                      # → 3.8.7, using default Java (21)
```

> **Key duty:** always get the required tool versions (Java, Maven, Node, etc.) from the developers — they build on their machines and know what works. Install exactly those versions.

## 4. Clone and Build

```bash
git clone https://github.com/<user>/vprofile-project.git   # HTTPS URL from GitHub
cd vprofile-project
git status                     # check branch (local branch is fine)
git branch -a                  # list all branches
git checkout <branch>          # switch if needed
```

Run through phases:

```bash
mvn validate    # validates project structure → BUILD SUCCESS
mvn test        # runs JUnit unit tests; reports go to target/
mvn install     # runs all previous phases + downloads dependencies
```

### Key facts

- `target/` = **output** of Maven commands (test reports, compiled classes, artifacts).
- Dependencies download from the **global Maven repository** by default (you can host your own proxy repo, e.g., Nexus).
- Dependencies are cached in **`~/.m2/repository`**; each dependency pulls its own transitive dependencies (long download list).

### Cleaning up

```bash
rm -rf ~/.m2/repository/*    # remove cached dependencies (do this when changing Maven version or dependencies)
rm -rf target                # remove build output
mvn clean install            # clean removes only target/, NOT ~/.m2
```

## 5. Troubleshooting Build Failures

### Failure 1: Java heap space

- Error: *problem creating war ... Java heap space* during `mvn install`.
- Cause: **resource issue** — t2.micro has ~1 GB RAM; the JVM ran out of heap while assembling the WAR.
- Fix — allocate more memory to Maven:

```bash
export MAVEN_OPTS="-Xmx1024m"
mvn install                    # → BUILD SUCCESS, target/vprofile-v2.war created
```

### Failure 2: Incompatible dependency version

- Simulated by editing `pom.xml`: downgrade **JaCoCo** plugin to `0.8.8`.
- Error: *error while instrumenting ... jacoco 0.8.8*.
- Cause: JaCoCo versions prior to 0.8.11 don't fully support Java 21 — a **compatibility issue**.
- Fix: upgrade JaCoCo to `0.8.11` in `pom.xml`, then `mvn clean install`.

### Debugging approach

Paste the error into an AI tool (ChatGPT, Amazon Q, etc.) **with context**: the error, `mvn -version` output, and the `pom.xml`. More context → better diagnosis. Distinguish **resource issues** (heap) from **build errors** (wrong dependency versions).

## 6. Switching JDK Versions (Ubuntu)

```bash
apt install openjdk-17-jdk -y      # now both 17 and 21 installed
java -version                      # still shows 21 (default)

update-alternatives --config java  # interactive prompt — choose 17 or 21
java -version                      # → 17
mvn clean install                  # project works on both 17 and 21
```

## 7. Using a Different Maven Version

Unlike Java, Maven has no version-switch command — **download the binary, extract, and call it by full path**.

1. Google "Download Maven 3 archive" → Apache archive distribution directory → pick version (e.g., **3.9.9**) → binaries → copy link to `apache-maven-3.9.9-bin.tar.gz`.

```bash
cd /tmp
wget <apache-maven-3.9.9-bin.tar.gz link>
tar xvf apache-maven-3.9.9-bin.tar.gz
cp -r apache-maven-3.9.9 /usr/local/maven3.9

# use full path to the binary for a non-default version
/usr/local/maven3.9/bin/mvn -version
cd ~/vprofile-project
/usr/local/maven3.9/bin/mvn clean install
```

- Plain `mvn` = default version; full path = specific version.
- You could set it as default, but it's not required — Jenkins handles multiple tool versions (covered later).
